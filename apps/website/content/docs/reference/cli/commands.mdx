## Rules that apply to every command

- **Extra positional arguments are an error.** Every command rejects positionals beyond the ones
  documented for it: `pair install ./a ./b` fails with `error: too many arguments for 'install'`
  (exit 1) instead of silently ignoring `./b`. This is what catches an unquoted option value —
  `--name Acme KB` (which used to mean `--name Acme`) now fails instead of half-working; quote it:
  `--name "Acme KB"`. This is a behavior change — earlier releases ignored the stray argument, so a
  wrapper script or CI job that passed one must drop it.
  [GitHub Releases](https://github.com/foomakers/pair/releases) names the release that introduced
  it.

## install

Install documentation and assets from KB source to target folder.

### Usage

```bash
pair install [target]
pair install [registry:target ...]
```

### Arguments

- `[target]` — Optional target directory path (default: current working directory)
- `[registry:target ...]` — Install specific registries to custom targets

### Options

| Option                      | Description                                                       |
| --------------------------- | ----------------------------------------------------------------- |
| `--list-targets`            | List all available asset registries with descriptions             |
| `--config <file>`           | Use custom configuration file (default: `config.json`)            |
| `--source <url\|path\|git>` | KB source: URL, local path, or git repo (overrides auto-download) |
| `--offline`                 | Skip KB download, use local source only                           |
| `--skip-verify`             | Skip package integrity verification (for ZIP sources)             |

**KB Source Options:**

- `--source <url>` — Download KB from custom HTTP/HTTPS URL or use local path
- `--source <git-url>` — Clone KB from a git repository (`*.git`, `git@…`, `ssh://git@…`, append `#ref` to pin version)
- `--offline` — Skip automatic KB download (requires `--source` with local path)

**Note:** Cannot combine `--source <url>` or `--source <git-url>` with `--offline`. The `--offline` flag requires `--source` with a local filesystem path.

**Target Resolution:** Registry output is written relative to the current working directory. When running via `pnpm --filter`, the CLI reads `INIT_CWD` (set by pnpm to the original invoking directory) so output lands at the monorepo root, not inside the filtered package directory.

### Examples

```bash
# List available registries
pair install --list-targets

# Install with defaults
pair install

# Install to custom directory
pair install ./my-custom-path

# Install specific registries
pair install github:.github knowledge:.pair

# Use custom KB source (remote URL)
pair install --source https://internal-mirror.company.com/kb.zip

# Use custom KB source (git repository)
pair install --source https://github.com/acme/kb-artifacts.git
pair install --source git@github.com:acme/kb-artifacts.git#v1.0.0

# Use custom KB source (local path)
pair install --source /absolute/path/to/kb-content
pair install --source ./relative/path/to/kb-content

# Offline mode (no KB download)
pair install --offline --source ./local-kb-content
```

## package

Package KB content into validated ZIP file for distribution.

### Usage

```bash
pair package [options]
```

### Options

| Option                        | Short | Description                                                  |
| ----------------------------- | ----- | ------------------------------------------------------------ |
| `--layout <mode>`             |       | Layout mode: `source` or `target` (default: `target`)        |
| `--output <path>`             | `-o`  | Output ZIP file path (default: `kb-package.zip`)             |
| `--source-dir <path>`         | `-s`  | Source directory to package (default: current directory)     |
| `--config <path>`             | `-c`  | Path to config.json file                                     |
| `--name <name>`               |       | Package name for manifest                                    |
| `--version <version>`         |       | Package version for manifest                                 |
| `--description <description>` |       | Package description for manifest                             |
| `--author <author>`           |       | Package author for manifest                                  |
| `--skip-registries <list>`    |       | Comma-separated registry names to exclude                    |
| `--root <path>`               |       | Custom root path for link relativization (default: `.pair/`) |
| `--log-level <level>`         | `-l`  | Set logging level (trace, debug, info, warn, error)          |
| `--interactive`               | `-i`  | Enter interactive mode with guided prompts                   |
| `--tags <tags>`               |       | Comma-separated tags (e.g., `"ai,devops,testing"`)           |
| `--license <license>`         |       | Package license (default: `MIT`)                             |
| `--org`                       |       | Enable organizational packaging mode                         |
| `--org-name <name>`           |       | Organization name (required when `--org`)                    |
| `--team <team>`               |       | Team name within the organization                            |
| `--department <department>`   |       | Department within the organization                           |
| `--approver <approver>`       |       | Package approver (free-text)                                 |
| `--compliance <tags>`         |       | Comma-separated compliance tags (e.g., `"SOC2,ISO27001"`)    |
| `--distribution <policy>`     |       | Distribution policy: `open`, `private`, or `restricted`      |

### Examples

```bash
# Package current directory (target layout — default)
pair package

# Package from source layout
pair package --layout source

# Package with custom output path
pair package -o dist/kb-v1.0.0.zip

# Package with metadata
pair package --name "My KB" --version 1.0.0

# Interactive package creation
pair package --interactive

# Organizational package
pair package --org --org-name "Acme Corp" --team "Platform" --compliance "SOC2,ISO27001"
```

### Interactive Mode

Quick mode is the default: omitting `--interactive` resolves smart defaults from `package.json`, `git config`, and saved preferences (`~/.pair/preferences.json`) and applies them in one shot — so `pair package` in a repo whose `package.json` name is `foo` produces a `foo` package, not `kb-package`. Passing `--interactive` (the guided selector, requires a TTY) enters a guided flow that pre-fills prompts from the _same_ resolved defaults and lets you confirm or override each. This guided/quick duality follows the [Guided / Quick Setup Convention](/docs/contributing/writing-skills#setup-skills-guided-vs-quick).

### Org Template

When `--org` is active, the CLI looks for `.pair/org-template.json` to pre-fill defaults. CLI flags override template values.

## kb-info

Display metadata from a KB package ZIP file, or — when no package path is given — check the
project's installed KB version against the current one.

### Usage

```bash
pair kb-info [package-path] [options]
```

### Options

| Option                 | Description                                                             |
| ---------------------- | ----------------------------------------------------------------------- |
| `--json`               | Output package metadata or version-check result as JSON format          |
| `--source <path\|url>` | KB source to resolve the current version from (version-check mode only) |
| `--log-level <level>`  | Set minimum log level (debug, info, warn, error)                        |

### Version Check Mode

Running `pair kb-info` without a package path compares the KB version recorded as installed in
the project (written by `install`/`update` on success) against the current one:

- **Up to date** — installed matches current, exit code 0.
- **Version drift** — installed differs from current; the output includes a migration-page URL
  for the version jump (one page per jump, per the docs Migrations index).
- **Unknown installed version** — legacy install with no recorded metadata; run `pair install` or
  `pair update` to record it.
- **Current version unavailable** — the source could not be resolved (offline, unreachable
  mirror, etc.); the installed version is still reported. Exit code is 0 in all cases — this is a
  metadata check only, it never performs migration.

`install` and `update` also print a non-blocking heads-up with the same migration-page pointer
when the version about to be applied differs from what's currently recorded.

### Examples

```bash
# Display package metadata
pair kb-info my-kb.zip

# Display as JSON
pair kb-info my-kb.zip --json

# Check installed vs current KB version
pair kb-info

# Version check, JSON output (for CI)
pair kb-info --json

# Version check against a custom source
pair kb-info --source /path/to/kb
```

## kb-cache

Inspect and reclaim the shared KB cache — the machine-wide directory where `install` and
`update` keep downloaded knowledge bases so repeated runs do not re-fetch them.

### Usage

```bash
pair kb-cache [list|prune] [options]
```

### Arguments

| Argument | Description                                                          |
| -------- | -------------------------------------------------------------------- |
| `list`   | Show every cache slot with its kind, size and label (default action) |
| `prune`  | Remove the slots that are safe to remove                             |

### Options

| Option                | Description                                                   |
| --------------------- | ------------------------------------------------------------- |
| `--dry-run`           | `prune` only: report what would be removed and delete nothing |
| `--json`              | Output the inventory or the prune result as JSON              |
| `--log-level <level>` | Set minimum log level (debug, info, warn, error)              |

### What prune removes — and what it never removes

`prune` removes only slots that a later `install`/`update` can recreate:

- **backup** — a `.bak` slot left behind by an interrupted install
- **stage** — an abandoned `.tmp-*` staging directory
- **legacy-git** — a pre-`external/` git clone at the cache root
- **official** — KB slots for CLI versions other than the one running

It never removes:

- **external KBs** (`external/`) — fetched from a URL the CLI does not retain, so deleting one
  is not undoable by re-running an install
- **every official slot when the running version cannot be resolved** — rather than compare
  against an empty version and delete the KB currently in use

A cache root that exists but cannot be read is reported as an error, not as an empty cache, and
a prune that fails to remove part of what it identified exits non-zero instead of reporting a
clean sweep.

This command reads the cache only — it never downloads a KB.

### Examples

```bash
# Show what the cache holds
pair kb-cache

# See what prune would reclaim, without deleting
pair kb-cache prune --dry-run

# Reclaim the stale slots
pair kb-cache prune

# Machine-readable inventory
pair kb-cache list --json
```

## kb-validate

Validate KB structure, links, and metadata using layout-aware validation.

### Usage

```bash
pair kb-validate [options]
```

This command takes **no positional argument** — the KB directory is passed as
`--path <path>` (a stray positional is rejected, see
[Rules that apply to every command](#rules-that-apply-to-every-command)).

### Options

| Option                            | Description                                                                            |
| --------------------------------- | -------------------------------------------------------------------------------------- |
| `--path <path>`                   | KB directory to validate (default: current directory)                                  |
| `--layout <mode>`                 | Layout mode: `source` or `target` (default: `target`)                                  |
| `--strict`                        | Zero tolerance: optional link patterns are discarded, every missing target is an error |
| `--ignore-config`                 | Consult no config: no registries resolve, so nothing is collected or checked           |
| `--skip-registries <list>`        | Comma-separated registry names to exclude from validation                              |
| `--optional-link-patterns <list>` | Comma-separated globs whose **missing** link targets are warnings, not errors          |
| `--log-level <level>`             | Set logging level (trace, debug, info, warn, error)                                    |

### Examples

```bash
# Validate current directory
pair kb-validate

# Validate another directory
pair kb-validate --path ./my-kb

# Validate source layout
pair kb-validate --layout source

# Validate with zero tolerance (optional link patterns discarded)
pair kb-validate --strict

# Validate excluding specific registries
pair kb-validate --skip-registries adoption,github

# Tolerate links into a codebase that is not checked out beside the KB
pair kb-validate --optional-link-patterns "apps/**,packages/**"
```

### Optional link patterns

A KB validated on its own still contains relative links into the codebase it
normally sits next to. Declaring those targets **optional** keeps every other link
checked, instead of switching whole registries off:

```json
{
  "link_validation": {
    "optional_link_patterns": ["apps/**", "packages/**"]
  }
}
```

Patterns are written in the **resolved** form — the target's path relative to the KB
root — because that form does not change with the depth of the file the link is written
in. Above: links landing on `<kb-root>/apps/…`, however deep the source file is. A target
that is a true **sibling** of the KB root resolves one level up, so its rule starts with
`../` (`../apps/**`), and `**/apps/**` covers both anchorings at once.

Rules:

- A pattern only affects a **missing** target. A target that exists is simply valid.
- A missing target matching a pattern is a **warning** (`optional link (pattern-matched)`)
  and does not fail the run; a missing target matching nothing stays an **error**.
- Config patterns and `--optional-link-patterns` are **merged** (union), never replaced. Entries
  are trimmed on both sides before the union, so declaring the same pattern twice (even with
  different surrounding whitespace) yields one matcher.
- Each pattern is matched against the target **resolved relative to the KB root**
  (`apps/x.ts`) and — only when the link **as written** is a genuine spelling of that same
  target, i.e. its leading `../` climb lands exactly on the KB root (`../../apps/x.ts` from
  `.pair/knowledge/`), or the resolved target leaves the KB tree — against the written form
  too. A match in either form makes the link optional, and overlapping patterns still produce
  a single warning. Every other link is matched on its **resolved form only**: one that stays
  inside the KB (`apps/x.md`, `./apps/x.md`), and one whose `../` climb lands back inside the
  KB (`../../apps/y.md` from `.pair/knowledge/a/b/`, resolving to
  `.pair/knowledge/apps/y.md`). So a rule like `apps/**` or `../../apps/**` cannot silence a
  broken link that merely **looks** like it — typically a file moved deeper, whose `../` depth
  is now wrong and whose target will never exist.
- **Prefer the resolved form; the written form is depth-bound.** `../../apps/**` matches only
  links whose `../` climb lands exactly on the KB root, so the same rule stops matching as soon
  as the same target is linked from a deeper file. Measured with two files linking to the SAME
  out-of-KB target: `[x](../../../apps/x.ts)` from `.pair/knowledge/a.md` and
  `[x](../../../../apps/x.ts)` from `.pair/knowledge/deep/b.md` are **both errors** under
  `../../apps/**`, and **both warnings** under `../apps/**` (their common resolved form) or
  `**/apps/**`. Nothing is silenced by the mismatch — the error stays — but the rule does not
  do what it looks like it does.
- Glob syntax: `**` (a whole segment: **zero or more** path segments, so `a/**/b` matches
  `a/b` and `**/apps/**` matches `apps/x.ts`), `*` (any characters except `/`, which is also
  what a `**` that is not a whole segment means), `?` (one character, never `/`), `[abc]` /
  `[a-z]` / `[!abc]`. Patterns are anchored — `apps/**` does not match `vendor/apps/x.ts`.
  Anchoring is on the KB root, so the decorations that would only restate it are stripped from
  the pattern and from the path alike: a leading `/` or `./`, a trailing `/`, repeated `/`.
  `/apps/**` (how an absolute internal link is written) and `./apps/**` are the same rule as
  `apps/**`, and `apps/` the same as `apps` — note that is the directory itself, NOT everything
  under it: write `apps/**` for that. A malformed pattern (unterminated class, out-of-order
  range like `[z-a]`) is reported and skipped, never fatal — including under `--strict`, where the matchers are discarded but the
  typo is still warned about. A **blank** entry is not a malformed pattern: on the flag it is
  dropped silently (`"apps/**,,"` is one pattern), in config it is dropped with its own
  "not a non-empty string" warning.
- **Everything outside that list is literal, not an error.** Brace expansion (`{apps,packages}/**`),
  extglob (`+(a|b)`) and leading-`!` negation (`!apps/**`) are compiled character by character, so
  they simply never match — and they are **not** reported as malformed patterns, so nothing warns.
  Write one pattern per alternative instead (`["apps/**", "packages/**"]`).
- A pattern containing a **comma** cannot be passed on `--optional-link-patterns` (the flag value is
  split on `,`, so `"[a,b]/*"` becomes two patterns, one of them malformed). Declare such a pattern
  in `link_validation.optional_link_patterns` instead.
- Three places this matcher is **more permissive than `minimatch`**, so do not assume parity:
  a trailing `/**` also matches the **directory itself** (`apps/**` matches `apps`, `**/b/**`
  matches `a/b`), `**` **traverses `..` segments** (`**` matches `../../apps/x.ts`), and the
  normalization above collapses spellings minimatch keeps distinct (`/apps/**` matches
  `apps/x.ts`). All three make a pattern broader than a minimatch habit suggests — and a
  too-broad pattern is not malformed, so nothing warns about it. Prefer the narrowest pattern that covers the links you
  mean to tolerate.
- A `link_validation` section of the wrong **shape** — not an object, `optional_link_patterns`
  not an array (`"apps/**"` instead of `["apps/**"]`), a camelCase key, or non-string entries —
  is reported as a warning and ignored, never fatal. Without that warning the run would look
  like "all these links are broken" rather than "the config key is misspelled". An empty section
  (`"link_validation": {}`) declares nothing and is silent.
- Config-shape and malformed-pattern diagnostics are printed under **`Configuration:`** in the
  report and counted in its `Warnings:` total, alongside the per-file ones. They are **also
  logged on stderr**, so each one deliberately appears twice: on stderr, where it is visible
  without scrolling back through a long report (and survives piping the report to a file), and
  in the report itself for the counted summary.
- `--strict` **overrides** optional patterns: in strict mode every missing target is an error.
  That is all it does today — the CLI makes **no network requests**, so external (`http`/`https`)
  links are never fetched, with or without `--strict`. A green `--strict` run in CI means "every
  internal target exists", never "external links are reachable".
- Links carrying a **non-http URI scheme** — `mailto:`, `tel:`, `ftp:`, `vscode:`, any
  `scheme:` of two characters or more — address something that is not a file: they are skipped
  entirely, never resolved as a path and never reported broken, with or without `--strict`
  (they are not fetched either, as nothing is). A Windows drive letter (`C:/x`) is a single
  character and therefore not a scheme: it stays an internal path.
- `--ignore-config` consults no config at all, so no registries resolve, **no files are
  collected and nothing is validated** — structure, links and metadata are all skipped, and
  optional patterns (config or CLI) have no effect, since there is nothing to match against.
  The run says so rather than passing silently: a `Configuration:` notice
  (`--ignore-config: … nothing validated …`) is printed on stderr and in the report, counted in
  the `Warnings:` total. Use it to skip validation entirely, not as a way to run with CLI-only
  patterns.
- Config patterns are read from the config of the **KB being validated**
  (`<--path>/pair.config.json`, falling back to `<--path>/config.json` when the former is
  absent), not from the invoking project — the same config `--path` already
  resolves registries from. Validating `--path ./my-kb` therefore ignores a `link_validation`
  section left in the repo-root config.

## scaffold-kb

Scaffold an external knowledge base repository — a pure KB repo (knowledge + skills)
plus the script that releases it. Publishing itself lives in the generated script, not
in the CLI, so any code host works.

### Usage

```bash
pair scaffold-kb [path] [options]
```

### Arguments

- `[path]` — Target directory for the KB repo (default: current working directory)

### Options

| Option          | Short | Description                                                        |
| --------------- | ----- | ------------------------------------------------------------------ |
| `--name <name>` |       | KB name (default: derived from the target directory name)          |
| `--host <host>` |       | Release automation host: `github` or `generic` (default: `github`) |
| `--force`       | `-f`  | Regenerate scaffold-owned files without confirmation               |

`--name` is embedded in generated YAML, bash, and Markdown: newlines, control characters
and `${{` (which GitHub Actions would evaluate as a live expression in the generated
workflow) are rejected, and the value is limited to 100 characters. Quote names that
contain spaces (`--name "Acme KB"`) — an unquoted value is rejected as an extra
positional argument rather than silently truncated.

`--host` is never inferred from the target repository's `origin` remote: pass
`--host generic` for GitLab, Bitbucket, or self-hosted, otherwise a GitHub Actions
workflow is generated. The command has no `--json` output — it reports a human-facing
summary only.

### Refused Targets

`scaffold-kb` fails, before writing anything, when the target exists and is not a
directory, or when it is a configured pair project (`.pair/adoption/` present).
`--force` does not bypass the second check: it is a wrong-target mistake, not an
overwrite decision.

### What Gets Created

| Path                            | Ownership                                           |
| ------------------------------- | --------------------------------------------------- |
| `.pair/knowledge/`, `.skills/`  | your content (seed files are never overwritten)     |
| `pair.config.json`              | scaffold-owned — knowledge + skills registries      |
| `README.md`, `.gitignore`       | scaffold-owned                                      |
| `scripts/release.sh`            | scaffold-owned — wraps `pair package` (mode `0755`) |
| `.github/workflows/release.yml` | scaffold-owned — `--host github` only               |

No `.pair/adoption/` is created: a KB is knowledge, not a configured project.

### Idempotency

Re-running is safe. Unchanged files are left alone, content under
`.pair/knowledge/`/`.skills/` is never touched, and a modified scaffold-owned file is
only regenerated after confirmation (or with `--force`). Without a terminal the file is
kept and reported as skipped.

### Examples

```bash
# Scaffold in the current directory
pair scaffold-kb

# Scaffold into a new directory with an explicit name
pair scaffold-kb ../acme-kb --name "Acme KB"

# Non-GitHub code host: release script only, no workflow
pair scaffold-kb ../acme-kb --host generic

# Release it (wraps pair package, then tags and publishes)
cd ../acme-kb && bash scripts/release.sh 1.0.0

# Install it into a project
pair install --source https://github.com/acme/acme-kb.git
```

See [Scaffold an External KB](/docs/customization/external-kb) for the full workflow.

## Global Options

Options available for all commands:

| Option                | Description                                                                                                                                                             |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--help`              | Display help for command                                                                                                                                                |
| `--version`           | Display CLI version                                                                                                                                                     |
| `--log-level <level>` | Set global logging level (trace, debug, info, warn, error)                                                                                                              |
| `--url <url\|path>`   | KB source for whichever command runs, used when that command names no `--source` (which outranks it); resolves exactly like `--source` — same identity, same cache slot |
| `--no-kb`             | Skip the knowledge base download — cannot be combined with `--url` (see below)                                                                                          |

<Callout type="warn">
  **`--no-kb` takes effect again, and now conflicts with `--url`.** The flag skips the KB
  pre-flight that `install` and `update` run before their work, so nothing is fetched and the
  command proceeds with whatever KB is already on disk. It was a **no-op** in every release up to
  and including 0.4.3: its only consumer was that pre-flight, and a guard in the `preAction` hook
  returned before it on every invocation. Two consequences of reviving it, both user-visible:
  `pair install --no-kb` no longer downloads a KB, and `--url <source>` together with `--no-kb` is
  now **rejected** (`Cannot use --url and --no-kb together`) where it was previously accepted and
  silently ignored — naming a source and refusing to fetch it is a contradiction. Only `install`
  and `update` run the pre-flight at all; every other command reads what is already on disk.
</Callout>
