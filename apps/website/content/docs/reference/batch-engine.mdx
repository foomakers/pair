`pair install` writes two directories that carry the batch engine:

| Installed to         | What it is                                        |
| -------------------- | ------------------------------------------------- |
| `.claude/workflows/` | the orchestration workflows                       |
| `.claude/agents/`    | the agent definitions those workflows dispatch to |

They install **unconditionally**, on every project, whatever tool you use.

Three workflows ship:

| Workflow               | What it drives                                                                                                                          |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `pair-implement-batch` | a batch of cards, each to a review-approved PR through four judgment stages — preparation, independent contract validation + seal, implementation, independent final verification — resuming a cycle from its first incomplete step |
| `pair-refine-batch`    | a batch of backlog cards to Ready — classify, refine, or read-only triage. By its dispatched prompts it writes to the PM tool only and touches no file in the repo — that is process, not permission: see the note below the agent table |
| `pair-loop`            | the unattended delivery loop — selects eligible cards via `/pair-next`, runs a dependency + mutex analysis, composes `pair-implement-batch` for the actual batch, enacts the automation policy (auto-advance) and evaluates the stop predicate. Realization for the `/pair-loop` skill in Claude Code (ADR-017 §4); elsewhere the skill takes a degraded one-card + continue-token path and this workflow never runs |

`pair-refine-batch` deliberately carries neither of the two knobs `pair-implement-batch` has.
It has **no parallelism cap** because each card costs one API round trip and holds no worktree,
no branch and no CPU — the cap exists on the implement engine because a card there occupies a
working tree. And it has **no `args.pipeline`** because it drives pair's own refinement
lifecycle by name (`/pair-capability-classify`, `/pair-process-refine-story`, …) rather than a
configurable one; generalizing it is a separate change, and the file says so at the top.

## Workflows are Claude-Code-specific

The engine is a workflow script driven by Claude Code's orchestration primitives — it spawns
subagents by type and runs their steps in parallel. No other tool executes it today.

**Under any other tool the files are inert.** They are never read, never executed, and cost
about **150 KB** on disk — mostly the implement engine itself, which carries its rationale
inline. The workflows' own dry-run test suites are development artifacts and are **excluded from
the install**, so they are not part of that figure. Nothing errors.

## What the agent layer can do

Under Claude Code they are not inert, and it is worth knowing exactly what arrives.

`.claude/agents/` declares five subagents, each with real tool access:

| Agent                     | Tools it declares                          | What that lets it do                                                        |
| ------------------------- | ------------------------------------------ | --------------------------------------------------------------------------- |
| `pair-implementer`        | `Read, Edit, Write, Bash, Grep, Glob, Skill` | write files, run commands, create worktrees, commit, push, open or update pull requests — always above a sealed acceptance contract (`/pair-workflow-implement-phase`, `/pair-workflow-green-fix`) |
| `pair-reviewer`           | `Read, Grep, Glob, Bash, Skill`            | the independent final verifier (`/pair-workflow-review-phase`): read the code, run commands (`git`, `gh`), run the custody script, publish the marker-keyed review comments; by its own instructions it does not edit, commit or merge |
| `pair-fix-test-author`    | `Read, Edit, Write, Bash, Grep, Glob, Skill` | the preparation owner (`/pair-workflow-red-spec`): inventory, grouping, tests and fixtures only; it cannot commit, push, post or edit production artifacts by instruction |
| `pair-red-contract-verifier` | `Read, Grep, Glob, Bash, Skill`          | the independent validator and sealer (`/pair-workflow-red-verify`): reproduce the contract, reject with every gap or run `red-snapshot.mjs seal`; read-only apart from the seal commit the script makes |
| `pair-contract-generator` | `Read, Write, Bash`                        | read a KB template and write the derived `*.contract.json` cache beside it    |

**One more agent type arrives with no definition of ours: `general-purpose`.** `pair-refine-batch`
spawns it at both of its stages. It is a host built-in of Claude Code, not a file `pair install`
writes, so it is not in the table above — and that is precisely why it is worth naming here: it
carries your tool configuration's **unrestricted** set, `Bash` included, which is wider than any
of the shipped definitions above. What keeps that engine to PM-tool writes is the read-only clause
in every prompt it dispatches, not a tool grant.

**Read the third column as process, not as permission.** `Bash` is unrestricted wherever it is
declared, so writing files, committing, pushing and `gh pr merge` are all technically inside the
authority you install. What keeps `pair-reviewer` and `pair-red-contract-verifier` read-only,
`pair-fix-test-author` test-only, and keeps merge out of every run is instruction — the engine's
dispatched prompts and each agent's own definition — not the tool grant.

So after an `install` or `update`, your project contains definitions that — when you invoke a
batch — can create worktrees, write files, commit, push branches and open pull requests under
your credentials. The `Tools it declares` column is checked against each agent's frontmatter by
the docs staleness gate, so it cannot understate what arrives; the column beside it is prose the
gate does not check.

They do nothing on their own. Nothing runs until you start a batch.

**No prompt this engine dispatches instructs a merge, on any path, and no configuration enables
one.** Every run stops at PR-review-approved and reports `ready-for-merge`, leaving the merge
decision to you — asserted by a dry-run test that inspects every dispatched prompt and every
returned status.

Every shipped name carries a `pair-` prefix — file names, agent names, and the workflows'
registry names (`meta.name`) alike — so neither an existing `.claude/agents/reviewer.md` nor
your own `implement-batch` workflow is overwritten or shadowed by one of ours.

They install anyway rather than being gated on the tool detected at install time, because that
detection is a snapshot: a user who adopts Claude Code later would need a full re-install rather
than an `update` to acquire files that were always harmless to have.

## The degraded path

Without a workflow runtime you drive the same lifecycle by hand, one card at a time. The
per-step skills are the same ones the engine composes, and they work standalone under any tool:

1. `/pair-process-implement` — implement the card, test-first, on its own branch
2. `/pair-capability-publish-pr` — open or update the PR, run the tier-resolved gate
3. `/pair-process-review` — review it independently, from the acceptance criteria and the diff
4. `/pair-process-implement` again — apply the findings, then re-review

What you lose is the orchestration, not the process: parallelism across cards, the isolated
worktree per card, the executable acceptance contract sealed before the implementation, the
durable cycle state that survives a context reset, and the convergence rule that decides when a
card is done.

## Merge is always the human gate

No configuration enables an autonomous merge. The engine stops at a review-approved PR and
reports it; the decision to merge is yours, on every path — convergence, escalation, or failure.

## Configuring it

The engine ships with pair's own values as defaults, so it runs in a pair-shaped project with no
configuration. A project whose skills, worktree root or base branch differ passes
`args.pipeline` to override them per key; anything left unmentioned keeps its default.

An unknown key, an empty override, a retired key or a `maxParallelism` below 1 is rejected loudly
rather than ignored — a discarded setting would run the batch on values you did not choose while
reporting success.

### Four judgment stages, one transition authority

From engine `4.0.0` (US-479, ADR-024 amendments b and the 2026-09-10 amendment) a story's cycle is four judgment dispatches,
each a skill invoked by name with typed arguments; the workflow file carries no phase policy of
its own and dispatches nothing mechanical:

| Stage | Skill | Who | What it owns |
| ----- | ----- | --- | ------------ |
| 1 preparation | `/pair-workflow-red-spec` | `pair-fix-test-author` | the authoritative inventory (AC or finding → producer → inputs, representations, consumers → equivalence classes and interactions → executable evidence), the grouping of a remediation round, the executable acceptance contract — red witnesses, positive controls that may pass, stable row ids — as tests and fixtures only, before any production edit; `initial`, `remediation`, `repair` and `revision` modes |
| 2 validation + seal | `/pair-workflow-red-verify` | `pair-red-contract-verifier` | reproduces every row and artifact at the base, re-derives the inventory from the producer, returns every gap in one typed rejection (one repair, then `failed-contract`), and on approval runs `red-snapshot.mjs seal` in the same execution |
| 3 implementation | `/pair-workflow-implement-phase` · `/pair-workflow-green-fix` | `pair-implementer` | GREEN above the seal, inside `fixScope`, never touching a sealed test byte; the initial stage publishes the story's one PR through the configured publish-pr skill, the remediation stage updates it; an approved test that still fails returns here once on the same seal |
| 4 final verification | `/pair-workflow-review-phase` | `pair-reviewer` | `red-snapshot.mjs verify-chain` first (a breach is terminal), then the fixers' evidence re-run, the witnesses and controls, every prior finding with an explicit transition, the delta and its consumers, cross-group interactions, the adopted risk-tier passes (general via `/pair-process-review`; security and boundary on `risk:yellow`; architecture and an adversarial second pass on `risk:red`); one verdict, the head reviewed, readiness only when the remote head equals it |

Batch-level, once per run and cache-by-hash: `/pair-workflow-contract-phase` (`pair-contract-generator`,
haiku) derives the review template's vocabulary contract. It is the **template** contract; the
**acceptance** contract a story is judged against is the one stage 1 prepares and stage 2 seals.

Every stage begins and ends with `cycle-state.mjs` — a script shipped inside each skill — which
reads the phase handoffs under `.pair/working/runs/<runId>/<story>/` in the main checkout (never
a worktree), publishes the stage's own handoff atomically (sequenced, predecessor-checked, a
stale writer is refused, a held lock is never broken) and derives the **first incomplete step**.
A stage dispatched when another step is due returns `{ status: "redirect", next }` without
spending judgment; the coordinator follows `next`, validates every typed result and enforces the
budgets — it never derives a transition of its own. Handoffs stay the storage authority: there is
no register, no projector.

### Resume, recovery, findings

- **Same inputs, unchanged head** ⇒ the cycle continues from its first incomplete step; a
  completed cycle is a cheap identity check (remote head equals the verified head) and no new
  judgment. A different invocation id for the same PR finds the existing run directory
  (`other-run`) instead of opening a second cycle; several candidate run directories are
  `incompatible` until the caller names one.
- **Moved head or changed relevant inputs** ⇒ the prior findings plus the delta and its
  affected boundaries are re-validated (`re-review`), never a fresh full pass; an unrelated card
  edit invalidates nothing.
- **An approved witness fails on production** ⇒ back to `green-fix` on the same seal, once; a
  second failure is `failed-fix`. **A genuine contract gap** ⇒ `red-spec` revises only the
  affected group (`r<n>-g<k>-rev<m>`), stable row ids kept, the changed rows re-validated and
  sealed as a successor snapshot; `verify-chain` treats the earlier seal as history. A revision
  or repair inherits the predecessor's `fixScope` and may only add paths — the sealer refuses a
  narrowed one (`fixScope-narrowed`, engine 3.0.8). **A
  custody breach** ⇒ `failed-custody`, the trusted snapshot preserved, nothing reset.
- **Findings** carry an id assigned once by the verifier that first saw them
  (`r<round>[-<reviewer>]-<n>`), a `kind` (`defect`, `regression`, `approved-test-failing`,
  `contract-gap`, `question`), a `transition` on every later review (`open`, `resolved`,
  `superseded`, `human`) and `blocking`, computed from the severity floor and re-checked by the
  coordinator; a severity change needs `severityEvidence`; a dropped, duplicated or invented id
  fails the verification closed. An `external` finding (the card, the PR body) is a location,
  never acceptance: it stays blocking until a human disposition or a read-back-verified
  correction, and the story escalates rather than converging around it.
- **Publication is idempotent**: the first review, the synthesis and an escalation are one
  comment each, keyed by a hidden marker and edited in place through `pr-comment.mjs upsert`,
  which reads the PR back before writing — a restart under another invocation never posts twice.
- **Statuses** a caller may see: `ready-for-merge` (only with a 40-hex `reviewedHead` and a
  `verdict`), `escalate`, `failed-preparation`, `failed-contract`, `failed-seal`,
  `failed-implement`, `failed-fix`, `failed-verify`, `failed-custody`, `failed-resume`,
  `incompatible`, and four added in `4.0.0`: `awaiting-scope-decision` (quality converged, one or
  more scope proposals still pending a human decision), `failed-publication` (the final summary
  could not be confirmed — retry publication only, quality evidence stays intact),
  `interrupted` and `abandoned` (an explicit developer abandonment). `pair-loop` halts on every
  one but the first.

### Scope proposals are never defects (`4.0.0`)

A finding that violates an accepted obligation (an AC, an adoption rule, a supported boundary) is
a defect and is fixed or absorbed into the story like before. Something demonstrably **absent**
from the baseline — a genuinely new requirement, not a violation — is instead recorded as a
`scopeChanges[]` entry (`sc-<n>`, stable across rounds): it never carries a severity, is never
`blocking`, never enters a remediation plan and is never counted as a defect. Once quality
converges (zero blocking findings) with one or more proposals still `pending`, the cycle halts at
`awaiting-scope-decision` — never `ready-for-merge` — and the reviewer posts the consolidated
packet (`<!-- pair:scope-decision #<story> PR#<n> -->`): each proposal's evidence that it is new
scope, the affected AC, and the three permitted choices.

The maintainer's decision is applied mechanically, never generated by an agent:
`cycle-state.mjs apply-scope-decisions --dir <run/story dir> --decision-ref <PR comment URL> --repo <owner/name> --pr <n>`
reads the ACTUAL comment through `gh`, verifies its author is a `User` in the adopted maintainer
set (never a caller-supplied string, never a bot), parses one fenced JSON object
(`{schemaVersion: 1, scopeBaselineHash, decisions: [{id, action, rationale?, targetIssueUrl?, approvedDelta?}]}`,
`action` one of `ignore | new-card | extend-current-card`), and rejects a stale baseline, a
duplicate id, an unknown action or an unauthenticated comment outright. `ignore` and `new-card`
disposition the proposal without touching source or severity; `extend-current-card` names the
exact new/changed AC, bumps `scopeEpoch` exactly once, and opens a targeted remediation round for
that delta through the ordinary pipeline — no parallel path. The whole exchange is idempotent: a
replayed `decisionRef` is a no-op, never a duplicate epoch.

### Metrics, host runtime and the final PR summary (`4.0.0`)

Two scripts new in `4.0.0`, shipped beside `cycle-state.mjs` in `review-phase`'s (and, where
imported, other phases') scripts folder:

- **`cycle-metrics.mjs`** — a pure, schema-1 reducer over the durable handoffs plus optional
  normalized runtime observations: cycle/review/defect/scope counts, token and time aggregation
  (known/partial coverage, never a fabricated zero), a cohort aggregator (completion rate, mean/
  median/p90 completed cycles), and the render/publish functions for the final summary.
- **`cycle-runtime.mjs`** — a narrow HOST process (never the Workflow sandbox, which still has no
  clock, filesystem or usage API): `entry` prepares a cache-hint capsule, `observe` tails ONLY the
  journal/usage sources it is given on a 5-second default interval and updates `metrics.json`/
  `metrics.md` at every observed boundary, stopping on a durable terminal result once reconciled
  or after a 30-second grace period leaves it partial; `finalize` combines the last verdict with
  the accumulated metrics and posts the ONE synthesis comment.

The final summary — one comment at `<!-- pair:synthesis #<story> PR#<n> -->`, upserted, never a
second one per run/step/scope-decision/metrics-correction — carries, in order: workflow identity/
versions/models/reviewed head; quality vs. delivery status; effective cycles and review executions
(retries, redirects, contract revisions kept separate); tokens and time with explicit coverage;
late defects by origin (`preexisting-missed`, `introduced-by-remediation`, `unknown`) and a
separate scope-proposal table; a compact schema-1 JSON tail (`sourceDigest`, `asOf`,
`metricsRevision`, `completeness`). Readiness is reported only after that candidate summary is
read back and confirmed — until then delivery is `failed-publication` even when quality already
converged. A confirmation-only republish is not a new semantic revision; human text written after
the comment's owned section survives every republish.

**Known limitation at `4.0.0`:** `usage.byRole`/`sharedOverhead` and `execution.redirects` /
`engineRecoveries` / `startedWithoutResult` / `administrativeDispatches` / `nestedDispatches` are
placeholders (empty/zero) until a live host wiring supplies them — never claimed as measured.
Every other quantity's known/partial coverage is exact.

A supplied `entryCapsules` map (per story id) lets a caller whose prior run already reached
`done` skip every dispatch for that story on the next invocation — including the batch-wide
template-contract call — once its identity (workflow major, schema version, story, PR, the 40-hex
reviewed head) is re-verified; it is a cache hint, never approval, and any mismatch falls through
to the ordinary dispatch pipeline unchanged.

`model` remains a legacy global override. For a measured trial use `models`, for example
`{ models: { green: "fable" } }`: that changes only GREEN, leaving the independent verifier,
the preparation author and the validator on their declared models. Roles: `implementation`,
`reviewer`, `red`, `redVerifier`, `green`. The retired roles (`planner`, `seal`, `preflight`,
`pr`) and the retired skill keys (`pipeline.skills.remediationPlan`, `redSeal`, `p3Verify`,
`cycleComments`, `prPhase`) are rejected with a message naming what absorbed them — never
mapped silently.

Every result carries `workflowVersion` and `metrics` (dispatches, retries, redirects; wall time
and token counters are not exposed to a workflow script — the sandbox has no clock and no usage
API — and are reported as `unknown`, never as zero: read both from the harness run summary), and every stage receives `$workflowVersion`, `$policy` and the effective-inputs digest so
each handoff records which coordinator, policy and inputs produced it. An incompatible workflow
major or schema found in a run directory is `incompatible`; prior approval is never reused or
overwritten silently.

`runId` (optional, one safe path segment) names the run directory `.pair/working/runs/<runId>/`;
absent, each card uses `story-<id>`. The six phase skills are pipeline configuration like the
others — `pipeline.skills.contractPhase`, `redSpec`, `redVerify`, `implementPhase`, `greenFix`,
`reviewPhase` — and `pipeline.reviewers` (default 1, the KB tier default) is the number of
independent final verifiers the tier requires.

### Carrying verified evidence

A card may pass `requiredFindings`: a compact verified observation with `observedHead`, finding
fields, oracle, probe and observed result. The final verifier re-proves it on the same reviewed
SHA (`kind: regression` if the defect is still present). A different SHA is `failed-verify`; old
evidence never silently becomes a new specification.

### History rewrites and rebases

If a review finding can only be fixed by rewriting existing Git history, the verifier types it
`humanDecisionKind: "history-rewrite"` and the engine escalates to a human before any RED, seal
or GREEN. Nothing in the engine can accept or waive such a finding; the human decides out of band
and re-runs.

A rebase is never repaired. An in-flight attempt whose base moved fails closed where it is
measured — the sealer refuses a `HEAD` that is not its base, the custody check refuses a snapshot
that is not an ancestor — and the trusted snapshot is preserved, never reset. There is no
card-level reset, no `supersedes` field and no SHA-scoped waiver to carry across runs; unknown
dirty state in a worktree is reported (`dirty`), never cleaned.
