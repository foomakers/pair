`pair install` writes two directories that carry the batch engine:

| Installed to         | What it is                                        |
| -------------------- | ------------------------------------------------- |
| `.claude/workflows/` | the orchestration workflows                       |
| `.claude/agents/`    | the agent definitions those workflows dispatch to |

They install **unconditionally**, on every project, whatever tool you use.

Three workflows ship:

| Workflow               | What it drives                                                                                                                          |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `pair-implement-batch` | a batch of cards, each to a review-approved PR — implement, open the PR, then an independent review ↔ fix loop until it converges         |
| `pair-refine-batch`    | a batch of backlog cards to Ready — classify, refine, or read-only triage. By its dispatched prompts it writes to the PM tool only and touches no file in the repo — that is process, not permission: see the note below the agent table |
| `pair-loop`            | the unattended delivery loop — selects eligible cards via `/pair-next`, runs a dependency + mutex analysis, composes `pair-implement-batch` for the actual batch, enacts the automation policy (auto-advance) and evaluates the stop predicate. Realization for the `/pair-loop` skill in Claude Code (ADR-017 §4); elsewhere the skill takes a degraded one-card + continue-token path and this workflow never runs |

`pair-refine-batch` deliberately carries neither of the two knobs `pair-implement-batch` has.
It has **no parallelism cap** because each card costs one API round trip and holds no worktree,
no branch and no CPU — the cap exists on the implement engine because a card there occupies a
working tree. And it has **no `args.pipeline`** because it drives pair's own refinement
lifecycle by name (`/pair-capability-classify`, `/pair-process-refine-story`, …) rather than a
configurable one; generalizing it is a separate change, and the file says so at the top.

## Workflows are Claude-Code-specific

The engine is a workflow script driven by Claude Code's orchestration primitives — it spawns
subagents by type and runs their steps in parallel. No other tool executes it today.

**Under any other tool the files are inert.** They are never read, never executed, and cost
about **150 KB** on disk — mostly the implement engine itself, which carries its rationale
inline. The workflows' own dry-run test suites are development artifacts and are **excluded from
the install**, so they are not part of that figure. Nothing errors.

## What the agent layer can do

Under Claude Code they are not inert, and it is worth knowing exactly what arrives.

`.claude/agents/` declares eight subagents, each with real tool access:

| Agent                     | Tools it declares                          | What that lets it do                                                        |
| ------------------------- | ------------------------------------------ | --------------------------------------------------------------------------- |
| `pair-implementer`        | `Read, Edit, Write, Bash, Grep, Glob, Skill` | write files, run commands, create worktrees, commit, push, open pull requests |
| `pair-reviewer`           | `Read, Grep, Glob, Bash, Skill`            | read the code and run commands (`git`, `gh`); by its own instructions it does not edit, commit or merge |
| `pair-remediation-planner` | `Read, Grep, Glob, Bash, Skill`            | group one review's actionable findings into a frozen remediation plan (`/pair-workflow-remediation-plan`); read-only, it cannot edit, commit, push, post or merge |
| `pair-fix-test-author`    | `Read, Edit, Write, Bash, Grep, Glob, Skill` | write and run only failing regression tests; it cannot commit, push, post or edit production artifacts by instruction |
| `pair-red-contract-verifier` | `Read, Grep, Glob, Bash, Skill`          | independently reproduce the RED contract before it is sealed; it is read-only and cannot edit, commit, push, post or merge |
| `pair-red-sealer`         | `Read, Bash, Skill`                        | run `red-snapshot.mjs seal` (`/pair-workflow-red-seal`) and return its answer; it cannot edit, push, post or merge — the script decides |
| `pair-fix-verifier`       | `Read, Grep, Glob, Bash, Skill`            | independently preflight a just-fixed delta; rerun evidence and tests without editing, posting or merging |
| `pair-contract-generator` | `Read, Write, Bash`                        | read a KB template and write the derived `*.contract.json` cache beside it    |

**One more agent type arrives with no definition of ours: `general-purpose`.** `pair-refine-batch`
spawns it at both of its stages. It is a host built-in of Claude Code, not a file `pair install`
writes, so it is not in the table above — and that is precisely why it is worth naming here: it
carries your tool configuration's **unrestricted** set, `Bash` included, which is wider than any
of the shipped definitions above. What keeps that engine to PM-tool writes is the read-only clause
in every prompt it dispatches, not a tool grant.

**Read the third column as process, not as permission.** `Bash` is unrestricted wherever it is
declared, so writing files, committing, pushing and `gh pr merge` are all technically inside the
authority you install. What keeps `pair-reviewer`, `pair-remediation-planner`, `pair-red-contract-verifier` and `pair-fix-verifier` read-only, `pair-fix-test-author` test-only, `pair-red-sealer` snapshot-only, and keeps merge out of every run is
instruction — the engine's dispatched prompts and each agent's own definition — not the tool
grant.

So after an `install` or `update`, your project contains definitions that — when you invoke a
batch — can create worktrees, write files, commit, push branches and open pull requests under
your credentials. The `Tools it declares` column is checked against each agent's frontmatter by
the docs staleness gate, so it cannot understate what arrives; the column beside it is prose the
gate does not check.

They do nothing on their own. Nothing runs until you start a batch.

**No prompt this engine dispatches instructs a merge, on any path, and no configuration enables
one.** Every run stops at PR-review-approved and reports `ready-for-merge`, leaving the merge
decision to you — asserted by a dry-run test that inspects every dispatched prompt and every
returned status.

Every shipped name carries a `pair-` prefix — file names, agent names, and the workflows'
registry names (`meta.name`) alike — so neither an existing `.claude/agents/reviewer.md` nor
your own `implement-batch` workflow is overwritten or shadowed by one of ours.

They install anyway rather than being gated on the tool detected at install time, because that
detection is a snapshot: a user who adopts Claude Code later would need a full re-install rather
than an `update` to acquire files that were always harmless to have.

## The degraded path

Without a workflow runtime you drive the same lifecycle by hand, one card at a time. The
per-step skills are the same ones the engine composes, and they work standalone under any tool:

1. `/pair-process-implement` — implement the card, test-first, on its own branch
2. `/pair-capability-publish-pr` — open or update the PR, run the tier-resolved gate
3. `/pair-process-review` — review it independently, from the acceptance criteria and the diff
4. `/pair-process-implement` again — apply the findings, then re-review

What you lose is the orchestration, not the process: parallelism across cards, the isolated
worktree per card, the audit log that survives a context reset, and the convergence rule that
decides when a card is done.

## Merge is always the human gate

No configuration enables an autonomous merge. The engine stops at a review-approved PR and
reports it; the decision to merge is yours, on every path — convergence, escalation, or failure.

## Configuring it

The engine ships with pair's own values as defaults, so it runs in a pair-shaped project with no
configuration. A project whose skills, worktree root or base branch differ passes
`args.pipeline` to override them per key; anything left unmentioned keeps its default.

An unknown key, an empty override, or a `maxParallelism` below 1 is rejected loudly rather than
ignored — a discarded setting would run the batch on values you did not choose while reporting
success.

### Every phase is a skill

From US-479 c4 the workflow file dispatches no free-form prompt at all. `/pair-workflow-contract-phase`
ensures the template-derived contract (phase 0); `/pair-workflow-implement-phase` builds the story in
its worktree and writes the checkpoint (A); `/pair-workflow-pr-phase` publishes exactly one PR through
the configured publish-pr skill (B). The engine passes each skill the run's values — `$run`, `$story`,
`$branch`, `$worktree`, `$base`, `$stacked`, the configured skill names, `$notes` — and validates the
typed result; the isolation rules, the stacked-story rules, the finite-state and evidence disciplines
and every shell command live in the skill.

### The review and the cycle's comments are skills

From US-479 c3 the independent review is `/pair-workflow-review-phase`: it reads the PR's `risk:*`
label and declares its review set before running — a general pass (`/pair-process-review` phases
1–4) on `risk:green`, plus security and boundary lenses on `risk:yellow`, plus architecture
(`/pair-capability-assess-coupling`) and an adversarial second pass on `risk:red` — then unions and
deduplicates the findings, keeping the highest evidenced severity. The engine passes the mode
(`first` posts the report with the hidden marker; `re-review` inspects only the fix delta, silent;
`fresh` is a full silent pass on a resumed cycle), the template vocabulary and, on a re-review, the
prior findings and head. `/pair-workflow-cycle-comments` owns the PR-comment policy in three modes
— `probe` (log present? marker on the PR?), `flush` (escalation, superseding any prior flush),
`synthesize` (one remediation table across every run, intermediates minimized, log deleted) — so a
PR shows at most one first review and one final remediation.

### Remediation phases are skills

From US-479 the review ↔ fix loop is a sequence of **phase skills** the engine dispatches by name with typed arguments; the workflow file carries no phase policy of its own. A round with actionable findings runs `/pair-workflow-remediation-plan` (D0: findings grouped by canonical owner, one mode — `behavioral` or `structural` — and exact allowed paths), then per group, in dependency order: `/pair-workflow-red-spec` (D1: finite domain map + test-only RED contract, hashed), `/pair-workflow-red-verify` (D2: an independent reproduction; one bounded repair on rejection, a second rejection is `failed-red-contract`), `/pair-workflow-red-seal` (D3: the `red-snapshot.mjs seal` script shipped inside the skill — one local commit carrying the `Pair-RED-Snapshot` trailer), `/pair-workflow-green-fix` (D4: the fix inside `fixScope`, GREEN committed above the seal, PR updated) and `/pair-workflow-p3-verify` (D5: `red-snapshot.mjs verify` — parent, tree, sealed blobs byte-identical, no unlisted test change, scope respected — then a read-only evidence re-run). A custody breach or a P3 defect is terminal for the attempt: `failed-preflight`, and the next run starts a fresh RED contract.

A remediation group is `behavioral`, `structural` or `test` — the last for a guard-strength finding (the defect is in a test artifact, production is already correct): its RED is proven against an injected regression, it declares no production paths, it has no GREEN, and P3 treats any production change as a breach. A RED author's typed refusal (`stale`, `split-required`) is routed by status and never retried with the same prompt.

Every phase writes one handoff JSON under `.pair/working/runs/<run>/<story>/` in the main checkout the coordinator runs from (never inside a worktree); the next phase reads that artifact, never a previous agent's prose. The Git work — hashing, sealing, ancestry and blob checks — is deterministic in `red-snapshot.mjs`, a script that ships inside the `red-seal` and `p3-verify` skills and tested against throwaway repositories; no agent re-derives it.

`model` remains a legacy global override. For a measured trial use `models`, for example
`{ models: { green: "fable" } }`: that changes only GREEN, leaving the independent reviewer,
RED and P3 on their declared models. Roles: `implementation`, `pr`, `reviewer`, `planner`, `red`,
`redVerifier`, `seal`, `green`, `preflight`.

Every result carries `workflowVersion`, and every phase skill receives it as `$workflowVersion` so
each handoff records which coordinator produced it.

`runId` (optional, one safe path segment) names the handoff directory `.pair/working/runs/<runId>/`;
absent, each card uses `story-<id>`. The six phase skills are pipeline configuration like the others —
`pipeline.skills.remediationPlan`, `redSpec`, `redVerify`, `redSeal`, `greenFix`, `p3Verify`, `reviewPhase`, `cycleComments`, `contractPhase`, `implementPhase`, `prPhase` —
so an adopter who names them differently overrides the key rather than the engine.

### Carrying verified P3 evidence

A card may pass `requiredFindings`: a compact P3 observation with `observedHead`, finding fields,
oracle, probe and observed result. The reviewer does not receive it, preserving its independent
sample. On the same reviewed SHA the engine gives it once to RED, which must rerun the oracle and
make the case red even if the reviewer missed it. A different SHA stops as
`failed-required-findings`; old evidence never silently becomes a new specification.

`model` remains a legacy global override. For a measured trial use `models`, for example
`{ models: { green: "fable" } }`: that changes only GREEN, leaving the independent reviewer,
RED and preflight on their declared models.

### History rewrites and rebases

If a review finding can only be fixed by rewriting existing Git history, the reviewer types it
`humanDecisionKind: "history-rewrite"` and the engine escalates to a human before it creates a RED
snapshot. Nothing in the engine can accept or waive such a finding; the human decides out of band
and re-runs.

A rebase is never repaired. An in-flight attempt whose base moved fails closed where it is
measured — the sealer refuses a `HEAD` that is not its base, the preflight refuses a snapshot that
is not an ancestor — and a resumed run starts a fresh review on the current head. Older snapshots
are historical evidence, never a later breach. There is no card-level reset, no `supersedes`
field and no SHA-scoped waiver to carry across runs.
