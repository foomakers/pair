Releases are dispatched via GitHub Actions and [Changesets](https://github.com/changesets/changesets). This guide covers how to create a release and what happens behind the scenes.

## Overview

Releases are **dispatched, never merge-triggered**. Two runs per release:

1. **Run 1, `version.yml`**: the maintainer runs `pnpm release <channel>`; the workflow validates, versions and tags.
2. **Run 2, `release.yml`**: builds from the tag, publishes and cleans up.

![Release channels: pre, rc, final and cleanup of earlier pre-releases](/diagrams/release-channels.svg)

**Build once, verify, publish.** Changesets manages versions, CI builds artifacts from the tag, GitHub Releases distributes them.

## Every PR carries a changeset

`.changeset/<story-id>.md` mirrors the PR description and states the bump. CI fails a PR without one unless it is labelled `no-changeset`. Below 1.0 a breaking change is a `minor` bump.

If the change breaks `.pair/adoption/` or `.pair/knowledge/` structure, add a migration page under [Migrations](/docs/migrations) before merging — see [Writing Migration Pages](/docs/contributing/writing-migration-pages).

## Creating a release

```bash
pnpm release <pre|rc|final> [--version X.Y.Z] [--dry-run]
```

The command prints the plan (version, tag, cleanup) and dispatches `version.yml`; CI re-validates with the same state module. Channels are forward-only (`pre` → `rc` → `final`, see the [channel diagram](#overview)) and skippable; the same channel needs new `main` commits; duplicates are refused.

| Channel | Registry | GitHub Release | Website |
|---------|----------|----------------|---------|
| `pre` / `rc` (`X.Y.Z-pre.N`) | GitHub Packages, tag-only (`main` untouched) | prerelease | not deployed |
| `final` | npmjs.org, version commit + CHANGELOG on `main` | latest | deployed |

After a successful publish, the previous same-channel pre/rc is deleted; on `final` (or a base change) every pre/rc of that base is deleted — release, assets, tag and package version.

To install a prerelease, use a token with `read:packages` and `npm config set @foomakers:registry https://npm.pkg.github.com`.

## Release checklist: skill marketplace manifest

The [marketplace channel](/docs/integrations/claude-code#install-channels) is served by two hand-maintained files: `.claude-plugin/marketplace.json` at the repository root, and `.claude-plugin/plugin.json` inside the plugin root it points to (`packages/knowledge-hub/dataset/plugin`). They are deliberately **not generated**. The plugin ships the bootstrap corpus only, so adding a skill to the distributed catalog no longer touches them:

- `plugin.json` `skills` lists one `./skills/<name>` entry per directory under the plugin root's `skills/`, and nothing stale.
- The marketplace entry's `source` still points at the plugin root — pointing it at `./` would ship the whole repository again, and with it pair's own `.pair/adoption/` inside every user's plugin cache.
- `claude plugin validate .` passes. The "no version specified" warning is expected: the manifest pins no version so `/plugin update` always fetches the current catalog. Never run this check with `--strict` — that flag turns the expected warning into a hard failure, and the missing version pin is a deliberate decision.
- Skills only, on all three hand-edited surfaces — `plugin.json` carries metadata plus `skills` and nothing else; the marketplace entry carries metadata plus `source`/`category`/`tags`/`strict` and **no `skills`** (an entry-level `skills` silently replaces the plugin's whole catalog); and `marketplace.json`'s own top level carries marketplace metadata plus `owner`/`plugins`, never `forceRemoveDeletedPlugins`, `allowCrossMarketplaceDependenciesOn` or `metadata.pluginRoot`.
- At the **plugin root**, no component directory named after a manifest component key (`agents/`, `commands/`, `hooks/`, `monitors/`, …) and no `.mcp.json`. `skills/` is the one exception: at that root it is the declared payload, so auto-discovery and the manifest coincide instead of competing. The repository root is not the payload any more.

The catalog guard in `packages/knowledge-hub/src/tools/claude-plugin-manifest.test.ts` (run by `pnpm test`) fails when the manifest drifts from the bootstrap corpus (`packages/knowledge-hub/dataset/plugin/skills/`), naming the exact entry to add or remove — so a forgotten update is caught before release, not after. The same guard asserts the skills-only rule as an **allowlist** per surface — so `settings`, `dependencies`, `monitors`, `commands` and any key a future schema revision adds fail closed too — plus a root-payload check whose path list is *derived* from the schema's component keys, so the manifest half and the payload half of the rule can never drift apart. Both checklist lines have an automatic backstop.

## Workflows

| Workflow | File | Trigger | Purpose |
|----------|------|---------|---------|
| Version | `version.yml` | Dispatch (`channel`, `version`) | Validate, version, tag, dispatch release |
| Release | `release.yml` | Dispatch (tag) | Build from tag, publish, cleanup |

## Release artifacts

### CLI

| Artifact | Description |
|----------|-------------|
| `pair-cli-manual-{version}.zip` | Self-contained CLI bundle (ncc, no node_modules) |
| `pair-cli-manual-{version}.zip.sha256` | SHA256 checksum |
| `pair-cli-{version}.tgz` | npm package for npmjs.org |
| `pair-cli-{version}.tgz.sha256` | TGZ checksum |

### Knowledge Base

| Artifact | Description |
|----------|-------------|
| `knowledge-base-{version}.zip` | KB dataset with manifest |
| `knowledge-base-{version}.zip.sha256` | SHA256 checksum |

The CLI auto-downloads the KB on first run from GitHub Releases and caches it at `~/.pair/kb/{version}/`.

## Manual dispatch

Workflows can be triggered manually:

```bash
gh workflow run version.yml --ref main -f channel=final
```

## Post-release validation

After a release is published, run the manual test suite to validate all artifacts:

```text
/pair-capability-execute-manual-tests
```

This executes the test cases in `qa/release-validation/` against the live release — website, CLI binaries, KB dataset, and registry packages. The report is written to `.tmp/manual-test-reports/`.

If no test suite exists yet, create one first:

```text
/pair-capability-design-manual-tests
```

See the [Release Testing tutorial](/docs/tutorials/release-testing) for a full walkthrough.

## Rollback

If a release needs to be reverted:

1. Delete the GitHub Release and tag from the GitHub UI.
2. Revert the final version commit on `main`.
3. Add a changeset with the fix and dispatch a new release.
