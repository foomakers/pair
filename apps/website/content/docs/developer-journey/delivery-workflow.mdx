The **delivery workflow** is the second of the [lifecycle](/docs/developer-journey) workflows, after [analysis and refinement](/docs/developer-journey/refinement-workflow). It is how pair takes one refined card to a review-approved pull request, and optionally to a merge, without relying on one long conversation. It is a set of [workflow skills](/docs/concepts/skills#workflow-skills) driven by a single state machine.

> Reference for the mechanics: [Delivery cycle](/docs/reference/delivery-cycle). Hands-on: [Automated development](/docs/tutorials/automated-development).

## Why it exists

A single agent that writes the code, judges it and merges it grades its own work. The workflow splits that job so each judgment is made by someone who did not make the thing being judged, and it keeps its state in files so an interruption costs nothing.

## One state machine per card

![The delivery cycle: both entries, the remediation loop, terminal states and the human decision points](/diagrams/cycle-overview.svg)

- **Stages**: `prepare`, `implement`, `verify`, the remediation stages `validate` and `green`, then `merge`. A fresh card runs `implement → verify → merge`.
- **Remediation rounds**: blocking review findings loop `prepare → validate → green → verify`. The failing test comes first, is sealed, and the fix lands above the seal.
- **One rule authority**: a single script decides what is due next. Every driver asks it, dispatches exactly that stage, and asks again.

## Independent roles

Four roles, never the same agent for adjacent judgments: the **implementer** (writes tests and code), the **fix-test author** (writes a finding's failing test), the **contract verifier** (validates and seals it) and the **reviewer** (verifies the exact PR head). The implementer never reviews; the verifier never repairs.

## Durable handoffs and custody

Every stage publishes a handoff file under the run directory. State is files, not memory: a cycle resumes from its first incomplete stage. A sealed test is custody-checked byte for byte at verification; a fixer cannot weaken what it must satisfy.

## Autonomy gates and escalation

Three gates decide how far a card goes without you: `until` (`ready`, `pr`, `merged`), `prepare` (who refines a Draft card) and `merge` (whether a review-approved card merges). A `when` condition that fires **escalates** the card to a human. Defaults keep a human in the loop. Every key: [Adoption settings](/docs/reference/adoption-settings#techautomationmd); walkthrough: [Autonomy](/docs/tutorials/automated-development#autonomy-until-gates-escalation).

## Per mode

Same three modes as the [refinement workflow](/docs/developer-journey/refinement-workflow#per-mode); see [Lifecycle modes](/docs/developer-journey/lifecycle-modes).

### Assisted

Not the workflow: you run `/pair-process-implement` and `/pair-process-review` yourself, task by task.

### Semi-automatic

You trigger it per card (`/pair-workflow-cycle`, `pair-cli run --card`) or per batch (`/pair-implement-batch`). It runs implement, independent verify and remediation, then stops at a checkpoint for you: the review-approved PR, or an escalation.

### Automatic

It is the engine: `/pair-loop` or `pair-cli run --root --parallel --watch` re-select cards and run the cycle under the [autonomy gates](/docs/tutorials/automated-development#autonomy-until-gates-escalation). A card merges only when the `merge` gate allows it.

## Realizations

One cycle, several drivers: the in-session coordinator `/pair-workflow-cycle` in Claude Code, Codex or pi (with subagents), the console driver `pair-cli run` on any installed engine, and the Claude parallel batch. They differ in who dispatches the stages, never in the rules. Choosing: [Delivery cycle, realizations](/docs/reference/delivery-cycle#3-three-realizations-and-which-to-use).
