This is pair's first structured migration — the recipe below is dogfooded on the pair repo itself before being published for consumer projects.

Structural background: [Canonical states (#202)](https://github.com/foomakers/pair/issues/202) · [Domain model (#203)](https://github.com/foomakers/pair/issues/203) · [Context-safe implementation, `.pair/working/` (#206)](https://github.com/foomakers/pair/issues/206) · [Versioning & migration epic (#214)](https://github.com/foomakers/pair/issues/214)

## Changed

### Canonical backlog states

Skills used to read a literal board-state name (`Refined`, `Todo`) baked into their instructions. From this release, pair resolves backlog state through five canonical macrostates:

```text
Draft → Ready → In Progress → Review → Done
```

Your board can keep any naming. `.pair/adoption/tech/way-of-working.md` gains an optional `state-mapping` section (board state → macrostate, n-to-m). Omit it and pair assumes your board already uses the canonical names.

### Domain context map

`.pair/adoption/product/` gains `context-map.md` — a single living file holding your shared glossary, entities, and domain rules (and, while your project is small, the *entire* domain context). It's maintained inline during brainstorming/refinement sessions, not regenerated by a dedicated skill. When a subdomain later outgrows the shared file, its context moves out to a sibling `subdomain/<slug>.context.md`, indexed by the map.

### `.pair/working/`

A new top-level `.pair/working/` directory hosts **operational state** — checkpoints and reports — that `pair install`/`pair update` never touch and that KB registries never index:

```text
.pair/working/
├── checkpoints/   # resumable handoff state for long-running skill sessions
└── reports/       # qa/, performance/, cost/, security/ + consolidated panel
```

## Prompt

Copy-paste this into any AI coding agent (Claude Code, Cursor, Copilot, Codex, or similar) with write access to your project. It only touches files under `.pair/adoption/` and `.pair/working/` — never `.pair/knowledge/`, skill files, or application code. It's safe to re-run: each step checks whether it already applied before acting.

```text
You are migrating this project's `.pair/` structure to pair's canonical-states /
context-map / working-area release (v0.4 → v0.5). Work only inside
`.pair/adoption/` and `.pair/working/`. Do not edit `.pair/knowledge/`, any skill
file, or application code. Perform each step only if not already done, and
report what you skipped.

1. Ensure `.pair/working/checkpoints/` and `.pair/working/reports/` exist
   (create empty directories, adding a `.gitkeep` if your tooling needs one to
   track them).

2. If `.pair/adoption/product/context-map.md` does not exist, create it with:
   - a "Glossary" section seeded from the terms already used across
     `.pair/adoption/product/subdomain/*.md`
   - an "Entities & Rules" section, empty if nothing to seed yet
   - a note that this file is maintained inline during brainstorming/refinement
     sessions, not regenerated by a dedicated skill
   If it already exists, leave it untouched.

3. Open `.pair/adoption/tech/way-of-working.md`. Determine whether your PM
   board's state names already match the canonical set (Draft, Ready,
   In Progress, Review, Done):
   - If they match (or you have no board yet), do nothing — canonical names
     are the default and no `state-mapping` section is needed.
   - If they differ, add a `## state-mapping` section listing each of your
     board's state names next to the canonical macrostate it maps to.
     Multiple board states may map to the same macrostate; states outside the
     mapping are allowed and left unmapped.
   Skip this step entirely if a `## state-mapping` section already exists.

4. Summarize what you created or changed versus what was already in place, and
   confirm with `git status` (or equivalent) that only paths under
   `.pair/adoption/` and `.pair/working/` were touched.
```

## Verify

- [ ] `.pair/working/checkpoints/` and `.pair/working/reports/` exist
- [ ] `.pair/adoption/product/context-map.md` exists and has a Glossary section
- [ ] `.pair/adoption/tech/way-of-working.md` either has a `state-mapping` section matching your board, or your board already uses canonical names (Draft/Ready/In Progress/Review/Done)
- [ ] `git status` (or equivalent) shows changes only under `.pair/adoption/` and `.pair/working/`
- [ ] Re-running the prompt makes no further changes — a second run reports every step as skipped
