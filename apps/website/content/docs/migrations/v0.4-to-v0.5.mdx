This is pair's first structured migration — the recipe below is dogfooded on the pair repo itself before being published for consumer projects.

Structural background: [Canonical states (#202)](https://github.com/foomakers/pair/issues/202) · [Domain model (#203)](https://github.com/foomakers/pair/issues/203) · [Context-safe implementation, `.pair/working/` (#206)](https://github.com/foomakers/pair/issues/206) · [Versioning & migration epic (#214)](https://github.com/foomakers/pair/issues/214)

## Changed

### Canonical backlog states

Skills used to read a literal board-state name (`Refined`, `Todo`) baked into their instructions. From this release, pair resolves backlog state through five canonical macrostates:

```text
Draft → Ready → In Progress → Review → Done
```

Your board can keep any naming. `.pair/adoption/tech/way-of-working.md` gains an optional `## State Mapping` section — a `Board State | Macrostate` table, n-to-m (multiple board states may map to one macrostate; first-listed wins on write). Omit it and pair assumes your board already uses the canonical names.

### Domain context map

`.pair/adoption/product/context-map.md` gains a dispatcher + subdomain index + core domain model: a **Subdomain Index** (which subdomains keep context inline vs. split out, mirroring the classification and Volatility already recorded in your subdomain catalog), a **Glossary**, an **Entities** table, and a **Common Rules and Invariants** section. It's maintained inline during brainstorm/refine sessions, not regenerated by a dedicated skill. When a subdomain's inline context later outgrows the shared file, its Glossary/Entities rows move — lazily, on human approval — to a sibling `subdomain/<slug>.context.md`, indexed by the map's Subdomain Index.

### `.pair/working/`

A new `.pair/working/` area hosts **operational state** — checkpoints and reports — that's hard-excluded from every KB registry (D14) and never scaffolded by `pair install`/`pair update`:

```text
.pair/working/
├── checkpoints/           # resumable state for multi-task flows (e.g. an interrupted /implement run)
└── reports/
    └── <category>/        # generated reports, grouped by category (e.g. quality, monitoring)
```

Neither subdirectory is created upfront — a skill creates it on demand the first time it writes a checkpoint or report, so most projects have nothing to migrate here. The default path can be overridden with a top-level `working_path` field in `pair.config.json`; `pair validate-config` rejects any registry that overlaps it.

## Prompt

Copy-paste this into any AI coding agent (Claude Code, Cursor, Copilot, Codex, or similar) with write access to your project. It only touches files under `.pair/adoption/` (and, if you opt into a custom working-area path, `pair.config.json`) — never `.pair/knowledge/`, skill files, or application code. It's safe to re-run: each step checks whether it already applied before acting.

```text
You are migrating this project's `.pair/` structure to pair's canonical-states /
context-map / working-area release (v0.4 → v0.5). Work only inside
`.pair/adoption/` and `pair.config.json`. Do not edit `.pair/knowledge/`, any
skill file, or application code. Perform each step only if not already done,
and report what you skipped.

1. `.pair/working/` (checkpoints, reports) is now hard-excluded from every KB
   registry and is never scaffolded — a skill creates it on demand, so there
   is nothing to create here. Only act if you want a non-default location:
   add a top-level `working_path` field to `pair.config.json` (sibling of
   `asset_registries`, not nested inside it) and confirm no registry's
   `source`/`target` overlaps it. Skip this step if you're keeping the
   default `.pair/working` path.

2. If `.pair/adoption/product/context-map.md` does not exist, create it with:
   - a "Subdomain Index" table (Subdomain, Classification, Own Context,
     Volatility — Classification and Volatility mirrored from
     `.pair/adoption/product/subdomain/*.md`, never invented here; Own
     Context "No" for every subdomain until a later split)
   - a "Glossary" table seeded from terms already used across
     `.pair/adoption/product/subdomain/*.md` (leave the table header-only if
     that catalog doesn't define discrete terms yet)
   - an "Entities" table, empty if nothing to seed yet
   - a "Common Rules and Invariants" section, empty if nothing to seed yet
   - a note that this file is maintained inline during brainstorm/refine
     sessions, not regenerated by a dedicated skill
   If it already exists, leave it untouched.

3. Open `.pair/adoption/tech/way-of-working.md`. Determine whether your PM
   board's state names already match the canonical set (Draft, Ready,
   In Progress, Review, Done):
   - If they match (or you have no board yet), do nothing — canonical names
     are the default and no `## State Mapping` section is needed.
   - If they differ, add a `## State Mapping` section with a
     `Board State | Macrostate` table listing each of your board's state
     names next to the canonical macrostate it maps to. Multiple board
     states may map to the same macrostate (first-listed wins on write);
     states outside the mapping are allowed and left unmapped.
   Skip this step entirely if a `## State Mapping` section already exists.

4. Summarize what you created or changed versus what was already in place, and
   confirm with `git status` (or equivalent) that only paths under
   `.pair/adoption/` (and, only if step 1 applied, `pair.config.json`) were
   touched.
```

## Verify

- [ ] No registry in `pair.config.json` overlaps `.pair/working/` (or your `working_path` override) — `pair validate-config` passes
- [ ] `.pair/adoption/product/context-map.md` exists and has a Subdomain Index and a Glossary section
- [ ] `.pair/adoption/tech/way-of-working.md` either has a `## State Mapping` section matching your board, or your board already uses canonical names (Draft/Ready/In Progress/Review/Done)
- [ ] `git status` (or equivalent) shows changes only under `.pair/adoption/` (and, if you set an override, `pair.config.json`)
- [ ] Re-running the prompt makes no further changes — a second run reports every step as skipped

If you're several versions behind, run the earlier pages in the [Migrations index](/docs/migrations) first, then this one.
