---
title: Package-Local Adoption
description: Opt-in override that co-locates adoption rules in <pkg>/.pair/, makes central adoption a router, and scopes skill context to the packages a diff or story touches.
---

import { Callout } from 'fumadocs-ui/components/callout'

On a large monorepo one central adoption file grows noisy and every skill loads all of it. The **package-local adoption override** keeps rules next to their code and lets skills load only the packages they touch.

<Callout type="info">
  Opt-in. Without the override every rule loads from `.pair/adoption/`, exactly as before. Nothing is created until a human approves activation.
</Callout>

## Layout

```text
.pair/adoption/tech/architecture.md   # global rules + router section
apps/web/.pair/architecture.md        # rules for apps/web only
apps/web/.pair/testing.md
packages/ui/.pair/code-design.md
```

Local files follow `<pkg>/.pair/<area>.md`, where `<area>` is the central adoption area name. They hold only package-specific rules; global rules stay central.

## Router Format

The central file gains one section listing packages that have local context:

```markdown
## Package-Local Adoption

| Package     | Local context        | Areas                 |
| ----------- | -------------------- | --------------------- |
| apps/web    | `apps/web/.pair/`    | architecture, testing |
| packages/ui | `packages/ui/.pair/` | code-design           |
```

## Precedence

- **Local wins for its package** when a central and a local rule cover the same subject.
- Global rules always load; only package-locals are scoped.
- A rule that exists both centrally and locally is reported as a conflict by `review` and `assess-*`, never resolved silently.

**With the CLI:** create `<pkg>/.pair/<area>.md` and the router by hand. **With `/pair-assistant` (optional, Claude Code):** ask it to "add package-local rules for apps/web"; it shows the diff and routes the write ([package-local adoption](/docs/reference/pair-assistant#capability-menu), settings: [Adoption settings](/docs/reference/adoption-settings#package-local-adoption-and-templates)).

## Activation Proposal

Skills never activate the override. When `review`, `assess-*` or `refine-story` detect complexity, they **propose** it, a scaffold plan (which packages, which rules move, the router that would be added), and wait for approval.

| Signal | Default threshold |
| ------ | ----------------- |
| Packages touched with recurring package-specific rules in the central file | ≥ 3 |
| Central adoption file size | > 400 lines |

Thresholds live in the KB guideline, not in the skills.

## Scoped Loading

| Skill | Scope | Loads |
| ----- | ----- | ----- |
| [`review`](/docs/reference/skills-catalog) | PR diff (`git diff --name-only`) | globals + `<pkg>/.pair/` of touched packages |
| `assess-*` | diff | same |
| `refine-story` | packages referenced by the story | globals + `<pkg>/.pair/` of referenced packages |

Edge cases: a touched package without local `.pair` → globals only, no warning; a story referencing no package → central only; a router row whose directory is missing → reported as a dangling entry, globals still load.

## Registry Exclusion

Local `.pair` dirs are project content. `pair-cli install` / `pair-cli update` never touch them, and `pair-cli validate-config` rejects any registry `target` at or inside a `<pkg>/.pair` directory: the same protection as the [working area](/docs/reference/configuration#working-area-override).
