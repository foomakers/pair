You've adopted a Knowledge Base and it works. Now you want to adjust it — different testing framework, stricter quality gates, team-specific conventions. This guide shows how to customize without losing the ability to pull upstream updates.

## When to Customize

Customize when the default KB doesn't match your team's context:

- Your tech stack differs from the KB defaults (e.g., Jest instead of Vitest)
- Your team follows a different methodology (e.g., Scrum with 2-week sprints)
- You need stricter or different quality gates
- Your architecture pattern isn't covered by the KB defaults

If you just need to use the KB as-is, see [Adopt a Knowledge Base](/docs/customization/adopt).

## How the Layered Architecture Works

The `.pair/` directory has two layers:

| Layer | Directory | Updated by | Your changes |
| --- | --- | --- | --- |
| Knowledge | `.pair/knowledge/` | `pair-cli update` | Overwritten — don't edit |
| Adoption | `.pair/adoption/` | You | Preserved — never overwritten |

**Adoption always wins.** When both layers have an opinion on the same topic, the AI reads adoption files first. This means you can override any guideline by recording a decision in the adoption layer.

## Quick Recipe: Override a Guideline

Need to change a single KB default? Three steps:

### Step 1: Identify what to change

Browse the knowledge layer to find the guideline:

```bash
# List all guideline categories
ls .pair/knowledge/guidelines/

# Example: see testing guidelines
ls .pair/knowledge/guidelines/quality-assurance/
```

### Step 2: Record your decision

Create or update the corresponding adoption file. For example, to change the testing framework, edit `.pair/adoption/tech/tech-stack.md`:

```markdown
## Testing

- jest is adopted as the testing framework (jest v29.x).
```

Adoption files always override knowledge files — no need to touch `.pair/knowledge/`.

### Step 3: Verify

```bash
pair-cli kb-validate
pair-cli update-link --dry-run
```

**With the CLI:** `pair-cli kb-validate` then `pair-cli update-link --dry-run`.

**With `/pair-assistant` (optional, Claude Code):** ask for "the KB checked for structural soundness" ([how to ask](/docs/reference/pair-assistant#how-to-ask)).

### Which file to edit

| You want to change...                 | Edit this adoption file                 |
| ------------------------------------- | --------------------------------------- |
| Testing framework, language, library  | `.pair/adoption/tech/tech-stack.md`      |
| Architecture pattern                   | `.pair/adoption/tech/architecture.md`    |
| Methodology, quality gates             | `.pair/adoption/tech/way-of-working.md`  |
| Classification tiers (tag projection, criticality, overrides) | `.pair/adoption/tech/risk-matrix.md` |
| Add a new guideline                    | Create a new file in `.pair/adoption/`   |
| Record a significant decision          | Create an ADR in `.pair/adoption/tech/adr/` |

The rest of this guide covers each of these in depth.

## Customize Guidelines

### Override the Tech Stack

Edit `.pair/adoption/tech/tech-stack.md` to declare your team's choices:

```markdown
## Testing

- jest is adopted as the testing framework (jest v29.x).
- @testing-library/react is adopted for component testing.
```

The AI will now use Jest in all generated code, ignoring the KB's default recommendation.

### Change the Architecture Pattern

Edit `.pair/adoption/tech/architecture.md`:

```markdown
- Microservices architecture is adopted for backend services.
- Each service owns its database (database-per-service pattern).
```

### Set Your Methodology

Edit `.pair/adoption/tech/way-of-working.md`:

```markdown
- Scrum is adopted with 2-week sprints.
- GitHub Projects is adopted for project management.
- pnpm quality-gate is the adopted quality gate command.
```

## Adjust Quality Gates

Quality gates run before every commit. Customize them in `.pair/adoption/tech/way-of-working.md`:

```markdown
## Quality Gates

- `npm run quality` is the adopted project-level quality gate command.
- Quality gate includes: type checking, testing, linting, formatting.

### Custom Gate Registry

| Order | Gate | Command | Required |
| --- | --- | --- | --- |
| 1 | Quality Gate | `npm run quality` | Yes |
| 2 | Security Scan | `npm audit` | Yes |
```

## The Review Gate — Off by Default

pair reviews every pull request and publishes a verdict. Whether that verdict can **block a merge** is a separate switch, and it ships **off**.

**Off (the default).** The review runs, posts its findings, and sets the PR's state label (`pr-state:to-be-reviewed` / `ready-to-merge` / `not-approved`). Nothing it says stops you merging. The verdict is information.

**On.** Two status checks become required — `pair-review` (the verdict itself) and `pair-explicit-approval` (the 🔴 rule) — so a merge waits for the review, and a red-tier PR additionally waits for a human approval from **someone other than the author**.

Turn it on in `.pair/adoption/tech/way-of-working.md`:

```markdown
- **Review enforcement**: `enabled`
```

Then apply branch protection for the two checks — writing it needs admin rights, so it is a deliberate human step, not something a skill does behind you. Until that is applied the switch is declared but not in force, and pair says so rather than claiming a merge is blocked when it is not.

<Callout type="warn">
  **Before you enable it on a one-person repository.** The 🔴 tier requires an approval from a
  non-author human, and hosts reject self-approval — so on a single-maintainer repo a red PR cannot
  reach `ready-to-merge` at all. It is not a bug to work around (never self-approve to unblock):
  either a second account reviews, or `pair-explicit-approval` is deliberately not a required check
  there. This is why the switch is off by default — a review that blocks on a fresh install produces
  a repository nobody can merge into.
</Callout>

### Changing what each tier requires

Reviewer count, SLA, checklist depth and whether 🔴 needs explicit approval are **KB defaults**. To change them, add only the keys you are changing to `way-of-working.md`:

```yaml
# tier.red.reviewers: 2
# tier.red.sla_days: 3
```

The defaults are not copied into your adoption file, deliberately: a copy that matches is a second version of the same truth with nothing keeping the two in step, and because adoption wins over the KB default, a stale copy would quietly override an improved one. **Once you do override, write the effective table into that file** — when the values differ from the defaults, the ones in force belong where they are decided.

## Enable Classification Tiers

Classification (the `risk:*` tier that scales gates and review) is configured in `.pair/adoption/tech/risk-matrix.md`. The file is optional: absent, KB defaults apply and no tags are emitted. It has three independent sections; add only the ones you need. What the tiers mean is in the [Quality Model](/docs/reference/quality-model) and [Tag-Driven Quality Gates](/docs/concepts/tag-driven-gates); how the process uses them is in the [Process Lifecycle](/docs/developer-journey#the-risk-driven-flow).

**Tag projection** — which tag families are written onto cards and PRs. Without it nothing is tagged, so gates, review effort and automation eligibility cannot read a tier.

```markdown
## Tag Projection

Active: risk
```

Add `cost` to the list to also emit `cost:*`.

**Criticality Table** — how critical each deployable is, as the input to the Service/domain criticality dimension. Rows are keyed by the app, package or path scope that owns the touched files; a diff touching several takes the highest. A deployable not listed contributes the conservative High, so list every one you own. `/pair-process-bootstrap` can propose the rows from your domain model.

```markdown
## Criticality Table

| Service/Domain | Criticality |
| --- | --- |
| apps/api | High |
| apps/website | Low |
```

**Overrides** — per-tier reviewer count and SLA, threshold tweaks, and dimension-resolution rules. Write only the keys you change; the defaults are not copied into your file (see [Changing what each tier requires](#changing-what-each-tier-requires) above).

```markdown
## Overrides

- tier.red.reviewers: 2
- tier.red.sla_days: 3
```

Tier-aware pre-merge gating is a separate switch (`Pre-merge tiering: enabled` in `way-of-working.md`), described in [Tag-Driven Quality Gates](/docs/concepts/tag-driven-gates#setting-it-up-opt-in).

<Callout type="info">
  Migrating an existing project's adoption files to a new KB version: see [Migrations](/docs/migrations).
</Callout>

*Source: `tech/risk-matrix.md` sections as documented in `quality-model.md` §5–§6; D21 (adoption holds only the delta over KB defaults).*

## Record Significant Decisions

For decisions that need rationale and context — "why did we choose this?" — record an Architecture Decision Record:

```bash
# Using pair skills (recommended)
/pair-capability-record-decision
```

Or create a file manually in `.pair/adoption/tech/adr/` following the [ADR template](https://adr.github.io/).

ADRs help future team members (and AI assistants) understand not just what you decided, but why.

## Stay Updated

Pull upstream KB changes without losing your customizations:

```bash
pair-cli update
```

**With the CLI:** `pair-cli update`.

**With `/pair-assistant` (optional, Claude Code):** ask for "the KB and skills refreshed" ([how to ask](/docs/reference/pair-assistant#how-to-ask)).

What happens during update:

1. `.pair/knowledge/` is replaced with the latest upstream content
2. `.pair/adoption/` is untouched — all your decisions survive
3. New guidelines appear automatically; removed guidelines disappear
4. Your adoption overrides continue to take precedence

See [CLI Commands](/docs/reference/cli/commands) for the full `update` reference.

### Handling Conflicts

Occasionally an upstream update changes something your adoption files reference. When this happens:

1. The AI assistant will notice the inconsistency during the next session
2. Review the updated guidelines in `.pair/knowledge/`
3. Update your adoption files if needed to stay aligned

## Add Project-Specific Content

Create files in `.pair/adoption/` for guidelines that don't exist in the upstream KB:

```markdown
<!-- .pair/adoption/tech/api-conventions.md -->

# API Conventions

- All REST endpoints use kebab-case paths
- Response format follows JSON:API specification
- Pagination uses cursor-based approach
```

The AI assistant reads all files in `.pair/adoption/` — custom files are treated the same as overrides.

## Verify Your Customizations

After customizing, verify everything is consistent:

```bash

pair-cli kb-validate

# Check internal links
pair-cli update-link --dry-run
```

**With the CLI:** `pair-cli kb-validate` then `pair-cli update-link --dry-run`.
