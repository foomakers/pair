title: Project Management Tools
description: How pair integrates with project management tools to manage stories, tasks, and initiatives automatically.
---

pair manages work items for you. When you run process skills like `/pair-process-implement` or `/pair-process-plan-stories`, pair reads your `way-of-working.md` adoption file to determine which PM tool to use, then creates and updates issues, stories, and tasks automatically.

## The problem this section solves

pair was first exercised against a single tool: GitHub Projects. On GitHub, the place your backlog lives and the place your code lives are the same product — one tool holds the issue *and* the branch, the pull request, the review. So the whole skill corpus read one adoption field, `pm-tool`, for two genuinely different jobs: **backlog operations** (create an item, read its labels, transition its state) and **code operations** (cut a branch, open a PR, submit a review, merge). Nothing forced the two apart, so nothing kept them apart.

The conflation stayed invisible until a project's backlog lived somewhere that hosts no repositories. Linear and Jira are the obvious cases; pair's own offline `filesystem` tracker is a third, since it only moves Markdown files between status directories and has no branches or pull requests at all. On those tools the single field breaks: asking the "PM tool" to open a pull request is asking a backlog for something it has no concept of, and the failure is silent — the operation routes to a tool that quietly does nothing rather than to one that errors (per [ADR-018](https://github.com/foomakers/pair/blob/main/.pair/adoption/tech/adr/adr-018-code-host-optional-wow-override.md)).

Two constraints shaped the fix. An existing single-tool project had to keep working with **zero** new configuration — nobody on GitHub should have to declare anything to keep the behaviour they already had. And pair could not lean on any PM tool's own VCS integration (Linear's GitHub app, for instance), because depending on a proprietary integration would make every new PM tool a bespoke porting job and lock out self-hosted setups.

What came out of it is the model the rest of this section describes: **one optional field, `code-host`**. Leave it out and the code host *is* the PM tool — the zero-configuration path for a tracker that hosts repositories. Declare it and pair routes item/state work to the PM tool and branch/PR/review work to the code host, linking the two by plain text (`Refs: <issue-id>` in the PR body, the PR URL commented back on the item) rather than by an integration. PR state is never mirrored onto the board: state lives in exactly one place, so there is nothing to reconcile when the two disagree. [Code host vs PM tool](/docs/concepts/code-host) is the page that states the routing rule itself.

This is why the table below has a **"Hosts your code?"** column, and why two of the four tools carry a `code-host` note. It isn't a feature matrix — it is the one question that decides whether your project is a one-tool setup or a two-tool one.

## How It Works

1. **You choose a PM tool** during project bootstrap (or change it later in `way-of-working.md`)
2. **pair reads the config** every time a process skill runs
3. **pair creates and updates work items** — initiatives, epics, stories, tasks — in the configured tool
4. **Status flows automatically** — completing a task updates the story, completing all stories updates the epic, and so on

You focus on the work. pair keeps the board in sync.

## Supported Options

| Tool | Best For | External Service | Hosts your code? |
|------|----------|-----------------|------------------|
| [Filesystem](/docs/pm-tools/filesystem) | Solo devs, offline work, simple projects | No | No — declare a [`code-host`](/docs/concepts/code-host) |
| [GitHub Projects](/docs/pm-tools/github-projects) | Teams already on GitHub, open source projects | Yes (free) | Yes |
| [Linear](/docs/pm-tools/linear) | Teams wanting a polished PM experience | Yes (paid) | No — declare a [`code-host`](/docs/concepts/code-host) |
| [Azure DevOps](/docs/pm-tools/azure-devops) | Teams in the Microsoft ecosystem, enterprise requirements | Yes (free tier) | Yes (Azure Repos) |

**Two tools, or one?** GitHub Projects and Azure DevOps host repositories, branches and pull requests themselves, so the PM tool *is* the code host and there is nothing extra to configure. Filesystem and Linear host **no code**, so those projects are split by construction: add one line — `code-host: github` — to `way-of-working.md` → `## Git Workflow`, and pair routes item/state work to the PM tool and branch/PR/review work to the code host, cross-linking the two with a `Refs: <issue-id>` line in the PR body. See [Code host](/docs/concepts/code-host).

### Choosing a Tool

- **Starting solo or want zero dependencies?** Use [Filesystem](/docs/pm-tools/filesystem) — everything lives in your repo as Markdown files (plus a `code-host` for the PRs).
- **Team on GitHub?** Use [GitHub Projects](/docs/pm-tools/github-projects) — issues, labels, and project boards you already know, and one tool for everything.
- **Want a dedicated PM tool?** Use [Linear](/docs/pm-tools/linear) — clean UI, fast workflows, great API (plus a `code-host` for the PRs).
- **Microsoft shop or enterprise?** Use [Azure DevOps](/docs/pm-tools/azure-devops) — Boards work items, branch policies, and pipelines in one place.

You can switch between tools at any time by updating `way-of-working.md`. Your adoption files and Knowledge Base stay the same.

## The Mapping Model

pair uses a consistent hierarchy regardless of tool:

```text
Initiative (strategic goal)
└── Epic (feature set)
    └── User Story (deliverable increment)
        └── Task (implementation step)
```

Each PM tool maps this hierarchy to its own concepts:

| pair Concept | Filesystem | GitHub Projects | Linear | Azure DevOps |
|-------------|-----------|----------------|--------|--------------|
| Initiative | Markdown file | Issue + label | Project | Epic |
| Epic | Markdown file | Issue + label | Issue (parent) | Feature |
| User Story | Markdown file | Issue + label | Issue (sub-issue) | Product Backlog Item |
| Task | Checklist in story | Checklist in issue body | Checklist in issue | Task (child work item) |

## Configuration

All PM tool configuration lives in one place: `.pair/adoption/tech/way-of-working.md`. Each tool guide shows the exact configuration lines to add.
