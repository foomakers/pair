## Prerequisites

- [Claude Code](https://docs.anthropic.com/en/docs/claude-code) installed and authenticated
- A pair-enabled project (`pair-cli init` completed, `.pair/` directory exists) — required for the CLI channel, optional for the [marketplace channel](#install-channels)
- Node.js 18+

## Install Channels

pair ships its skills through **two channels**. Pick one per project — never both at once, or the same skill is installed twice from two sources.

| Channel | Command | What you get | Use it when |
|---------|---------|--------------|-------------|
| **Marketplace** (Claude Code native) | `/plugin marketplace add foomakers/pair` | The full skill catalog as the `pair` plugin, invoked as `/pair:pair-next` (or the bare `/pair-next`) | You work in Claude Code only, want zero setup, and only need knowledge-base-reading skills — adoption-dependent skills need the CLI channel ([see the caveat below](#adoption-files-on-the-marketplace-channel) / [#392](https://github.com/foomakers/pair/issues/392)) |
| **CLI** (tool-agnostic) | `pair-cli init` / `pair-cli update` | Skills written into your repo's `.claude/skills/` plus the `.pair/` knowledge base and adoption files | You want the KB and adoption files in the repo, or you also use Cursor, Windsurf, or Copilot |

Both channels are built from the same source of truth — `packages/knowledge-hub` in the pair repository — so the skill names and content are identical.

<Callout type="warn">
  **Install one channel, not both.** Because the content is identical, installing both puts the
  same skill name in `.claude/skills/` *and* in the plugin catalog — and every cross-skill
  composition in the corpus (a process skill invoking `/pair-capability-verify-quality`,
  `/pair-capability-classify`, …) plus every doc reference uses the bare `/pair-…` form, which now
  matches two sources. **Resolution order between project scope and the plugin is unspecified — do
  not rely on it** (we have verified bare-name resolution only with the plugin as the *sole* source;
  the both-installed case has not been observed). Use the prefixed `/pair:pair-…` form if you ever
  need to be sure which copy runs. Nothing detects this state today — keeping to one channel per
  project is on you.
</Callout>

### Marketplace Install

```bash
# 1. register pair's marketplace (the repository itself)
/plugin marketplace add foomakers/pair

# 2. install the plugin
/plugin install pair@pair
```

The marketplace manifest lives at `.claude-plugin/marketplace.json` in the pair repository, with the plugin manifest alongside it at `.claude-plugin/plugin.json`. The plugin **loads skills only** — it declares no agents, hooks, MCP or LSP servers, commands, monitors, settings overrides or plugin dependencies, and pair's repository root carries none of the directories Claude Code would auto-discover them from. A guard in the pair repository allowlists the keys each manifest may declare (the plugin manifest, the marketplace manifest, and every plugin entry in it), so nothing else can be added by hand without failing the build.

Be precise about what "skills only" covers: because the plugin's source is the whole pair repository, every file in it is **copied** into the cache — including files the plugin never declares, such as `.claude/agents/` and the third-party `.claude/skills/agent-browser`. Non-declaration is a *loading* control: those files sit in the cache inert, and Claude Code exposes exactly the 41 declared pair skills (`claude plugin details pair@pair` reports `Skills (41)`, `Agents (0)`, `Hooks (0)`, `MCP servers (0)`, `LSP servers (0)`).

Claude Code copies the plugin into its own cache (`~/.claude/plugins/cache`), so the knowledge base the skills reference travels with them. Treat the cache as **disposable, not as storage**: `/plugin update` replaces it wholesale, so anything written there — see the adoption-writes warning below — is lost.

### Adoption Files on the Marketplace Channel

<Callout type="warn">
  **Adoption files: the marketplace channel reads pair's, not yours.** The plugin's source is the
  pair repository itself, so `.pair/adoption/` travels inside the plugin cache. Skill steps that read
  an adoption file resolve *that* copy — pair's own decisions — and see them as if they were your
  project's. This is not a graceful-degradation path: no default kicks in, because from the skill's
  point of view adoption files are present.

  Concretely, on the marketplace channel a skill can resolve pair's PM tool
  (`way-of-working.md`: GitHub Projects on the `foomakers/pair` board), pair's risk-matrix and
  coverage deltas, and pair's tech stack — running against **your** credentials. So skills whose
  behavior depends on adoption files — `/pair-capability-write-issue`, `/pair-process-review`,
  `/pair-capability-verify-quality`, `/pair-capability-record-decision`, and any process skill
  composing them — require the **CLI channel** (`pair-cli init`), which puts your own
  `.pair/adoption/` in your repo. On the marketplace channel, stick to skills that only read the
  knowledge base.

  **Adoption *writes* have no correct destination on this channel at all.**
  `/pair-capability-record-decision` is the sole writer of adoption files (ADRs, ADLs, context maps)
  and resolves its targets skill-relative, so on the marketplace channel your recorded decision is
  written **inside the plugin cache** — invisible to your repository and destroyed by the next
  `/plugin update`. Record decisions on the CLI channel; there is no marketplace-channel workaround.
  Project-scoped adoption resolution, read *and* write, is tracked in
  [#392](https://github.com/foomakers/pair/issues/392).
</Callout>

<Callout type="info">
  **Skill naming on the plugin channel.** Plugin skills are exposed as `pair:pair-…`, while the docs
  and every cross-skill composition name siblings in the bare `/pair-…` form. Claude Code resolves
  the bare name too, as long as it is unique — verified on CLI v2.1.220 for a real composition pair
  (`pair-process-review` → `pair-capability-verify-quality`, both resolved from the plugin by bare
  name, with no pair skills installed in the project or user scope). Uniqueness is exactly what
  installing both channels destroys, which is the other reason to pick one. If a bare name ever fails
  to resolve, the prefixed form always works: `/pair:pair-capability-verify-quality`.
</Callout>

Update or remove the plugin with the standard Claude Code commands:

```bash
/plugin update pair@pair
/plugin marketplace update pair
/plugin uninstall pair@pair
```

No version is pinned in the manifest, so an update always fetches the current catalog.

## Configure Agent File

<Callout type="info">
  **CLI channel only.** Everything from here to [Use Skills](#use-skills) — the project structure,
  `AGENTS.md`/`CLAUDE.md` generation, the `.claude/` directory, the bridge pattern — describes a
  project set up with `pair-cli init`. On the marketplace channel none of it exists in your
  repository: the skills and the knowledge base live in the plugin cache.
</Callout>

Claude Code reads two files at the repository root plus the `.claude/` directory:

### Project Structure

```text
your-project/
├── AGENTS.md                    ← universal bridge file (all AI tools read this)
├── CLAUDE.md                    ← Claude Code-specific (generated from AGENTS.md)
├── .claude/
│   ├── settings.local.json      ← permissions and allowed tools
│   └── skills/                  ← canonical skill directory
│       ├── pair-next/
│       ├── pair-process-implement/
│       ├── pair-capability-verify-quality/
│       └── ...                  ← 41 skills
├── .pair/
│   ├── knowledge/               ← upstream guidelines (don't edit)
│   └── adoption/                ← your project decisions
└── ...
```

### AGENTS.md

The universal bridge file. pair generates it during `pair-cli init`. It contains:

- Task selection algorithm (which how-to guide to follow)
- Essential commands (`pnpm install`, `pnpm test`, `pnpm lint`)
- Key references to adoption files and guidelines
- Quick rules (testing, commits, adoption checks)

Claude Code reads `AGENTS.md` automatically when entering a repository. No manual configuration needed.

### CLAUDE.md — Generated from AGENTS.md

`CLAUDE.md` is **not written manually** — pair generates it automatically from `AGENTS.md` using the transform pipeline defined in `config.json`. The `agents` registry controls this:

```json
"agents": {
  "source": "AGENTS.md",
  "behavior": "mirror",
  "targets": [
    { "path": "AGENTS.md", "mode": "canonical" },
    { "path": "CLAUDE.md", "mode": "copy", "transform": { "prefix": "claude" } }
  ]
}
```

The `transform: { "prefix": "claude" }` applies **marker-based rewrites** — the KB source `AGENTS.md` can include or exclude sections for specific targets using markers:

```markdown
<!-- +claude: Claude Code-specific section -->
### Claude Code Tips
Use `/pair-next` at session start. Skills are slash commands.
<!-- +claude -->

<!-- -claude: Exclude from CLAUDE.md -->
### Generic section
This content appears in AGENTS.md but not in CLAUDE.md.
<!-- -claude -->
```

After transformation, all markers are stripped from the output. This lets a **single source file** produce tool-specific variants without duplication.

### The .claude/ Directory

The `.claude/` directory is Claude Code's native configuration location:

- **`.claude/skills/`** — the **canonical** copy of all pair skills. Other AI tool directories (`.github/skills/`, `.cursor/skills/`, etc.) are symlinks pointing here.
- **`.claude/settings.local.json`** — Claude Code permissions (allowed Bash commands, MCP tools, additional directories).

### The Bridge Pattern

All files point to `.pair/` — the single source of truth:

```text
AGENTS.md    ──→ .pair/knowledge/     (guidelines, how-to guides)
CLAUDE.md    ──→ .pair/adoption/      (your decisions)
.claude/skills/ ──→ .pair/ (skills reference adoption + knowledge)
```

When you update adoption files or install new skills, Claude Code picks up the changes at the next session start.

## Use Skills

Skills are invoked as slash commands in Claude Code:

```bash
/pair-next                    # what should I work on?
/pair-process-implement #42   # implement story #42
/pair-process-review          # review current PR
```

### Common Skills

| Skill | Purpose |
|-------|---------|
| `/pair-next` | Determine next action based on project state |
| `/pair-process-specify-prd` | Create or update Product Requirements Document |
| `/pair-process-plan-initiatives` | Plan strategic initiatives from PRD |
| `/pair-process-plan-epics` | Break initiatives into epics |
| `/pair-process-plan-stories` | Break epics into user stories |
| `/pair-process-refine-story` | Refine a story with acceptance criteria |
| `/pair-process-plan-tasks` | Break a story into implementation tasks |
| `/pair-process-implement` | Implement a story task by task |
| `/pair-process-review` | Structured code review |

For the full catalog, see [Skills Catalog](/docs/reference/skills-catalog).

### Skill Discovery

Claude Code discovers skills in `.claude/skills/`. pair installs skills there during `pair-cli init` or `pair-cli update`. Each skill is a `SKILL.md` file that Claude Code reads when you invoke the corresponding slash command.

Skills are installed through the **transform pipeline** — the KB source uses a category structure (`.skills/process/implement/`) which gets flattened and prefixed:

```text
KB source:    .skills/process/implement/SKILL.md
Flatten:      process/implement → process-implement
Prefix:       process-implement → pair-process-implement
Installed:    .claude/skills/pair-process-implement/SKILL.md
```

This happens automatically during `pair-cli init` and `pair-cli update`.

## Workflow Tips

### Start Every Session with `/pair-next`

This reads your adoption files and PM tool state, then recommends the most relevant action. It keeps sessions focused and prevents context loss between conversations.

### Commit Strategy

pair supports two strategies configured in your `way-of-working.md`:

- **Commit per task** — one commit per task, with checkpoints between tasks
- **Commit per story** — continuous flow, single commit at story end

Both strategies produce a single PR per story. The choice affects how granular your Git history is during development.

### Session Context

Claude Code maintains context within a session but starts fresh in new sessions. `AGENTS.md` and `CLAUDE.md` ensure it recovers project context automatically. For long-running work, the `/pair-process-implement` skill tracks progress in the PM tool so you can resume across sessions.

## Verify It Works

Open Claude Code in your pair-enabled project and run:

```bash
/pair-next
```

**Expected output**: Claude Code reads your adoption files and suggests the next action (e.g., "Story #42 is refined and ready — run `/pair-process-implement #42`"). If it can't find `.pair/`, check that `pair-cli init` completed successfully.
