---
title: Adoption Files
description: How adoption files record your project-specific decisions and keep AI assistants aligned with your team's standards.
---

Adoption files are your project-specific decisions, recorded in `.pair/adoption/`. They tell AI assistants what your team chose — which tech stack, architecture pattern, way of working, and product requirements define your project.

While the [Knowledge Base](/docs/concepts/knowledge-base) provides general guidelines and process guides, adoption files provide the **constraints**. Together, they ensure the AI generates code that follows both industry best practices and your team's specific decisions.

## Structure

```text
.pair/adoption/
  product/                      # Product decisions
    adopted/
      PRD.md                    # Product Requirements Document
    context-map.md              # Domain glossary, entities, common rules (optional)
    subdomain/                  # Domain-Driven Design subdomains
      <slug>.md                 # Subdomain catalog entry
      <slug>.context.md         # Lazy per-subdomain context split (optional)

  tech/                         # Technical decisions
    adopted/
      architecture.md           # Architecture pattern and style
      tech-stack.md             # Languages, frameworks, libraries
      infrastructure.md         # Hosting, CI/CD, deployment
      way-of-working.md         # Process, methodology, quality gates
      ux-ui.md                  # Design system, component library
    adr/                        # Architectural Decision Records
```

## What Each File Records

### architecture.md

Documents your chosen architecture pattern, API style, and data storage approach:

```text
- Monolith with REST API
- SQLite for data storage
- All components self-hosted
```

### tech-stack.md

Lists every approved technology with exact versions:

```text
- TypeScript v5.x
- React ^19.0.0
- Vitest v3.x for testing
- pnpm v10 for package management
```

When the AI generates code, it only uses libraries listed here. During code review, unlisted dependencies are flagged.

### way-of-working.md

Defines your development process:

```text
- Kanban workflow
- Feature branches with squash merges
- Quality gate: pnpm quality-gate
- Code review required before merge
```

It also hosts an optional `## State Mapping` section — only needed if your board's column names differ from pair's [canonical states](/docs/concepts/canonical-states). Omitted by default.

### PRD.md

Your Product Requirements Document — the source of truth for what the project does, who it serves, and what features are prioritized (P0/P1/P2).

### context-map.md

An optional, living domain model: dispatcher + subdomain index + core (glossary, entities, common rules and invariants). Unlike the other adoption files, it isn't scaffolded during bootstrap — it's created and updated inline the first time a brainstorm or refine session sharpens a domain term, per the [Context Map Maintenance](https://github.com/foomakers/pair/blob/main/packages/knowledge-hub/dataset/.pair/knowledge/guidelines/architecture/design-patterns/context-map-maintenance.md) guideline. There's no dedicated skill for it — no ceremony, just an embedded step in the skills that already touch domain scope.

For a worked example, see Pair's own map — the framework dogfoods this artifact to register its canonical terms (macrostate, risk matrix, DDR, checkpoint, working area, marketplace…): [`.pair/adoption/product/context-map.md`](https://github.com/foomakers/pair/blob/main/.pair/adoption/product/context-map.md).

```text
- Subdomain Index: which subdomains have their own context file, classification, Volatility (mirrored from the subdomain catalog)
- Glossary: ubiquitous language, one row per term
- Entities: domain entities and aggregates
- Common Rules and Invariants: domain-wide business rules
```

The unit is the **subdomain**, not a separate "domain" taxonomy. When a subdomain's inline context grows too large, the session proposes moving it to a co-located `subdomain/<slug>.context.md` file — lazy, and only after you approve. The map keeps the index entry and the domain-wide rules; everything subdomain-specific (glossary, entities) moves to the sibling file.

If the file doesn't exist, AI assistants skip the domain check entirely — this is the expected state for most projects, not an error.

## How They Get Created

You don't write adoption files by hand. There are two paths:

**New project** — Run `/pair-next` in your AI assistant. It guides you through the full structured process: PRD creation, bootstrap checklist, architecture assessment, tech stack evaluation, and so on. Each step produces the corresponding adoption file automatically.

**Existing project** — Ask your AI assistant to analyze the codebase and generate adoption files from what already exists. For example: *"Analyze this project and write the adoption files — architecture, tech stack, way of working."* The AI inspects your dependencies, folder structure, CI config, and conventions, then produces adoption files that reflect your current reality. From there, skills stay aligned with your actual stack.

Either way, once adoption files exist, every subsequent AI session reads them and stays consistent.

## How the AI Uses Them

Every time an AI assistant starts a session, it reads the adoption files to understand your constraints:

1. **Generating code** — uses only approved libraries and follows the architecture pattern
2. **Creating tasks** — references adoption files in each task specification
3. **Code review** — checks that new code conforms to recorded decisions
4. **Making decisions** — when a new choice arises, records it as an ADR, ADL, or DDR; a completed technical analysis is logged separately (analysis-log)
5. **Generating stories** — reads the decision log, the ADRs and the context map *before* drafting, so a new story never re-proposes something already rejected (see below)

If a developer asks the AI to add a feature and the implementation requires a library not in `tech-stack.md`, the AI flags it and creates an Architectural Decision Record (ADR) to document the choice.

### Adoption is read back when stories are generated

Recording a decision is only half the loop. Story generation — `/pair-process-plan-stories`, `/pair-process-brainstorm`'s triage phase, and `/pair-process-refine-story` — reads your recorded decisions and your context map **before** it drafts anything, and that read does exactly three things:

- **Constrains** — a candidate that contradicts a live decision is reshaped to fit it or dropped, and one that re-proposes something a decision already rejected is never generated.
- **Cites** — whatever a decision shaped carries it inline: `(per ADR-013)`, `(per decision-log/2026-07-12-adr-sequential-naming-convention)`, `(per context-map: macrostate)`. You see *why* the story is shaped that way without opening the adoption tree.
- **Flags a revisit** — a story that genuinely needs to reopen a decision is allowed, but it says so (`Revisits ADR-013: <why>`) in the proposal you confirm. Silently contradicting a decision is the one thing it won't do.

The read is **read-only** (generation never writes a decision — that stays with you and `/pair-capability-record-decision`), **bounded** (every record is indexed, but only the ones in the story's scope are opened in full, so a large decision log doesn't flood the prompt), and **superseded-aware** (a record marked `Superseded` is never the authority; the record that replaced it is). On a fresh project with no decisions yet, generation behaves exactly as it did before — no citations, no warnings, never a failure.

The mechanics are defined once, in the [adoption-informed generation convention](https://github.com/foomakers/pair/blob/main/packages/knowledge-hub/dataset/.pair/knowledge/guidelines/technical-standards/ai-development/skill-conventions/adoption-informed-generation.md), and pointed at from each generating skill.

## Architectural Decision Records

When significant technical decisions are made, they are recorded as ADRs in `.pair/adoption/tech/adr/`:

```text
adr/
  adr-001-tty-detection-pattern.md
  adr-002-http-range-resume.md
  adr-003-checksum-validation.md
```

Each ADR documents:
- **Context** — what problem needed solving
- **Decision** — what was chosen and why
- **Consequences** — tradeoffs and implications

ADRs provide an audit trail of your project's technical evolution.

## Domain Decision Records

Domain decisions — business rules, glossary terms, or behavior — are recorded as DDRs in `.pair/adoption/product/ddr/`, but only when they clear a 3-criteria gate: hard to reverse, surprising without context, and a real trade-off. A candidate that fails the gate is recorded as an ADL or an inline context-map note instead.

```text
ddr/
  ddr-001-refund-window-30-days.md
  ddr-002-single-active-subscription.md
```

Each DDR documents:
- **Context** — the domain rule affected and evidence for each gate criterion
- **Decision** — the rule now in force
- **Consequences** — tradeoffs and implications
- **Context Map Impact** — which entry in `context-map.md` (or `<slug>.context.md`) changed

Unlike ADRs, a DDR always syncs a second artifact — the context map — so the domain's current state never diverges from why it got that way.

## Analysis Log

A completed technical analysis (performance investigation, dependency evaluation, benchmark) isn't itself a decision, so it's recorded differently: an analysis-log entry in `.pair/adoption/decision-log/` — the same directory ADL uses, distinguished only by Category `Analysis`. No new artifact directory is introduced.

```text
decision-log/
  2026-06-01-checkout-latency-investigation.md   # Category: Analysis
  2026-06-15-payment-provider-benchmark.md       # Category: Analysis
```

Each analysis-log entry documents:
- **Context** — what prompted the analysis
- **Analysis / Findings** — what was investigated and found
- **Recommendation** — what should happen next, if anything
- **Adoption Impact** — which adoption file's current-state summary now reflects this analysis

Like DDR↔context-map, this follows a history↔state split: the record is history (never edited once written — a repeated analysis always adds a new record), while the pertinent adoption file's summary is current state, always replaced with the latest analysis' findings. If no adoption file is clearly pertinent, the AI asks instead of guessing; if the findings contradict an existing ADR, it flags that instead of silently overwriting the summary.

## Protection

Adoption files are protected by design. When pair updates the Knowledge Base (`pair-cli update`):

- **Knowledge files** update — guidelines, process guides, templates refresh
- **Adoption files stay** — your decisions are never overwritten

This is enforced by the asset registry system: the `adoption` registry uses **add** behavior, meaning it only creates files that don't already exist. Your team's decisions are permanent until you explicitly change them.
