# Trigger Eval — After T3 (2026-07-13)

Run of `../trigger-prompts.json` against the **rewritten** frontmatter descriptions (T3 of
story #313 — trigger-oriented rewrite of all 35 `description` fields). This is the "after" half
of the before/after evidence required by AC7 and by principle 9 ("Evaluation") of the authoring
standard. Baseline ("before"): `2026-07-12-baseline.md`.

## Methodology

- **Executor**: single LLM (Claude, Sonnet 5), single pass per prompt. The executor was shown the
  full catalog of 35 `name` + `description` pairs (frontmatter only, post-T3) and one prompt at a
  time, cold (no conversation history about the corpus beyond having authored the rewrite in the
  same session — see bias disclosure below).
- **Instruction**: pick the single skill you would load, `none` if no skill applies, name all
  candidates when two or more descriptions claim the prompt equally.
- **Bias disclosure**: same caveat as the baseline — the description author and the eval executor
  are the same model/session lineage, and here the rewrite was explicitly targeted at the three
  known ambiguities (AD-12, AD-14, PB-N2). Ambiguity may be *under*-reported for that reason. To
  compensate, every prompt (not just the previously-ambiguous ones) was re-run against the full
  new catalog rather than only re-checking the three known cases, so a regression on an
  unrelated, previously-clean prompt would still surface. Near-ties resolved by judgment are
  marked PASS with a note rather than silently passed, exactly as in the baseline.
- **Verdicts**: PASS (selected = expected), AMBIGUOUS (>=2 candidates named), FAIL (selected !=
  expected).
- **Scope note**: `next`'s description was reviewed and left unchanged — it already satisfied
  principle 1 (when-to-use phrasing, no body-identity restatement) per the baseline's own
  observation that it was the one description already conformant. All other 34 descriptions were
  rewritten.

## The 3 baseline ambiguities — resolution

### AD-12 / PB-N2 (assess-pm vs setup-pm)

**Root cause (baseline)**: both descriptions claimed tool *selection* — assess-pm "proposes a
tool choice", setup-pm "guiding selection from supported options".

**Fix**: removed "selection" language from setup-pm entirely; the split is now by **verb**, not
by decision-state:

- `assess-pm`: "Evaluates and recommends which project management tool fits this project (Jira,
  Linear, GitHub Projects, etc.) when the choice is still open — proposes a choice, doesn't
  configure anything. `/setup-pm` configures the tool once picked; otherwise the caller persists
  the proposal via `/record-decision`."
- `setup-pm`: "Configures the project management tool — creates/wires it up, applies its
  implementation guide, updates way-of-working, records the decision — whether the tool was
  already chosen or picked here. Invoke directly to set up a tracker ('configure Jira', 'set up
  GitHub Projects'). Composed by `/bootstrap`; `/assess-pm` delegates here once a tool is picked."

`assess-pm` owns *recommend/evaluate* ("haven't picked... what should we use", "recommend where
to track work items"); `setup-pm` owns *configure/set up* ("configure Jira", "set up GitHub
Projects", "we already decided — set it up"). Neither description shares the ambiguous "selection"
word anymore, so a prompt names at most one verb.

**Result**: AD-12 ("recommend where we should track our work items") -> assess-pm only, clean.
PB-N2 ("haven't picked a tracker — what should we use") -> assess-pm only, clean. AD-N1 / PB-03
(the setup-pm-side prompts) remain clean, now on a stronger "configure"/"set up" verbatim match.

### AD-14 (assess-stack vs verify-adoption)

**Root cause (baseline)**: assess-stack's implementation-phase branch ("add dependency") was
buried in the cryptic clause "implementation (add dependency)"; verify-adoption's "checks code and
configuration against project adoption files" claimed the same prompt.

**Fix**: made the branch explicit with the exact prompt phrasing, and added an explicit
forward/backward-looking distinction on both sides:

- `assess-stack`: "...when the choice is open: full evaluation at bootstrap, or a single new
  dependency during implementation ('should we add Redis', 'is this new dependency consistent
  with our stack'). Doesn't audit code already written (that's `/verify-adoption`)."
- `verify-adoption`: "Detects conformity/non-conformity of **already-written** code and
  configuration against the project's adopted decisions... a compliance audit, not a
  new-choice evaluation (that's `/assess-stack` and siblings)."

The distinguishing predicate is **already-written vs proposed**: Redis in AD-14 is a dependency
being *proposed*, not code already in the repo, so assess-stack's verbatim example wins and
verify-adoption's own description now explicitly disclaims new-choice prompts.

**Result**: AD-14 -> assess-stack only, clean (near-verbatim match to the description's own
example phrasing).
