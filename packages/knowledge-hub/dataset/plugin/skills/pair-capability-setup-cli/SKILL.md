# /pair-capability-setup-cli — Bootstrap pair in this project

Install `pair-cli` and let **the CLI** produce this project's pair files.

## When to use this

You installed pair through Claude Code's marketplace (`/plugin install pair@pair`). You have the skills, but this project has no `.pair/` and no `.claude/skills/` of its own — so every skill step that reads an adoption file finds **pair's own**, not yours. This skill closes that gap: one run, and the project's files exist, generated by the CLI with the CLI's paths.

Do **not** use it to update an existing pair install — that is `pair update`. This skill is the first-time bootstrap.

## Why this skill carries no knowledge-base references

Every other pair skill links into `.pair/knowledge/**`. This one deliberately does not, and must not: it runs **before** the knowledge base exists in the project, and on the marketplace channel the only knowledge base within reach is pair's own. A reference here would be dangling at best and wrong at worst. Everything this skill needs to know is written in this file.

## Step 1 — Establish a repository

Read the state, then act:

```bash
git rev-parse --is-inside-work-tree 2>/dev/null
```

- **Inside a work tree** → continue to Step 2.
- **Not a repository** → create one, then continue. The absence of a repository is a handled precondition, not a failure:

```bash
git init
```

Say which branch `git init` created, because the rest of the session (branch names, PR flow) depends on it.

## Step 2 — Choose the install mode

Two facts decide it: whether this project has a `package.json`, and which package manager it uses.

```bash
ls package.json 2>/dev/null
ls pnpm-lock.yaml yarn.lock package-lock.json bun.lockb 2>/dev/null
```

| State | Mode | Command |
| --- | --- | --- |
| `package.json` + `pnpm-lock.yaml` | local dev dependency | `pnpm add -D @foomakers/pair-cli` |
| `package.json` + `yarn.lock` | local dev dependency | `yarn add -D @foomakers/pair-cli` |
| `package.json` + `package-lock.json` | local dev dependency | `npm install -D @foomakers/pair-cli` |
| `package.json`, no lockfile | local dev dependency | ask which manager to use, then the matching command |
| no `package.json` | no install | `npx @foomakers/pair-cli <command>` |

Three rules, each with a reason:

1. **Detect the manager from the lockfile, never default to one.** Installing with the wrong manager writes a second lockfile into the project, which is a change the user did not ask for and will not expect.
2. **With a `package.json`, install locally rather than globally.** The CLI version then travels with the project, so a later run resolves the same version rather than whatever is on the machine.
3. **No `package.json` means no install at all** — use `npx`. Creating a `package.json` to hold a dev dependency would turn a non-Node project into a Node one.

**Already installed?** If `@foomakers/pair-cli` is already a dependency, skip the install and go to Step 3. Do not reinstall.

**Always state the mode you chose** before running anything. A user who cannot tell whether a tool was added to their project has to go and check.

## Step 3 — Let the CLI produce the files

Run the install through the mode chosen above:

```bash
# local mode — npx resolves the project's own binary first, so this is
# manager-agnostic and needs no pnpm/yarn/npm exec variant
npx pair-cli install

# no-package.json mode — fetch and run without installing
npx @foomakers/pair-cli install
```

This writes `.pair/` (knowledge base, adoption templates) and `.claude/skills/` (the skill catalog) with the CLI's own naming — which is the point of routing through the CLI instead of copying files by hand: the paths a skill references and the paths on disk are produced by the same transform, so they cannot disagree.

Report what the CLI reported. Do not summarise a failure as success.

## Step 4 — Report what exists now, and what the plugin is still for

There is **no duplicate to resolve**, and it is worth saying so rather than leaving the user to wonder: this bootstrap skill is the plugin's only skill, and the CLI does not install it — it is authored outside the distributed corpus for exactly that reason. So after Step 3 the project's `.claude/skills/` holds the full catalog, the plugin holds this one skill, and no name resolves from two sources.

Report:

> pair is installed in this project: `.pair/` (knowledge base and adoption files) and `.claude/skills/` (the full skill catalog) are now in your repository, generated by the CLI. The marketplace plugin still holds this bootstrap skill only — no skill name comes from two places, so you can keep it for the next project or remove it with `/plugin uninstall pair@pair`.

Then point at the next step: `/pair-next` reads the project state and recommends what to do first.

## Idempotence

Re-running this skill is safe and is expected to be a confirmation, not a repeat: an existing repository is left alone, an installed CLI is not reinstalled, and `pair install` on an already-installed project reports what it finds. If any step would overwrite something the user changed, say so and stop instead.

## What this skill does not do

- It does not configure a PM tool, quality gates, or any adoption decision — those are their own skills, and they need the knowledge base this skill installs.
- It does not update an existing install (`pair update`).
- It does not uninstall the plugin for you. Removing a plugin from the user's Claude Code installation is theirs to run, not a side effect of a setup step.
