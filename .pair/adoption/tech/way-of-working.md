# Way of Working

- Rapid, iterative development cycles with releases as needed.
- Lightweight code review and testing practices focused on speed and learning.
- Minimal documentation: key decisions and usage documented in markdown files.
- Collaboration and process guidelines follow the standards in `/.pair/tech/knowledge-base/12-collaboration-and-process-guidelines/project-management-framework.md`.
- Github Projects is adopted for project management, using Kanban as the workflow methodology. The project is pair under the github organization foomakers. See `/.pair/tech/knowledge-base/12-collaboration-and-process-guidelines/project-management-framework.md` for usage. use #github MCP to access Github Projects, boards and issues.
- High risk tolerance: quick rollbacks and fast recovery from errors.
- Team communication is informal and direct, with decisions validated collaboratively.
- **Commit History Policy:**: feature branches are squashed into a single commit at PR merge, unless the story or epic says otherwise ([commit template](../../knowledge/guidelines/collaboration/templates/commit-template.md)). Unless specified, commit per task (commit title marks the task number besides the story number), completing all the story's tasks and updating the story body at each commit without confirmation. At the end of the story raise a draft PR per the PR template.
- Commit messages and PRs use the [commit template](../../knowledge/guidelines/collaboration/templates/commit-template.md) and [PR template](../../knowledge/guidelines/collaboration/templates/pr-template.md).
- **Assignment — everything worked on carries an assignee:** every item an agent or a human touches (story, tech-debt, epic, PR) is **assigned to the person the work is done for** — here, the maintainer — when the work starts, including follow-ups filed _during_ the work (most often orphaned) and the PR as well as the story. The board is read filtered by assignee: an unassigned item (or a PR with `author` set but empty `assignees`) is invisible there even when open, with a PR and green. `/pair-capability-write-issue` and `/pair-capability-publish-pr` set the assignee as part of the write, never as a follow-up step.
- **PR granularity — one PR per story (default):** a story lands in one PR even when broken into inline tasks/findings. Splitting needs an explicit reason (e.g. unusually large story, or independently shippable/needed-sooner parts). Per-task granularity is commit-per-task (Commit History Policy above), not separate PRs. See ADL [2026-07-12-one-pr-per-story-default.md](../decision-log/2026-07-12-one-pr-per-story-default.md).
- **Implementation and review never file a new card:** a defect, gap or debt found while implementing or reviewing is fixed **in the same PR**; outside the story's stated scope, the **story is extended** (scope section + acceptance criteria) and it is still fixed there. Only a finding so large it would swamp the story stays an _actionable_ finding on the PR for the maintainer at the merge gate — never a fresh issue. Citing an **already-existing** card is allowed; creating one is not. See ADL [2026-08-12-implementation-never-files-a-card-it-extends-the-story.md](../decision-log/2026-08-12-implementation-never-files-a-card-it-extends-the-story.md).
- **Only substantive findings cost a review round:** a finding blocks only when substantive — behaviour, correctness, security, or a documentation statement that would lead someone to do the wrong thing. A cosmetic finding (wording, style, a stale phrase with no practical effect) is a non-blocking note (severity `Questions`) and never triggers another fix-and-review round. A delta review judges only the lines its delta changed; anything else it notices is a note. See ADL [2026-09-25-only-substantive-findings-cost-a-review-round.md](../decision-log/2026-09-25-only-substantive-findings-cost-a-review-round.md).
- **Delivery-cycle automation:** the cycle, its stages, realizations, profiles, hooks, `merge` stage and unattended flow are mapped in [The Delivery Cycle](../../knowledge/guidelines/collaboration/automation/delivery-cycle.md); schemas in [automation-policy.md](../../knowledge/guidelines/collaboration/automation/automation-policy.md), the GitHub trigger adapter in [github-automation.md](../../knowledge/guidelines/collaboration/automation/github-automation.md).

## Story Closure (post-merge)

Per merged PR, in order: **1)** squash merge, message per [commit template](../../knowledge/guidelines/collaboration/templates/commit-template.md) · **2)** story: check the DoD boxes in the body, close (`completed`), write board state `Done` ([State Mapping](#state-mapping)) · **3)** cascade: epic/initiative close only when ALL sub-issues are Done · **4)** cleanup: delete branch **remote AND local** (remove any worktree holding it first), remove the story checkpoint and the PR analysis under `working/pr-analyses/` · **5)** optional P0 manual tests.

Detail: [merge-and-cascade.md](../../knowledge/guidelines/technical-standards/) Steps 6.0–6.6 · local-branch + analysis-retention rules: [ADL 2026-08-25](decision-log/2026-08-25-post-merge-cleanup-covers-local-branches-pr-analyses-retire-at-merge.md).

## State Mapping

Maps this project's GitHub Projects board columns to the 5 canonical macrostates (see [canonical-states.md](../../knowledge/guidelines/collaboration/project-management-tool/canonical-states.md)). Skills read and write item state through this map, never the raw board labels.

| Board State | Macrostate  |
| ----------- | ----------- |
| Todo        | Draft       |
| Refined     | Ready       |
| In Progress | In Progress |
| Done        | Done        |

- `Refined` (legacy board column) maps to the canonical `Ready` — the column keeps its name, skills treat it as `Ready` (migration note #243). This is what lets `/pair-process-refine-story` complete its Draft→Ready transition on this board.
- No board column maps to `Review`: this project reviews on the PR and merges straight to `Done`. A skill asked to write `Review` will HALT and report the gap rather than guess.
- `Not planned` (Status option `1d5cee95`) is a board column **deliberately left unmapped** — skills ignore it, like `Removed` ([Closure Without Completion](../../knowledge/guidelines/collaboration/project-management-tool/canonical-states.md#closure-without-completion)). Whoever closes an item as not planned sets its Status to `Not planned`, never `Done`: the built-in close automation cannot tell the reasons apart ([ADL](../decision-log/2026-10-14-not-planned-board-column.md)).

## Review Convergence

- **Mirrors counted once:** code review (classification footprint included), the PR body and the PR analysis count a mirror copy (`.claude/**`, `.pair/knowledge/**`, `.github/agents/**`, generated from `packages/knowledge-hub/dataset/**`) **zero times** when its canonical `dataset` file changed in the same diff and the copy equals the regenerator's output (`pnpm mirrors:regenerate` leaves the head unchanged; `cmp` only for `.claude/workflows` and `.claude/agents`). Counts use the canonical file; mirrors are reported once as `mirrors regenerated: N files, match the regenerator`; a mirror-only file or a drifted copy is counted and flagged. See ADL [2026-09-29-mirrors-counted-once.md](../decision-log/2026-09-29-mirrors-counted-once.md).
- **Baseline then delta:** the first review is complete and returns the immutable 40-character
  head it inspected. A re-review verifies prior findings plus only the diff from that head and
  directly changed producer/consumer boundaries; an unchanged PR surface does not create another
  fix round. Missing or invalid review-head evidence fails closed, never converges a PR.
- **Provisioned artifact proof:** a fix that installs, builds, publishes, names, or invokes an
  artifact maps `producer -> published identity -> consumer` and proves the real path in a clean
  temporary environment. The exact boundary is never stubbed, aliased, or faked. See ADL
  [2026-08-31-review-baseline-and-provisioned-artifact-contract.md](../decision-log/2026-08-31-review-baseline-and-provisioned-artifact-contract.md).
- **Contract inventory before a loop:** before reporting or fixing a changed contract, inventory
  its authoritative producer, inputs, consumers and representations. A finite protocol, parser,
  configuration or state transition gets a complete decision table of supported and
  invalid/boundary states, with a real probe/test per row. A row, equivalence, normalization or
  repair that depends on an external tool/service/format is proven at that authoritative boundary;
  an internal unit test cannot prove external semantics or that repair advice works. Re-review
  applies the same rule only to its delta and changed boundary. See ADLs
  [2026-09-01-review-contract-inventory-prevents-serial-findings.md](../decision-log/2026-09-01-review-contract-inventory-prevents-serial-findings.md)
  and [2026-09-01-external-boundary-proof-prevents-false-equivalence.md](../decision-log/2026-09-01-external-boundary-proof-prevents-false-equivalence.md).

## Quality Gates

- `pnpm quality-gate` is the adopted project-level quality gate command.
- Quality gate includes: type checking (`ts:check`), testing (`test`), linting (`lint`), formatting and markdown lint in **check mode** (`format:check`), plus a guard that the gate stays check-mode (`gate:composition`) and the smoke-scenario mode guard (`smoke-modes:check`).
- **`format:check`/`format` coverage is whole-repo, derived from git, not turbo's per-workspace scope** (#414): `scripts/format-lib/run-format.sh` lists every path `git ls-files --cached --others --exclude-standard` reports (extension-filtered), so "gitignored ⇒ never checked" is git's own rule (nested `.gitignore` files and the global `core.excludesFile` apply by construction). Root-level and non-workspace files (`.claude/**`, `.pair/adoption/**`, `qa/**`, `scripts/**`) are checked like workspace files. **One documented exception**: third-party skills under `.claude/skills/` (any directory not matching the `pair-*` prefix, e.g. a marketplace skill) are never checked. An empty derived file set is a broken wrapper (exit 2), never a silent pass (`scripts/format-lib/git-tracked-paths.sh`). The per-package glob invocation (`pnpm --filter <pkg> prettier:check`/`mdlint:check`) still uses the wrappers' `_ignore-args.sh`/`_ignore-file.sh` ignore assembly.
- **A guard whose only caller is a turbo task is not enforced.** `turbo ts:check test lint` are cacheable with package-scoped inputs, so a change OUTSIDE the guard's package replays a cached PASS and the guard never executes. A guard over repo-wide state therefore gets a thin CLI and a **root gate step** (`hygiene:check`, `smoke-modes:check`, `docs:staleness`, `skills:conformance`), run unconditionally — a unit test alone enforces only logic whose inputs live inside its own package (#400).
- **No step reachable from the gate writes files**: the gate reports, `pnpm format` / `pnpm lint:fix` fix deliberately. `gate:composition` enforces this through an **explicit offender list** — the two formatters, eslint autofix, and the repo's write scripts (`sync-version`, `test:perf`, `mirrors:regenerate`) — so **adding a new write-mode script to this repo means adding it to that list** (a differently named writer passes green). For `mirrors:regenerate`, the gate's own remedy, `gate:composition` checks both that it EXISTS (named advice must resolve) and that it is never REACHED (it would rewrite the tree at pre-push). See ADL [2026-07-31-pre-push-gate-is-check-only.md](../decision-log/2026-07-31-pre-push-gate-is-check-only.md).
- **Pre-merge tiering**: `disabled` (default) — every PR runs the full pre-merge check suite. Set to `enabled` to opt into risk-tier-scoped pre-merge checks (lighter checks on lower-risk PRs) per [tier-aware-pipeline.md](../../knowledge/guidelines/infrastructure/cicd-strategy/tier-aware-pipeline.md); `/pair-capability-setup-gates` reads this flag before generating the pipeline.
- **Review enforcement**: `disabled` (default) — the pair review **runs and publishes its verdict**, but nothing it says blocks a merge: `pair-review` and `pair-explicit-approval` are not required status checks, and the 🔴 explicit-approval rule is advisory. Set to `enabled` to make them required and the rule binding, per [pr-states.md](../../knowledge/guidelines/collaboration/project-management-tool/pr-states.md); `/pair-capability-setup-gates` reads this flag before touching branch protection, `/pair-process-bootstrap` asks for it when no decision exists. Disabled by default because a blocking review makes a first install unmergeable — on a single-maintainer repo the 🔴 non-author approval is unobtainable. The tier requirements are redefinable in this file (§ Review Tier Matrix); that the review **runs** is not.
- **Review identity**: `none` (default) — every code-host write (the native review verdict, the `pair-review` publication) executes with the **session token**, i.e. the human or agent running the flow. Set to `app` (a GitHub App — recommended: it unlocks the Checks API and makes "who reviewed" auditable per-identity) or `bot-user` (a second machine account) to run those writes as a **dedicated review identity** ([github-implementation.md](../../knowledge/guidelines/collaboration/project-management-tool/github-implementation.md) § Dedicated review identity; model and actor table in [pr-states.md](../../knowledge/guidelines/collaboration/project-management-tool/pr-states.md)). Configured-but-broken is a **HALT**, never a silent fallback to the session user. It does **not** relax the 🔴 rule: an `app` identity fails `pair-explicit-approval`'s account-type clause (`user.type == "User"`); a `bot-user` types as `"User"`, is rejected only by its login, and so **requires** the repository variable `REVIEW_IDENTITY_LOGIN` (unset ⇒ unhealthy ⇒ HALT). Either way a `risk:red` PR still needs a second human account. A native `APPROVE` is submitted **only** where the adoption-gated light row authorizes it; every other approving verdict is a comment-form review, so the identity never satisfies a host `required_approving_review_count` on the project's behalf.
- **Coverage guardrail**: `enabled` — pair dogfoods its own capability: the CI [`Coverage guardrail` step](../../../.github/workflows/ci.yml) sources [`coverage-gate.sh`](../../knowledge/assets/coverage-gate.sh), reads the line-coverage % from each package's istanbul `coverage-summary.json`, and blocks a PR whose coverage drops below the human-committed baseline in [`tech/coverage-baseline.md`](./coverage-baseline.md) (maintaining/improving passes — not an absolute wall). The framework **default remains `disabled`** (the dataset template ships off); this is pair's project-level opt-in. See [coverage guardrail](../../knowledge/guidelines/infrastructure/cicd-strategy/tier-aware-pipeline.md#coverage-guardrail-opt-in-regression-gate-consumed-by-this-pipeline) + [config format](../../knowledge/assets/coverage-config-example.md); `/pair-capability-setup-gates` reads this flag before generating the pipeline. **Coverage baseline commit-back**: `disabled` — the nested opt-in ratchet (#372, framework default also `disabled`): when `enabled`, a push to the base branch proposes a raised `baseline.<type>` as a **bot pull request** from `chore/coverage-baseline-ratchet`, never a push to `main`, and needs a repo-scoped `COVERAGE_RATCHET_TOKEN` (absent: the step warns, the gate's verdict is unchanged; details in ADL [2026-07-30-coverage-ratchet-pr-not-push.md](../decision-log/2026-07-30-coverage-ratchet-pr-not-push.md)). It stays `disabled` here until story #234's branch protection is applied and that secret is provisioned (ADR-018, landing with that story, is not linked from here yet). It runs the **shipped** KB asset `node .pair/knowledge/assets/coverage-ratchet.cjs` (ADR-023), the one an adopter's pipeline invokes, so `enabled` means the same everywhere.
- **Pair review required checks**: `pair-review` + `pair-explicit-approval` are the required status checks that make the judgment review unskippable (R5.7) and enforce the 🔴 explicit-human-approval rule (D10) — see [pr-states.md](../../knowledge/guidelines/collaboration/project-management-tool/pr-states.md) and [ADR-018](adr/adr-018-pr-state-flow-required-checks.md). Here: **not yet applied** (branch protection needs admin scope — a deliberate human step); until then enforcement is advisory (the documented degraded mode). **Ordering constraint** (else every merge stops; the whole sequence is verified in `github-implementation.md` § "Verified on a throwaway repository", so what remains is applying it): 1. provision the `pr-state:*` labels + add the `pair-explicit-approval` workflow (no admin scope; not added here yet, so the context does not report today); 2. confirm on a real PR that both contexts report on the head commit **and** the approval context re-reports on that same head SHA after a review submission; 3. only then `PUT` the branch protection, `enforce_admins` off until one PR has merged through it. **This repo is single-maintainer**: GitHub rejects a self-approval, so 🔴 is satisfied — without a second human reviewer account — by the **approval token** of [#398](https://github.com/foomakers/pair/issues/398) (`/approve <head-sha>`; the actor is resolved server-side — human account, not an app, **repository permission** read back from the collaborators API as `admin`/`maintain`/`write`, `author_association` only a pre-filter — and bound to the current head), which here requires the Actions variable `PAIR_SOLO_APPROVAL_TOKEN` = `true` (any case) to suspend its author exclusion (unset: refused on a self-authored PR, and the status names the variable). It is **explicit human confirmation, not independent review**, and **not** forgery-resistant while the agent runs on the maintainer's own credentials — that needs the dedicated agent identity of [#218](https://github.com/foomakers/pair/issues/218) (ADR-018 § Amendment). **When the protection is written here, use the `checks` form with `app_id` pinned** for `pair-explicit-approval` (unpinned, any push-access token satisfies it, the agent's included); `pair-review` stays unpinned — an anti-accident control, not an authorization control (`github-implementation.md` § "What each context proves").
- **`mirror-realign-command`**: `pnpm mirrors:regenerate` — the single, local, deterministic writer realigning the generated mirrors with `packages/knowledge-hub/dataset`: a wrapper of `pair update --source <local dataset> --offline`, no generation logic, **no check mode** (the mirror guards, `skills:conformance`, check). It writes into `.claude/**`, root `.pair/**`, `AGENTS.md`/`CLAUDE.md` and `.github/**` — **where its output lands, never a staging rule**: those trees also hold authored files (117 tracked under `.pair/adoption/**`), so `/pair-capability-publish-pr` stages a **before/after `git status --porcelain -z` comparison** and no adopter enumerates owned globs. **Writer and checker differ in scope**: the guards check only **dataset-sourced** mirrors; this command also rewrites skill references across the whole installed tree, unverified — drift there accumulates and lands, unrelated, in whichever PR next runs the writer (evidence, [PR #476](https://github.com/foomakers/pair/pull/476): `scripts/regenerate-mirrors.sh` header). **The writer reads the whole target tree, untracked files included; the registry's behaviour decides a target-only file's fate** (measured in `regenerate-mirrors.test.ts`; producers `apps/pair-cli/config.json`, `apps/pair-cli/src/registry/llms-generation.ts`). **Unsafe — the run must start with no untracked (`??`/`A.` in porcelain) file under them:** `.pair/knowledge/**` and `.github/agents/**` (`behavior: "mirror"`) — the file is **deleted**, before indexing; `.pair/adoption/product/**`, `.pair/adoption/tech/**`, `.pair/adoption/decision-log/**` (`behavior: "add"`, the sections `generateLlmsTxt` scans) — a `.md`/`.mdx` file **survives but is indexed** as a dangling line in the committed `.pair/llms.txt`. **Safe — written there, but not in that set:** `.claude/**` (`behavior: "overwrite"`; `.claude/settings.local.json` comes out byte-identical and unindexed), `.github/workflows/**`, `.github/ISSUE_TEMPLATE/**` and every other `.github/` folder outside `agents` (`skip`), the `*/skills/` symlink targets, `.pair/adoption/` outside the three indexed sections or a non-`.md` file inside them, and the rest of `.pair/**`; an untracked `AGENTS.md`/`CLAUDE.md` would be **overwritten**, not deleted. `git stash push -u -- <paths>` the unsafe ones and `git stash pop` afterwards, or commit them first; `/pair-capability-publish-pr` HALTs on them and only them (per-row examples and rationale: the ADL below). `PRE_PUSH_REMEDY`, both mirror guards, `DEVELOPMENT.md` and its docs-site twin name it; `/pair-capability-publish-pr` runs it (Phase 1, before the gate) and commits any diff separately, and skips the step when this key is absent (the zero-configuration default, not a degradation). Deliberately **not** `pair update`, which installs the latest PUBLISHED knowledge base and would make a local fix depend on a release. See ADL [2026-09-01-publish-pr-realigns-mirrors-before-the-gate.md](../decision-log/2026-09-01-publish-pr-realigns-mirrors-before-the-gate.md) and story [#419](https://github.com/foomakers/pair/issues/419).
- **`format-check-command`**: `pnpm -s format:check` — the repo-wide format gate, check mode. `cycle-state.mjs publish --repoRoot <worktree>` runs it when red-spec publishes a contract and refuses (`artifact-unformatted:<file>`) any test artifact it names: a sealed byte can never be reformatted. It fails closed: a listed artifact missing under the root (`artifact-missing`) or a run past `PAIR_FORMAT_CHECK_TIMEOUT_MS` (default 5 min, `artifact-format-check-timeout`) is refused. An optional trailing `(covers: <ext> …)` refuses extensions outside it (`artifact-format-uncovered`). None is declared here: the gate does not check `.mjs`/`.cjs`, so a sealed one cannot block a push, and refusing them would block workflow-script tests. Absent ⇒ no check.
- **`worktree-setup-command`**: `pnpm install --frozen-lockfile && pnpm build` — run once in a FRESH worktree (implement-phase story tree, review-phase detached review tree) before any gate: a new worktree has no `node_modules` and no `dist`, so `tsc` cannot resolve workspace packages (`@pair/content-ops`) and gates fail spuriously (#543). Never symlink another checkout's `node_modules`/`dist` instead. Absent ⇒ nothing run.
- **Gate & tooling code:** a gate's logic lives in a tested module in its owning package (white-box unit tests); scripts/CLIs are thin entrypoints and a root gate delegates (`pnpm --filter <pkg> <gate>`). Scripts are never unit-tested — CLI-level checks go to smoke tests. See ADL [2026-07-13-gate-tooling-code-in-tested-modules.md](../decision-log/2026-07-13-gate-tooling-code-in-tested-modules.md). **One bounded exception** (#419): a thin script whose behaviour IS the deliverable, with no logic to extract, is black-box executed from vitest against a throwaway fixture, asserting observable behaviour only — `scripts/format-lib/run-format.sh` and `scripts/regenerate-mirrors.sh`. Conditions, and why not the smoke suite: ADL [2026-09-01-publish-pr-realigns-mirrors-before-the-gate.md](../decision-log/2026-09-01-publish-pr-realigns-mirrors-before-the-gate.md). Gate/tooling packages are organized by bounded context, not one package per tool family — a new tool family sharing an existing package's bounded context is a new folder there, not a new package. See [ADR-014](adr/adr-014-tool-package-boundary-by-bounded-context.md).
- **Conformance tests** (`packages/knowledge-hub/src/conformance/`): one test file per target KB artifact (a `SKILL.md`, guideline, or template), not per introducing story — a new story extends the matching file's `describe` block. See ADL [2026-07-18-conformance-test-per-file-not-per-story.md](../decision-log/2026-07-18-conformance-test-per-file-not-per-story.md).
- **Monorepo tooling gotchas** (e.g. `pnpm --filter` bypassing turbo's `dependsOn` graph on a fresh checkout): documented once, in `DEVELOPMENT.md`'s `Turbo Caching` section — affected packages' READMEs carry only a short pointer. See ADL [2026-07-18-workspace-gotcha-doc-placement.md](../decision-log/2026-07-18-workspace-gotcha-doc-placement.md).

### Review Tier Matrix — overridable here

The per-tier requirements (reviewer count, SLA, checklist depth, whether 🔴 needs explicit approval) are **KB defaults**, resolved through the `Argument > Adoption > KB default` cascade. The defaults live in `quality-model.md` § \*Per-Tier Requirements`; this file is where a project changes them.

**No override in force**, and the defaults are deliberately not transcribed: since Adoption wins over KB default, a stale uncompared copy would silently override an improved default.

**To override**, add the keys you are changing — the shape the KB documents:

```yaml
# tier.red.reviewers: 2
# tier.red.sla_days: 3
```

**And then write the effective matrix here too**, as a table, so the values in force are visible where they are decided: identical means absent, different means written out.

The "Merge" column only bites when `Review enforcement` is `enabled` (above). Disabled — the default — the review runs and reports, and none of these requirements block a merge.
