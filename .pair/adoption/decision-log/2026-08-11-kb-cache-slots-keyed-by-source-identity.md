# Decision: a KB cache slot is keyed by SOURCE identity, never by CLI version alone

## Date

2026-08-11

## Status

Active

## Category

Convention Adoption

## Context

`~/.pair/kb/` is a **machine-wide** cache shared by every project. Keyed by CLI version alone (`~/.pair/kb/<cliVersion>/`), it assumed "one KB per machine"; `--source` contradicts that by design.

Reproduced in the review of #391 (story #395): `pair install --source <acme-kb.zip>` extracted the external KB **into the official KB's slot**. The project got the official `guidelines/`, `how-to/` and `getting-started.md` mixed with the external content, and `~/.pair/kb/<cliVersion>/manifest.json` became `{"name":"acme-kb","version":"1.0.0"}` — so `kb-info` in **every other project on the machine** reported the external KB. The damage outlives the command, with nothing connecting cause to effect.

`--url <remote zip>` wrote into the official slot too, guarded only by a backup/restore dance (`<slot>.bak`) — itself the admission the slot was being clobbered.

## Decision

**The cache slot is derived from the identity of the SOURCE. Two different sources can never share a slot, and the same source always resolves to the same slot.**

Layout:

```text
~/.pair/kb/<version>/                          official KB only
~/.pair/kb/external/url-<label>-<hash12>/      one slot per remote-URL source
~/.pair/kb/external/git-<hash12>/              one slot per git url#ref
~/.pair/kb/external/zip-<hash12>/              one slot per local-ZIP CONTENT
```

- Identity is `KBSource` in `apps/pair-cli/src/kb-manager/cache-slot-key.ts` — `official | remote | git | zip`. `cacheSlotKey()` is the single place a slot name is derived; `getSourceCachePath()` the single place a slot path is.
- **A local directory owns no slot and is not a `KBSource`.** `--source <dir>` is validated and installed **in place** — no copy, nothing to invalidate, edits picked up next install. Only forms that must be materialized (local ZIP, remote ZIP, git clone) need a slot. Encoded in the types (`LocalKBSource` classifies a path as `zip | directory`; only `zip` is a `KBSource`) — the previous wording claimed a `dir-<name>-<hash>/` slot no code ever created.
- The official KB keeps the bare version slot: existing caches stay valid, no re-download for the fix.
- The **git** slot reuses `gitCacheKey()` (`git-<sha256(url#ref)>`), now under `external/` — no second hashing scheme.
- **A local source's discriminator is the archive's CONTENT**: `zip-<sha256(bytes)[0..12]>` (`zip-source.ts`), no path label (that would re-smuggle the path into the identity). The same archive in two directories → ONE slot; two archives never share one. Enabled by `FileSystemService`'s byte-mode `readFileBytes` (text-mode-only reads made the path the first discriminator — see alternatives).
- **Only the remote-URL form keeps a readable label** (`url-acme-kb-<hash12>`), so `~/.pair/kb/external/` is inspectable without a lookup table. `git-<hash12>` and `zip-<hash12>` carry none; a slot's `manifest.json` names it when present.
- **A slot is populated ATOMICALLY: `populate` writes into `<slot>.tmp-<pid>-<n>` beside the slot, renamed into existence only when complete** (`cacheManager.writeSlotAtomically`, absorbed [#428](https://github.com/foomakers/pair/issues/428)). Every form (remote download, local ZIP, git clone) uses it: a concurrent reader sees the slot absent (⇒ re-fetch) or whole, and _replace wholesale_ comes from the swap, not delete-first. A failing `populate` removes its stage and rethrows the ORIGINAL error. Stages of DEAD processes are swept first (`process.kill(pid, 0)`); a LIVE process's stage is an install in flight and is left alone. Beside the slot = same filesystem, so the swap is one `rename`, not a cross-device copy.
- **A polluted slot is detected, not trusted** (#395 AC5). `inspectSlot()` compares `manifest.json` `name` with the expected name (`knowledge-base` for the official KB). On mismatch `ensureKBAvailable` (which calls `inspectSlot()` itself, so a plain `pair install` re-fetches) warns, replaces, re-fetches. `isKBCached()` is contamination-aware but a **diagnostic predicate**: its only production caller (`config/kb-resolver.ts`) uses it for a `[diag]` line, then calls `ensureKBAvailable` unconditionally; the code says so.
- **Only `name` is compared, never `version`** — AC's "name/version vs. the expected source" holds by construction: the official slot is _keyed_ by version, so a version mismatch inside `~/.pair/kb/0.4.3/` means a hand-edited cache, while the cross-KB case is a `name` mismatch. Comparing `version` adds a re-download with no defect behind it (a slot legitimately written by `0.4.3` and read by `0.4.3`).
- **An unreadable or nameless manifest is inconclusive, not foreign** — trusted. Pre-contract slots are common; deleting them would force re-downloads on no signal.
- **No manifest where one is expected is a half-written slot** — `empty`, re-fetched not served (an aborted extraction used to read as a hit with an empty KB path). `empty` deletes nothing: the slot is set aside and restored if the re-fetch fails.
- **A FETCHED slot is never deleted before its replacement is in hand.** `ensureKBAvailable` backs up (`<slot>.bak`), installs, drops the backup, restores on throw — so a failing re-fetch (offline, 5xx, proxy) of a contaminated official slot or a custom source leaves the cache the user had. **`installKBFromGit` does the same itself** (reached via `resolveDatasetRoot`, not `ensureKBAvailable`): it used to purge then clone, and `cloneGitRepo` deletes the destination on failure, so an offline clone left an empty slot. The set-aside gives git the empty destination it needs, replacing the purge. Scope: content over the network; local ZIP is the stated exception.
- **One classifier per question.** ZIP-vs-directory only in `localKBSource()` (case-insensitive), callers dispatch on `kind`; slot key and version normalization (`v0.2.0` → `0.2.0`) only in `cacheSlotKey()`, so `getCachedKBPath(key)` maps a key verbatim and rejects an empty one instead of resolving to the cache root. Two classifiers meant `--source /downloads/KB.ZIP` took a ZIP slot and the directory installer.
- **Pure derivation is separate from filesystem lifecycle**: `kb-manager/cache-slot-key.ts` (identity → key → path, no fs) vs `kb-manager/cache-manager.ts` (inspect, purge, backup/restore). The public surface is re-exported from `kb-manager/index.ts`; **no production module outside `kb-manager/` imports an internal module** — the three legacy deep imports (`kb-installer`, `git-clone`, `cli-options`) are gone. Tests import internals deliberately, to spy.
- **Slot mechanics never leave the module that owns slots.** Every form's lifecycle (purge → create → populate) sits behind a `kb-manager` entry point — `installKB`, `installKBFromLocalZip`, `installKBFromGit`; the config layer only dispatches. Git was briefly the exception (`kb-resolver` did `purgeSlot` → `ensureCacheDirectory` → `cloneGitRepo` → remove `.git`) — the duplicated-mechanics shape that caused the contamination. The barrel exports install entry points, never primitives (`getSourceCachePath`, `purgeSlot`, `ensureCacheDirectory`, `getCachedKBPath` are module-private).
- **The cache root honours `PAIR_KB_CACHE_DIR`** (documented in the configuration reference, previously read by no code), default `~/.pair/kb`, **validated, not trusted**: absolute, no `..` segments; a slot key may not contain `..` either. It prefixes every slot path and `purgeSlot` uses `rm -rf`, so `PAIR_KB_CACHE_DIR=.cache/kb` would make `pair install` create and recursively delete directories inside the current repo. Same reasoning as the empty-key guard.
- **Absolute is judged by the HOST convention for the cache ROOT, by EITHER convention for a SOURCE path.** For a source, accepting `C:\kb\acme.zip` _prevents_ a join onto the cwd; for the root, `join('C:\\cache\\kb', '0.4.3')` on POSIX yields the relative `C:\cache\kb/0.4.3`, reopening the hole. So `getCacheRoot` uses `path.isAbsolute`; only `resolveSourcePath` keeps the dual check.
- **The install dispatch is an exhaustive `switch` on `source.kind` with a `never` default**, like `cacheSlotKey`. The old "zip, else download" routed any other kind to the OFFICIAL release zip, written into that source's slot — a cross-source write with no signal. Unreachable then (`resolveSource` never produced `git`), but `KBSource` is a shared exported union: a new kind must be a type error.
- **A downloaded archive is unwrapped like a local one.** `installKB` (official download _and_ `--url <remote zip>`) calls `normalizeExtractedKB`, so a KB under a single root directory does not yield a root one level too high. Unwrap only: a negative result is not an error there (it never validated the download; making it fatal on the official download is a change with no defect). The local-ZIP path still throws — its caller can fix the archive.
- **Discarding the set-aside slot is BEST-EFFORT, outside the reverting `try`.** The post-install cleanup sat inside the block whose `catch` restores, so a failing `rm` of `<slot>.bak` deleted the freshly installed KB and reinstated the old slot (even the contaminated one AC5 had just replaced), reporting an unrelated fs error. Both call sites (`ensureKBAvailable`, `installKBFromGit`) discard after the `try/catch`; `removeBackupKB` swallows its failure (debug log) — a leftover `.bak` is inert, overwritten by the next `backupCachedKB`. It also passes `force: true` like every other `rm` here: its `existsSync` guard is check-then-act, and a concurrent same-source install (#428) can delete the `.bak` in between (ENOENT).
- **The `external` namespace is not a slot.** `getCachedKBPath` rejects a key naming the namespace directory, with the empty key and `..`: otherwise `purgeSlot` would `rm -rf` the parent of every external slot. Unreachable today (the official key is a semver) — defence-in-depth, because a partial guard set for the "one bad argument from `rm -rf`" class reads as complete. `EXTERNAL_NAMESPACE` stays module-private: no outside caller derives a slot path by hand.
- **The slot label is stripped after truncation, not only before.** Cutting at 32 characters can land on `-`/`.` (`zip-some-long-label--<hash>`), defeating recognizability. Uniqueness comes from the hash, never the label.
- **External slots are not inspected at all**, and the spec says so: `inspectSlot` returns `ready` early when the source declares no expected manifest name (every non-official source) — nothing to compare against, and `--source`/`--url` re-install into their slot regardless. The spec had stated the no-manifest re-fetch unconditionally; the code does it for the official slot only.
- **The staging file is keyed by the source too.** `installKB` stages at `<tmpdir>/kb-<version>-<hash12 of url>.zip` (`downloadStagingName`), since it serves the official release _and_ `--url <remote zip>`, which shared one staging path per version. `resume-manager.shouldResume()` resumes from the existence and SIZE of `<staging>.partial` alone, unbound to the URL, then sends `Range: bytes=<n>-` to the new url: interrupting an official download then `pair install --url https://acme…/kb.zip` at the same version appended acme's body to official bytes and finalized the hybrid (a failed install with a misleading error — the last place one source's bytes could reach another's install). Version stays for recognizability; the hash makes it unique.
- **The restore is rename-first, and best-effort by contract.** Round 4 moved the _discard_ out of the reverting `try`; the _restore_ needed the same, twice. (a) It renamed the backup back only after deleting the half-written slot, so a failing recursive delete (Windows antivirus/indexer) left both on disk, and the next `backupCachedKB` deleted that `.bak` — a second failure left the half-written slot and no backup, the opposite of the invariant above. `restoreCachedKB` now renames the backup in first and discards the superseded copy after (a leftover `.discarded-*` is inert). (b) It ran in the `catch`, so an EBUSY/EPERM replaced the actionable diagnosis ("Network error downloading KB… check connectivity", a 404 with the manual-download URL) with an fs message; it now swallows its failure like `removeBackupKB`. **A cleanup neither undoes nor speaks over the work it follows**; the rule lives in the function, so neither call site (`ensureKBAvailable`, `installKBFromGit`) nor a third needs its own try/catch. (c) Round 6: best-effort was **silent**. When the rename back throws, the slot was moved aside, so the only good copy sits at `<slot>.bak` behind an off-by-default `log.debug` — indistinguishable from loss. The give-up path is now a `log.warn` naming the kept copy and where to move it, reached only after the OLD order (delete whatever occupies the slot, retry the rename) was tried — delete and rename fail on different handles. The set-aside name adds a process-monotonic counter to the timestamp: `Date.now()` is millisecond-resolution, so two same-millisecond restores collided and both gave up.
- **A named source always reaches identity resolution — the monorepo shortcut is for the DEFAULT source only.** `getKnowledgeHubDatasetPathWithFallback` checked the monorepo dataset _before_ `customUrl`, so in a checkout `--url` silently resolved to the local dataset (no warning outside `PAIR_DIAG`), while `--source`/`--git` were honoured — contradicting the spec's precedence ("explicit user-provided source" first) and AC4 ("for ANY source form"). Side effect: `--url` is exercisable in a contributor checkout. Not a shipped regression (a released CLI has no monorepo dataset). Round 6 applied the rule to `config/bootstrap.ts`'s pre-flight (`shouldSkipKBDownload`); round 14 reverted it as a fix to dead code; round 17 revived the pre-flight (below) — so the rule holds at the resolver, the parsers (next clause) and the pre-flight. Round 19 made the third true: the hook read `thisCommand.opts()` (the PROGRAM's options), so `--source`, `--offline`, `--list-targets` (declared on the `install` SUBCOMMAND) were invisible and the bundled/network branch ran with a source named. It now reads the action command's options MERGED over the program's (round 19 first read the command's alone, leaving program-level `--url` invisible — see the double-download clause below) and returns before any fetch for any named source (`--source`, `--git`, `--url`, local or remote), `--offline` and `--list-targets`. The pre-flight only WARMS the cache; which KB a command installs is decided by `namedSource`.
- **`--url` is a source name, so it travels through the command config like `--source` — one channel, not two.** Round 12: program-level `--url` was read only by the pre-flight; parsers dispatched on `--source`, so `pair install --url <mirror>` produced `resolution: 'default'`. Survivable before by accident (the pre-flight wrote into `getCachedKBPath(version)`, the OFFICIAL slot, which default resolution served). With source keying the fetch lands in `external/url-<label>-<hash>/` and default goes to the official slot — the flag would name one KB, install another, and fail behind the firewall the mirror was for. Fix at the PARSER: `namedSource(options)` (`config/cli.ts`) returns `--source` or else program-level `--url`, and `install`, `update`, `kb-info` build config from it — `--url X` ≡ `--source X` (identity, slot, bytes), classified by the same code. Rejected: threading `customUrl` into `resolveDatasetRoot`'s `default` case — a second channel next to `config.resolution`. Precedence: `--source` wins (command-specific; `--url` applies to any subcommand). An empty `--source` passes through so "cannot be empty" fires; an empty `--url` is absent, matching the pre-flight's old `url && …` guard.
- **One filesystem location, one slot.** A source path is canonicalized before hashing (`.`/`..` collapsed, trailing separator stripped, under whichever convention called it absolute): `/kb/acme.zip`, `/kb/./acme.zip`, `/kb/../kb/acme.zip` share a slot; `--source /kb/` does not fork one. Distinct from path-vs-content below: here the _same path expression_ had to canonicalize.

## Alternatives Considered

- **Extract external ZIPs to a temp dir, leave keying alone** (the story's fallback): rejected — leaves `--url` and `--source <dir>` writing to the official slot; the defect is the keying.
- **Hash the ZIP's PATH instead of content** (this decision's first shape): superseded. Chosen because `FileSystemService.readFileSync` was text-mode (`utf-8`) and hashing a lossily decoded binary is no identity for a security-adjacent path. The API was fixed: `readFileBytes` (byte-mode, service and in-memory double) feeds the hash. Path-keying never merged two KBs; it spent one slot per copy.
- **Namespace by the manifest's `name@version`**: rejected — two unrelated KBs can declare both; the story lists it as an edge case.
- **Keep the backup/restore dance as the protection**: rejected — it protected the official slot only for one failing command; a successful external install still overwrote it. Under identity keying the dance protects **the source's own slot**.

## Consequences

- `install --source <zip>`, `--url` and git install into `~/.pair/kb/external/…`; `--source <dir>` installs in place, no cache. Only the official KB writes the official slot.
- `installKBFromLocalDirectory` was **removed**: its only caller `ensureKBAvailable` reached it only with a local-directory `customUrl`, which the parsers never produce (non-remote ⇒ `resolution: 'local'`) and `config/bootstrap.ts` short-circuits; it existed for its own tests. `ensureKBAvailable` now rejects a local directory explicitly, with a message naming `--source <dir>` (not internals) since `bootstrapEnvironment` prints it in `KnowledgeHubSetupError`; the layering note is in the JSDoc. Coverage (missing directory, invalid structure, relative path) already lived on `resolveLocalDataset`, the path users reach.
- **A contaminated machine self-heals** on the next install _of the same CLI version_, warning with both KB names. **Scope**: the official slot is version-keyed and the fix ships in a new version, so a slot polluted by an older CLI is abandoned under that version's directory, not discarded; AC5 (never serve foreign content) holds. Docs point to `~/.pair/kb/<old-version>/` for leftovers.
- **Disk**: one slot per distinct external source; since the discriminator is CONTENT (#429), one archive at two paths shares ONE slot. Slots are plain directories — `rm -rf ~/.pair/kb/external` is always safe. It does **not** cover four leftovers, all safe to delete by hand, named in the source-resolution spec, three reclaimable by `pair kb-cache prune`: `~/.pair/kb/<old-cli-version>/`, `~/.pair/kb/git-<hash>/` (pre-`external/` clones), `~/.pair/kb/<version>.bak` (interrupted installs; a stale one is cleared on the next backup) and `~/.pair/kb/<version>.discarded-*` (a full tree left when recovery could not delete the half-written slot; an external slot's `.discarded-*` falls inside the `external/` sweep, the official one's does not). **`pair kb-cache list` and `pair kb-cache prune`** (#427, absorbed): `list` reports each entry's size, manifest label and whether prune would take it; `prune` (`--dry-run`, `--json`) reclaims superseded official slots, pre-`external/` git clones, and abandoned stages/backups. **Prune NEVER removes**: (a) the running version's official slot — the next command's KB; (b) ANY `external/` slot — sources fetched from URLs/archives the CLI does not retain, unrecoverable, and nothing says which the user still wants; (c) anything `unknown` to the classifier — users touch this directory by hand; (d) with no resolvable current version, every official slot — comparing to an empty string would delete the slot about to be used; (e) **anything an install IN FLIGHT owns** — the cache is machine-wide; same predicate as `sweepOrphanedStages` (`isStageOwnerAlive`, exported via the barrel): a `<slot>.tmp-<pid>-<n>` stage is garbage only once its pid is dead. A `.bak` whose slot is ABSENT is the only copy of that KB; once the slot is back, prune takes it. Getting either wrong deletes what the never-delete-first invariant protects. **No automatic eviction (LRU/TTL)**: it needs its own policy and concurrency story, and growth tracks distinct KBs installed (single digits), not installs — re-installing reuses the slot. An explicit command fits a machine-wide directory: the user decides when, `--dry-run` shows what.
- **Same-source concurrency is safe via stage-and-swap** (#428, absorbed, not deferred). Not taken: a lock file — a stale lock blocks installs with no way to tell a crash from a live install; an abandoned stage is inert and swept by pid. Cross-source interference was already gone (no shared slot or staging file).
- **A local source's discriminator is content, not path** (#429, absorbed): the `FileSystemService` interface gained byte-mode `readFileBytes` — a `content-ops` change with its own tests.
- **A defect in a shared test double is fixed in the double.** `InMemoryFileSystemService.rename` of a directory registered `<dest>/` while `existsSync` matches exactly, so every `if (!existsSync(dest)) return` caller (`restoreCachedKB`, `removeBackupKB`) no-opped and the central safety assertion (a failing re-fetch leaves the cache intact) passed VACUOUSLY. Earlier rounds gave fixtures a direct-child `manifest.json` — invisible to the next test author. The double is fixed; a `cache-manager.test.ts` case with NO direct child pins it. Fallout measured: **zero** — full `pnpm turbo test` green. Rule: a test double is production code for the suite that trusts it; make it stop lying and measure.
- **The KB pre-flight (`bootstrapEnvironment`) is LIVE — revived here, after three rounds of documenting it as dead (rounds 12-18).** It never executed: `cli.ts`'s `preAction` hook guarded `if (thisCommand === prog) return`, and Commander calls a program-level hook as `callback(hookedCommand, actionCommand)` — `thisCommand` IS the program for every subcommand. Proven: with the parser fix reverted, `pair update --url <mirror>` issued ZERO HTTP requests. Rounds 14-15 recorded the deadness (code banners, `--no-kb` as a no-op in `--help`, the CLI reference and the contracts spec) and left revive / delete / retire `--no-kb` to the merge gate. **Round 17 revived it**; blast radius:
  - **The guard tests the ACTION command** (`actionCommand === prog` ⇒ no subcommand ⇒ skip). The Commander argument convention is pinned by a test, since a change would silently invert the fix.
  - **The exemption list became an ALLOW-list** (`commands/bootstrap-policy.ts`): only `install` and `update` resolve a KB in the pre-flight. Under the old deny-list (`package`, `scaffold-kb`) every new command inherited a network round-trip — pointless for local-state commands, a failure offline.
  - **`--no-kb` and the `--url` + `--no-kb` conflict became real.** `pair install --no-kb` no longer downloads. Round 19 completed it: the pre-flight's `kb === false` was ONE of two readers; the command resolved via `resolveDatasetRoot` -> `resolveDefaultDataset`, fetching whenever an httpClient existed — docs one round ahead of behaviour. `kb` is threaded into the resolver: `--no-kb` resolves from the bundled dataset or a populated slot, else FAILS naming the two ways out. `--url` with `--no-kb` is REJECTED by `validateCliOptions` (previously accepted and ignored) — a user-visible change with no defect behind it, stated in `--help`, the CLI reference callout and the contracts spec (all rewritten back from "inert"). A round-15 test PINNING the "no-op" help text was flipped: a pinned assertion outlives its condition.
  - **Pre-flight steps 2 and 3 must agree on ONE path.** The first revival aborted every RELEASED install: step 2 downloaded into `~/.pair/kb/<version>/`, step 3 re-derived the BUNDLED path via `getKnowledgeHubDatasetPath`, which THROWS in a published package (`@pair/knowledge-hub` hoisted next to `pair-cli`, `postbuild.js` bundles no dataset). Uncaught because every unit fixture seeds a monorepo dataset and smoke runs `dist` inside the monorepo, short-circuiting steps 2-3. `resolveDatasetForPreflight` RETURNS its path and the accessibility check takes it as an argument; a unit case with no bundled path covers the released shape, verified outside the repo (dist in a scratch package, `@pair/knowledge-hub` absent from a hoisted `node_modules`: "Unable to find @pair/knowledge-hub package" before, clean after). **Rule: a check that derives its own subject does not verify the operation it follows.** Corollary: a green suite says nothing about a released layout while every fixture is a checkout — a smoke test outside the monorepo would cover it, and today does not.
  - `shouldSkipKBDownload` and `hasLocalDataset` are folded into `resolveDatasetForPreflight` (same precedence: `--no-kb`, a local `--url`, the bundled dataset, the network); round 6's change, reverted in round 14, is moot. **A remote `--url` is fetched once — by the COMMAND, the pre-flight skipping it as a named source.** Round 19 recorded the opposite ("fetched once by the pre-flight and served from its slot to the command"), false in a released layout: `--url` is on the PROGRAM, so `actionCommand.opts()` lacked it, and `ensureKBAvailable` skips `inspectSlot` for ANY `customUrl` and re-installs — 2 full downloads per remote `install|update --url`, unseen because round 19's released-shape suite covered `--source`, `--offline`, `--list-targets`, `--no-kb` but not `--url`, and the older single-fetch assertion's fixture has a bundled monorepo dataset. **Rule: sharing a predicate across layers guarantees nothing unless they get the same INPUT** — the skip receives `namedSource`'s merged value (`cmdOptions.url ?? progOptions.url`). Consequently `validateCliOptions` moved ABOVE it in `runKbPreflight`: the `--url` + `--no-kb` rejection had fired only as a side effect of reaching `bootstrapEnvironment`'s step 1.
- `apps/pair-cli/src/kb-manager/cache-manager.ts` functions taking a `version` (`backupCachedKB`, `restoreCachedKB`, `removeBackupKB`) now take a `KBSource`. `getCachedKBPath(key)` maps a KEY verbatim (no normalization), throws on empty, and is exported by `cache-slot-key.ts` only — `cache-manager`'s default export had re-listed it (no production caller, one test call site), barrel bloat that blurred the module split.
- **Remote resolution in a monorepo checkout now downloads.** `resolveDatasetRoot({resolution:'remote', url})` no longer returns `packages/knowledge-hub/dataset`. Two tests asserting the old convenience ("resolves without network") now assert the URL is honoured; one (`commands/update/handler.test.ts`) asserted nothing about the URL, its spy on `getKnowledgeHubDatasetPathWithFallback` never intercepting an intra-module call.
- Local ZIP paths resolve against the **injected** cwd (`fs.currentWorkingDirectory()`), like directories, not `process.cwd()` — one relative path, one slot.
- The `scaffold-kb` smoke scenario's pinned #395 assertion (`assert_pinned_bug`) is now positive: it pre-seeds an official slot in an isolated `HOME` and fails if a ZIP install rewrites it or the external KB misses `external/`. The isolated `HOME` stays for test hygiene, not as a workaround.

- Local SOURCE paths are absolute under **either** convention (`posix.isAbsolute || win32.isAbsolute`), so `C:\kb\acme.zip` is not joined onto the cwd. The cache ROOT uses the host convention — see the decision clause.
- `OFFICIAL_KB_NAME` must byte-match the `--name` in `scripts/workflows/release/package-kb-dataset.sh`, or every official slot reads as contaminated; `apps/pair-cli/src/kb-manager/official-kb-name.test.ts` ties them. It lives in **pair-cli**, not `knowledge-hub`, where it could only regex `cache-slot-key.ts` as text (coupled to an app's layout, red on double quotes or a move); here it imports the constant, and text matching remains only for the shell script.
- `isKBCached` is probed **only under `PAIR_DIAG`**: it feeds only a `[diag]` line (`ensureKBAvailable` inspects regardless) and costs two `existsSync` + `readFile` + `JSON.parse` on every command reaching the fallback resolver. The `isKBCachedFn` seam stays; a test pins both halves (off ⇒ not called, on ⇒ called).

## Adoption Impact

- `.pair/adoption/tech/architecture.md` and the context map's glossary (`tech/boundedcontext/integration-process-standardization.md`) describe the cache as source-keyed; no other adoption record changes. An internal keying convention of the CLI's KB cache.
