# Decision: a KB cache slot is keyed by SOURCE identity, never by CLI version alone

## Date

2026-08-11

## Status

Active

## Category

Convention Adoption

## Context

`~/.pair/kb/` is a **machine-wide** cache shared by every project on the machine. It was keyed by CLI version alone (`~/.pair/kb/<cliVersion>/`), which encodes the assumption "one KB per machine". `--source` contradicts that assumption by design.

Reproduced during the review of #391 (story #395): `pair install --source <acme-kb.zip>` extracted the external KB **into the official KB's slot**. The consuming project received the official KB's `guidelines/`, `how-to/` and `getting-started.md` mixed with the external KB's content, and `~/.pair/kb/<cliVersion>/manifest.json` was rewritten to `{"name":"acme-kb","version":"1.0.0"}` — so `kb-info` in **every other project on the machine** then reported the external KB as the installed one. The damage outlives the command that causes it, and nothing connects cause to effect.

The same shape existed for `--url <remote zip>`: it wrote into the official slot too, guarded only by a backup/restore dance (`<slot>.bak`) whose existence is the admission that the slot was being clobbered.

## Decision

**The cache slot is derived from the identity of the SOURCE. Two different sources can never share a slot, and the same source always resolves to the same slot.**

Layout:

```text
~/.pair/kb/<version>/                          official KB only
~/.pair/kb/external/url-<label>-<hash12>/      one slot per remote-URL source
~/.pair/kb/external/git-<hash12>/              one slot per git url#ref
~/.pair/kb/external/zip-<hash12>/              one slot per local-ZIP CONTENT
```

- Identity is modelled as `KBSource` in `apps/pair-cli/src/kb-manager/cache-slot-key.ts` — `official | remote | git | zip`. `cacheSlotKey()` is the single place a slot name is derived; `getSourceCachePath()` the single place a slot path is.
- **A local directory owns no slot and is therefore not a `KBSource`.** `--source <dir>` is validated and installed from **in place** — no copy, nothing to invalidate, and edits to the directory are picked up by the next install. Only the forms that must be materialized before they can be read (local ZIP, remote ZIP, git clone) need a slot. This is encoded in the types (`LocalKBSource` classifies a `--source` path as `zip | directory`; only `zip` is a `KBSource`), not just documented — the previous wording claimed a `dir-<name>-<hash>/` slot that no code path ever created.
- The official KB keeps the bare version slot, so existing caches stay valid and no user re-downloads for the fix itself.
- The **git** slot reuses the pre-existing `gitCacheKey()` (`git-<sha256(url#ref)>`), now under `external/`, rather than introducing a second hashing scheme.
- **The discriminator for a local source is the archive's CONTENT**: `zip-<sha256(bytes)[0..12]>` (`zip-source.ts`), no path-derived label — a label would re-smuggle the path into the identity. The same archive copied to two directories lands on ONE slot, and two different archives can never share one — which is the property the whole decision is about, applied to the local form. It became available once `FileSystemService` grew a byte-mode `readFileBytes` (the earlier text-mode-only read is why the path was the discriminator first — see the alternatives below).
- **Only the remote-URL form keeps a human-readable label** (`url-acme-kb-<hash12>`), so a user inspecting `~/.pair/kb/external/` can tell what that slot is without a lookup table. `git` and `zip` slots carry no label — their identity is the url#ref or the content hash alone (`git-<hash12>`, `zip-<hash12>`); a slot's own `manifest.json` names it when one exists.
- **A slot is populated ATOMICALLY: `populate` writes into `<slot>.tmp-<pid>-<n>` beside the slot, and the slot is renamed into existence only when the stage is complete** (`cacheManager.writeSlotAtomically`, absorbed [#428](https://github.com/foomakers/pair/issues/428)). Every install form goes through it — remote download, local ZIP, git clone — so a concurrent reader sees the slot either absent (⇒ re-fetch) or whole, never half-written, and the _replace wholesale_ property comes from the swap instead of from a delete-first sequence. A failing `populate` removes its own stage and rethrows the ORIGINAL error: nothing new exists, nothing old was touched. Stages left by DEAD processes are swept before a new one is created (`process.kill(pid, 0)`); a LIVE process's stage is a concurrent install in flight, and deleting it would yank the tree out from under a running extraction. The stage sits beside the slot deliberately — same filesystem, so the swap is one `rename` and not a cross-device copy.
- **A polluted slot is detected, not trusted** (#395 AC5). `inspectSlot()` compares the slot's `manifest.json` `name` against the name the source is expected to carry (`knowledge-base` for the official KB). On mismatch, `ensureKBAvailable` warns, replaces and re-fetches — it calls `inspectSlot()` itself, which is what makes the re-fetch happen on a plain `pair install`. `isKBCached()` is contamination-aware for consistency, but it is a **diagnostic predicate**: its only production caller (`config/kb-resolver.ts`) uses it to decide whether to print a `[diag]` line and then calls `ensureKBAvailable` unconditionally. Nothing behavioural hangs off it, and the code says so.
- **Only `name` is compared, never `version`** — deliberate, and the AC's "name/version vs. the expected source" is satisfied by construction: the official slot is _keyed_ by the version, so a version mismatch inside `~/.pair/kb/0.4.3/` can only come from a hand-edited cache, while the cross-KB case the story exists to close is exactly a `name` mismatch. Comparing `version` would add a re-download path with no defect behind it (a slot legitimately written by `0.4.3` and read by `0.4.3`).
- **An unreadable or nameless manifest is inconclusive, not foreign** — the slot stays trusted. Slots predating the manifest contract are common; treating them as contaminated would delete user cache and force re-downloads for a signal that says nothing.
- **No manifest at all, where one is expected, is a half-written slot** — reported `empty`, so it is re-fetched rather than served (an aborted extraction used to read as a cache hit and yield an empty KB path). `empty` deletes nothing, so the argument above is untouched: the slot is set aside, and restored if the re-fetch fails.
- **A FETCHED slot is never deleted before its replacement is in hand.** `ensureKBAvailable` backs the slot up (`<slot>.bak`), installs, then drops the backup — and restores it when the install throws. This covers the contaminated official slot as much as a custom source: a failing re-fetch (offline, 5xx, proxy) must leave the user with the cache they had, not with none. **`installKBFromGit` does the same dance itself** (it is reached through `resolveDatasetRoot`, not through `ensureKBAvailable`): it used to purge and only then clone, and `cloneGitRepo` deletes the destination when git fails, so an offline clone left an empty slot where a working one had been. The set-aside also gives git the empty destination it requires, so it replaces the purge rather than adding to it. The scope of the invariant is exactly "content that comes over the network"; the local-ZIP path is the stated exception above.
- **One classifier per question.** ZIP-vs-directory is decided only in `localKBSource()` (case-insensitively) and every caller dispatches on the resulting `kind`; the slot key is derived only in `cacheSlotKey()`; version normalization (`v0.2.0` → `0.2.0`) happens only there too, so `getCachedKBPath(key)` maps a key verbatim and rejects an empty one instead of resolving to the cache root. Two classifiers meant `--source /downloads/KB.ZIP` took a ZIP slot and the directory installer.
- **Pure derivation is separated from filesystem lifecycle**: `kb-manager/cache-slot-key.ts` (identity → key → path, no fs) vs `kb-manager/cache-manager.ts` (inspect, purge, backup/restore). The public surface is re-exported from `kb-manager/index.ts` and **no production module outside `kb-manager/` imports one of its internal modules** — the three legacy deep imports (`kb-installer`, `git-clone`, `cli-options`) are gone. Test files still import internals directly, deliberately, to spy on them.
- **Slot mechanics never leave the module that owns slots.** Every source form's slot lifecycle (purge → create → populate) lives behind a `kb-manager` entry point — `installKB`, `installKBFromLocalZip`, `installKBFromGit` — and the config layer is a pure dispatcher. Git was briefly the exception (`kb-resolver` did `purgeSlot` → `ensureCacheDirectory` → `cloneGitRepo` → remove `.git`), which is precisely the shape — slot mechanics duplicated outside the owner — that produced the contamination this decision exists to fix. The barrel therefore exports install entry points, never slot primitives (`getSourceCachePath`, `purgeSlot`, `ensureCacheDirectory`, `getCachedKBPath` are module-private).
- **The cache root honours `PAIR_KB_CACHE_DIR`** (documented in the configuration reference, previously read by no code), defaulting to `~/.pair/kb`. The override is **validated, not trusted**: it must be absolute and free of `..` segments, and a slot key may not contain `..` either. This value prefixes every slot path and `purgeSlot` deletes a slot with `rm -rf` — `PAIR_KB_CACHE_DIR=.cache/kb` would otherwise make `pair install` create and recursively delete directories inside whatever repository it is run from. Same reasoning as the empty-key guard; leaving the root unchecked was the inconsistent half of it.
- **Absolute is judged by the HOST convention for the cache ROOT, by EITHER convention for a SOURCE path** — the two guards look alike and point opposite ways. For a source, accepting `C:\kb\acme.zip` as absolute _prevents_ a join onto the cwd. For the root, accepting it means `join('C:\\cache\\kb', '0.4.3')` on POSIX yields the relative `C:\cache\kb/0.4.3`, and every slot resolves against the process cwd again — the hole the guard exists to close, under a different spelling. So `getCacheRoot` uses `path.isAbsolute` and only `resolveSourcePath` keeps the dual check.
- **The install dispatch is an exhaustive `switch` on `source.kind` with a `never` default**, like `cacheSlotKey`. The earlier "zip, else download" shape routed any _other_ kind to the OFFICIAL KB's GitHub release zip, written into that source's slot — a cross-source write, the defect class this decision exists to close, with no compile-time or runtime signal. Unreachable at the time (`resolveSource` never produced `git`), but `KBSource` is a shared exported union: adding a kind must be a type error, not a silent official download.
- **A downloaded archive is unwrapped like a local one.** `installKB` (the official download _and_ `--url <remote zip>`) calls `normalizeExtractedKB`, so an external KB packaged under a single root directory does not yield a dataset root one level too high. Unwrap only: a negative result is not raised as an error on this path — it never validated the downloaded structure, and making a structure check fatal on the official download is a behaviour change with no defect behind it. The local-ZIP path still throws, because its caller handed us the archive and can fix it.
- **Discarding the set-aside slot is BEST-EFFORT, and happens outside the reverting `try`.** The cleanup that follows a successful install used to sit inside the block whose `catch` _restores_ the backup, so a failing `rm` of `<slot>.bak` deleted the KB that had just been installed correctly and reinstated the previous slot — including the contaminated one the AC5 self-heal had just replaced — while reporting an unrelated fs error. Both call sites (`ensureKBAvailable`, `installKBFromGit`) now discard after the `try/catch`, and `removeBackupKB` swallows its own failure (logging at debug): a leftover `.bak` is inert, because the next `backupCachedKB` overwrites it. `removeBackupKB` also passes `force: true` like every other `rm` in the module — its `existsSync` guard is check-then-act, and a concurrent same-source install (#428) can delete the `.bak` in between, turning the desired end state into an ENOENT throw.
- **The `external` namespace is not a slot.** `getCachedKBPath` rejects a key naming the namespace directory itself alongside the empty key and the `..` segment: `purgeSlot` would otherwise `rm -rf` the parent of every external slot on the machine. Unreachable today (the official key is a semver), so this is defence-in-depth — but the guard set is meant to cover the whole "one bad argument from `rm -rf`" class, and a partial guard set reads as a complete one. `EXTERNAL_NAMESPACE` stays module-private for the same reason the rest of the barrel is narrow: no caller outside derives a slot path by hand.
- **The slot label is stripped after truncation, not only before.** Cutting a long source name at 32 characters can land on a `-` or `.` and yield `zip-some-long-label--<hash>`, which defeats the label's only purpose (recognizing a slot in `~/.pair/kb/external/`). Uniqueness never depended on the label — it comes from the hash.
- **External slots are not inspected at all**, and the spec now says so: `inspectSlot` returns `ready` early whenever the source declares no expected manifest name, which is every non-official source. There is nothing to compare a foreign KB's manifest against, and `--source`/`--url` installs re-install into their own slot regardless of its content, so the check would have no consumer. The spec previously stated the no-manifest re-fetch unconditionally, which the code implements for the official slot only.
- **The staging file is keyed by the source too, not by CLI version alone.** `installKB` stages the download at `<tmpdir>/kb-<version>-<hash12 of url>.zip` (`downloadStagingName`), because that function serves the official release _and_ `--url <remote zip>`: at one CLI version two different sources shared one staging path. That is not merely a concurrency window — `resume-manager.shouldResume()` decides to resume from the existence and SIZE of `<staging>.partial` alone, with no binding to the URL that produced those bytes, and then issues `Range: bytes=<n>-` against the new url. Interrupting an official download and running `pair install --url https://acme…/kb.zip` at the same version appended the acme body onto the official KB's bytes and finalized the hybrid as one archive (a failed install with a misleading error, not a silent contamination — but the last place where one source's bytes could reach another source's install). The version stays in the name for recognizability; the hash is what makes it unique.
- **The restore is rename-first, and best-effort by contract.** Round 4 moved the backup _discard_ out of the reverting `try`; the _restore_ half needed the same rule, twice over. (a) It renamed the backup back only after deleting the half-written slot, so a failing recursive delete (the same Windows antivirus/indexer case) left both the `.bak` and the half-written slot on disk — and the next install's `backupCachedKB` deletes that `.bak` to make room, so a second failure left the user with the half-written slot and no backup: the exact opposite of the bolded invariant above. `restoreCachedKB` now renames the backup into place first and discards the superseded copy afterwards (a leftover `.discarded-*` directory is inert). (b) It ran inside the `catch`, so an EBUSY/EPERM there replaced the only actionable diagnosis the user had ("Network error downloading KB… check connectivity", a 404 carrying the manual-download URL) with an unrelated fs message. It now swallows its own failure rather than raising it, like `removeBackupKB` — at which level it speaks is (c) below: **a cleanup neither undoes nor speaks over the work it follows**, and because that rule lives inside the function, neither call site (`ensureKBAvailable`, `installKBFromGit`) needs a try/catch of its own — a third call site cannot get it wrong. (c) Round 6: best-effort was **silent**, which is a different failure from best-effort. When the rename back throws, the slot no longer exists — it was just moved aside — so the user's only good copy sits at `<slot>.bak` under a name nothing points at, with a `log.debug` line that is off by default: from the user's side that is indistinguishable from having lost the cache. The give-up path is now a `log.warn` naming the kept copy and the path to move it back to, and it is reached only after the OLD order (delete whatever occupies the slot, then retry the rename) has been tried — a recursive delete and a rename fail on different handles, so the retry is not a repeat of the same attempt. The set-aside name also carries a process-monotonic counter next to the timestamp: `Date.now()` alone is millisecond-resolution, so two restores of one source in the same millisecond collided on the rename and both took the give-up path.
- **A named source always reaches identity resolution — the monorepo shortcut is for the DEFAULT source only.** `getKnowledgeHubDatasetPathWithFallback` consulted the monorepo dataset _before_ `customUrl`, so in a development checkout `--url` silently resolved to the local dataset: no warning, no diagnostic outside `PAIR_DIAG`. `--source` and `--git` were honoured in a checkout; `--url` was the odd one out, and it contradicted both the spec's own precedence order ("explicit user-provided source" first) and AC4 ("for ANY source form"). Ignoring what a user typed is the same class of surprise as writing their KB into someone else's slot. Side effect worth having: the `--url` path is now exercisable in a contributor's checkout instead of only in a released binary. Not a regression that shipped — a released CLI has no monorepo dataset — but the dev-only behaviour is what kept the path under-exercised. Round 6 applied the same rule to `config/bootstrap.ts`'s pre-flight (`shouldSkipKBDownload`), which runs one layer further out; round 14 reverted that as a fix to dead code, and round 17 then revived the pre-flight (see below) — so the rule now holds at all three layers by construction: at the resolver, at the parsers (next clause), and in the pre-flight. Round 19 is what actually made the third layer true: the revived hook read `thisCommand.opts()` — the PROGRAM's option set — so `--source`, `--offline` and `--list-targets`, all declared on the `install` SUBCOMMAND, were invisible to it and the bundled/network branch was reached even when a source WAS named. It now consults the action command's options too and returns before any fetch for any named source (`--source`, `--git`, local `--url`), for `--offline`, and for `--list-targets`. What the pre-flight decides is narrower than it looks: it WARMS the cache, while which KB a command installs is decided by `namedSource`.
- **`--url` is a source name, so it travels through the command config like `--source` does — one channel, not two.** Round 12: the program-level `--url` was consumed only by `config/bootstrap.ts`'s pre-flight; the subcommand parsers dispatched on `--source` alone, so `pair install --url <mirror>` produced `resolution: 'default'`. Before this story that was survivable by accident — the pre-flight wrote the custom archive into `getCachedKBPath(version)`, the OFFICIAL slot, and default resolution then served it. Source-identity keying ends the accident by design: the fetch lands in `external/url-<label>-<hash>/` and default resolution goes to the official slot, so the flag would name one KB and install another, and fail outright behind the firewall the mirror existed for. The fix is at the PARSER, not at the resolver: `namedSource(options)` (`config/cli.ts`) returns the command's `--source` or, absent it, the program-level `--url`, and `install`, `update` and `kb-info` build their config from that one value. So `--url X` and `--source X` are the same command — same identity, same slot, same bytes — and a git/local/remote `--url` is classified by the code that already classifies `--source`. The alternative (thread a `customUrl` option down the dispatcher into `resolveDatasetRoot`'s `default` case) was rejected: it would re-introduce a second channel for "which source is in play" next to `config.resolution`, which is the ambiguity this whole decision removes. Precedence: `--source` wins where both are given — it is the command-specific flag, while `--url` applies to whichever subcommand runs. An empty `--source` is passed through so its "cannot be empty" validation still fires; an empty `--url` is treated as absent, matching the `url && …` guard the pre-flight used before it went dead.
- **One filesystem location, one slot.** A source path is canonicalized before it is hashed (`.`/`..` segments collapsed, trailing separator stripped, with the rules of whichever convention called it absolute), so `/kb/acme.zip`, `/kb/./acme.zip` and `/kb/../kb/acme.zip` share one slot and `--source /kb/` does not fork a second one. Distinct from the path-vs-content trade-off below: there the same bytes at two paths stay two slots on purpose; here the _same path expression_ simply had to canonicalize.

## Alternatives Considered

- **Extract external ZIPs to a temp dir, leave keying alone** (the story's fallback phrasing): rejected. It fixes the ZIP form and leaves `--url` and `--source <dir>` writing to the official slot; the defect is the keying, not the ZIP.
- **Hash the ZIP's PATH instead of its content** (the first shape of this decision): superseded. It was chosen because the only read API was `FileSystemService.readFileSync`, which is text-mode (`utf-8`), and hashing a lossily decoded binary is not an identity worth defending in a security-adjacent path. The blocker was the API, not the idea, so the API was fixed: `readFileBytes` (byte-mode, in the service and in its in-memory double) now feeds the hash. Path-keying was never wrong — it never merged two KBs — it just spent one slot per copy of the same archive.
- **Namespace by the manifest's declared `name@version`**: rejected. Two unrelated KBs can declare the same name and version, which is exactly the collision this decision exists to prevent; the story lists it as an edge case.
- **Keep the backup/restore dance as the protection**: rejected. It protects the official slot only for the duration of one command and only when the install fails; a successful external install still overwrote it. With identity keying the dance now protects **the source's own slot**, which is what it was always trying to express.

## Consequences

- `install --source <zip>`, `--url` and git sources install into `~/.pair/kb/external/…`; `--source <dir>` installs in place and touches no cache. The official slot is written only by the official KB.
- `installKBFromLocalDirectory` was **removed**, not kept as a spare: `ensureKBAvailable` was its only caller, reachable only with a local-directory `customUrl` — a combination the install/update parsers never produce (a non-remote source parses to `resolution: 'local'`) and `config/bootstrap.ts` short-circuits. It existed only for its own tests. `ensureKBAvailable` now rejects a local directory explicitly, so the two layers cannot silently disagree about where a directory KB lives. The message is written for the person who typed the flag — it names `--source <dir>`, not the internal functions — because `bootstrapEnvironment` wraps it in `KnowledgeHubSetupError` and prints it; the layering note stays in the JSDoc, where the reader who needs it is. Its coverage (missing directory, invalid structure, relative path) already lived on `resolveLocalDataset`, which is the code users actually reach.
- **A machine already contaminated self-heals** on the next install _of the same CLI version_: the foreign slot is detected, replaced and re-downloaded, with a warning naming both KBs. **Scope, stated honestly**: the official slot is keyed by CLI version, and this fix ships in a new version — a slot polluted by an older CLI lives under that older version's directory, which the fixed CLI never reads again. It is abandoned, not discarded; AC5's outcome (never serve foreign content) holds either way. The docs point users at `~/.pair/kb/<old-version>/` for the leftovers.
- **Disk**: one slot per distinct external source — and, since the discriminator became the archive's CONTENT (#429, below), the same archive copied to two paths shares ONE slot. Slots are plain directories with no hidden state — `rm -rf ~/.pair/kb/external` is always safe and the next install re-populates. That command does **not** cover four leftovers, all safe to delete by hand, named in the source-resolution spec, and three of the four reclaimable with `pair kb-cache prune` (next clause): `~/.pair/kb/<old-cli-version>/`, `~/.pair/kb/git-<hash>/` (git clones from before the `external/` namespace), `~/.pair/kb/<version>.bak` (interrupted installs — a stale one is now cleared automatically on the next backup) and `~/.pair/kb/<version>.discarded-*` (a full KB tree left behind when a recovery could not delete the half-written slot; an external slot's own `.discarded-*` falls inside the `external/` sweep, the official slot's does not). **`pair kb-cache list` and `pair kb-cache prune` make the cache inspectable and reclaimable** (#427, absorbed): `list` reports every entry with its size, its manifest label and whether prune would take it; `prune` (with `--dry-run` and `--json`) reclaims three of the four leftovers above — superseded official slots, pre-`external/` git clones, and abandoned stages/backups. **What prune NEVER removes, and why**: (a) the running CLI version's official slot — it is the KB the next command reads; (b) EVERY `external/` slot — one per source the user chose, fetched from a URL or an archive the CLI does not retain, so a wrong deletion is not recoverable by re-running an install, and nothing on disk says which sources they still care about; (c) anything the classifier does not recognise (`unknown`), because a cleanup command in a directory users also touch by hand must not delete what it cannot name; (d) with no current version resolvable, every official slot — comparing names against an empty string would delete the slot about to be used, which is the one deletion that turns a cleanup into an outage; (e) **anything an install IN FLIGHT owns** — the cache is machine-wide, so prune in one project runs while another project's install is mid-extraction in the same directory. That last one is the same question `sweepOrphanedStages` asks, so it is the same predicate (`isStageOwnerAlive`, exported through the barrel): a `<slot>.tmp-<pid>-<n>` stage is garbage only once its pid is dead. A `.bak` needs its own evidence — its slot's ABSENCE means the set-aside has not been undone yet, so that backup is the only copy of that KB; once the slot is back the backup is redundant and prune takes it. Getting either wrong deletes exactly what the bolded never-delete-first invariant above exists to protect. **Automatic eviction (LRU/TTL) is still deliberately not implemented**: it needs a policy and a concurrency story of its own, and the growth here is proportional to the number of KBs a user actually installs (single digits), not to installs over time — re-installing the same source reuses its slot. An explicit command is the honest shape for a machine-wide directory: the user decides when, and `--dry-run` shows what.
- **Same-source concurrency is now safe, by the stage-and-swap clause above** (#428, absorbed into this story instead of deferred). The route not taken is a lock file: a stale lock leaves a user unable to install with no way to tell a crash from a live install, whereas an abandoned stage is inert and swept by pid. Cross-source interference was already gone by construction (no shared slot, no shared staging file).
- **The discriminator for a local source is its content, not its path** (#429, absorbed): the same archive copied to two directories occupies ONE slot. The `FileSystemService` interface gained a byte-mode `readFileBytes` for it — a `content-ops` change, shipped with its own tests, that the text-mode-only read had made impossible.
- **A defect in a shared test double is fixed in the double, not worked around in the fixture.** `InMemoryFileSystemService.rename` of a directory registered the destination as `<dest>/` while `existsSync` matches exactly, so the destination was observable only when a moved file landed DIRECTLY under it — and every `if (!existsSync(dest)) return` caller (`restoreCachedKB`, `removeBackupKB`) silently no-opped, making the story's central safety assertion (a failing re-fetch leaves the cache intact) pass VACUOUSLY. Earlier rounds worked around it by giving fixtures a direct-child `manifest.json`; that convention is invisible to the next test author, so the next such test proves nothing again. The double is now correct, and a `cache-manager.test.ts` case whose fixture has NO direct child pins the behaviour. Deferring it was reconsidered because the fallout of fixing a monorepo-wide double is unknowable without measuring it — measured, it is **zero**: the full `pnpm turbo test` is green, so no other suite was passing _because_ a renamed directory read as absent. Rule this generalizes: a test double is production code for the suite that trusts it; when it lies, the correct move is to make it stop lying and measure, not to teach fixtures its lie.
- **The KB pre-flight (`bootstrapEnvironment`) is LIVE — revived here, after three rounds of documenting it as dead (rounds 12-18).** It had never executed: `cli.ts`'s `preAction` hook guarded with `if (thisCommand === prog) return`, and Commander invokes a program-level hook as `callback(hookedCommand, actionCommand)` — `thisCommand` IS the program for every subcommand, so the guard always fired. Proven, not read: with the parser fix reverted, `pair update --url <mirror>` issued ZERO HTTP requests. Rounds 14-15 chose to record the deadness rather than fix it (banners in code, `--no-kb` documented as a no-op in `--help`, the CLI reference and the contracts spec) and left the choice — revive / delete / retire `--no-kb` with it — to the merge gate. **Round 17 revived it**, so this ADL now records what ships, not that open question. Three things came with the revival, and they are the whole blast radius:
  - **The guard tests the ACTION command** (`actionCommand === prog` ⇒ no subcommand matched ⇒ skip). The Commander argument convention itself is pinned by a test, because if it ever changed the fix would silently invert.
  - **The command exemption list was inverted to an ALLOW-list** (`commands/bootstrap-policy.ts`): only `install` and `update` resolve a KB in the pre-flight. With the previous deny-list (`package`, `scaffold-kb`) every command added tomorrow would inherit a network round-trip by simply not being remembered there — pointless for a command that reads local state, and an outright failure for anyone offline.
  - **`--no-kb` and the `--url` + `--no-kb` conflict became real.** `pair install --no-kb` no longer downloads a KB (which is what the flag always promised). Round 19 completed that: the pre-flight honouring `kb === false` was only ONE of the two readers, and the command path resolved its dataset independently through `resolveDatasetRoot` -> `resolveDefaultDataset`, which fetched whenever an httpClient was present. So the flag skipped the warm fetch and the command downloaded anyway — the documentation shipped one round ahead of the behaviour. `kb` is now threaded into the resolver, where `--no-kb` resolves from the bundled dataset or an already-populated cache slot and otherwise FAILS with the two ways out, instead of fetching what the user just refused, and `--url` together with `--no-kb` is now REJECTED by `validateCliOptions` where it was previously accepted and ignored. That second one is a user-visible behaviour change with no defect behind it — it is the flag combination becoming coherent — so it is stated in `--help`, the CLI reference callout and the contracts spec, all three of which had been rewritten to call the flag inert and are now rewritten back. A round-15 test that PINNED the "no-op" help text was flipped: a pinned assertion outlives the condition it was written for, and this one had started locking the wrong promise in.
  - **Steps 2 and 3 of the pre-flight must agree on ONE path.** The first revival shipped with them disagreeing and it aborted every RELEASED install: step 2 downloaded the KB into `~/.pair/kb/<version>/`, then step 3 re-derived a path from `getKnowledgeHubDatasetPath` — the BUNDLED dataset — which THROWS in a published package (`@pair/knowledge-hub` is hoisted next to `pair-cli`, never nested under it, and `postbuild.js` bundles no dataset). Nothing caught it: every unit fixture seeds a monorepo dataset and the smoke suite runs `dist` from inside the monorepo, so in both the bundled path exists and steps 2-3 are short-circuited. `resolveDatasetForPreflight` now RETURNS the path it resolved and the accessibility check takes it as an argument; a unit case with no resolvable bundled path covers the released shape, and it was verified empirically outside the repo (dist copied into a scratch package with `@pair/knowledge-hub` absent from a hoisted `node_modules`: "Unable to find @pair/knowledge-hub package" before, clean run after). **Rule this generalizes: a check that derives its own subject does not verify the operation it follows.** Corollary for this repo: a green suite says nothing about a released layout while every fixture is a checkout — which is what a smoke test outside the monorepo would cover, and today does not.
  - `shouldSkipKBDownload` and `hasLocalDataset` are gone, folded into `resolveDatasetForPreflight` (same order of precedence: `--no-kb`, a local `--url`, the bundled dataset, the network). Round 6's change to `shouldSkipKBDownload` — reverted in round 14 as a fix to dead code — is therefore moot rather than reinstated: the pre-flight only WARMS the cache now, while which KB a command installs is decided by `namedSource` at the parsers (clause above). A remote `--url` is fetched once by the pre-flight and served from its slot to the command, not fetched twice.
- `apps/pair-cli/src/kb-manager/cache-manager.ts` functions that took a `version` string (`backupCachedKB`, `restoreCachedKB`, `removeBackupKB`) now take a `KBSource`. `getCachedKBPath(key)` survives as the key→path mapper — but takes a KEY verbatim now (no version normalization) and throws on an empty one. It is exported by `cache-slot-key.ts` only: `cache-manager`'s default export listed it too, a symbol that module merely imports, with no production caller and one test call site — the same surface bloat the barrel rule forbids, and it blurred the module split (a reader saw the path mapper offered by the lifecycle module).
- **Remote resolution in a monorepo checkout now downloads.** `resolveDatasetRoot({resolution:'remote', url})` no longer returns `packages/knowledge-hub/dataset`. Two tests asserted the old behaviour as a convenience ("resolves without network") and now assert the URL is honoured; one of them (`commands/update/handler.test.ts`) had been passing while asserting nothing about the URL at all, because its spy on `getKnowledgeHubDatasetPathWithFallback` never intercepted an intra-module call.
- Local ZIP paths now resolve against the **injected** cwd (`fs.currentWorkingDirectory()`), like local directory paths already did, instead of `process.cwd()`. Two resolutions of the same relative path must not produce two slots.
- The `scaffold-kb` smoke scenario's pinned assertion for #395 (`assert_pinned_bug`) is flipped to a positive assertion: it pre-seeds an official slot in an isolated `HOME` and fails if a ZIP install rewrites it, or if the external KB does not land under `external/`. The isolated `HOME` stays, for a different reason than before — test hygiene, not a workaround.

- Local SOURCE paths are classified absolute under **either** convention (`posix.isAbsolute || win32.isAbsolute`), so a Windows path (`C:\kb\acme.zip`) is no longer joined onto the cwd into a bogus slot. The cache ROOT is judged by the host convention instead, for the opposite reason — see the decision clause.
- `OFFICIAL_KB_NAME` must byte-match the `--name` the release script passes (`scripts/workflows/release/package-kb-dataset.sh`), or every official slot reads as contaminated. A conformance test (`apps/pair-cli/src/kb-manager/official-kb-name.test.ts`) ties the two artifacts together. It lives in **pair-cli**, not in `knowledge-hub`: from there it could only read `cache-slot-key.ts` as text and regex the constant out — a package's suite coupled to an app's file layout, red on a semantically identical edit (double quotes, a move). Next to the code it imports the constant; text matching survives only for the shell script, which has no importable form.
- `isKBCached` is probed **only under `PAIR_DIAG`**. Its result feeds a `[diag]` line and nothing else — `ensureKBAvailable` inspects the slot itself and runs either way — while the probe now costs two `existsSync` + `readFile` + `JSON.parse` on the hot path of every command that reaches the fallback resolver. The injectable `isKBCachedFn` seam stays, and a test pins both halves (not called with diagnostics off, called with them on).
