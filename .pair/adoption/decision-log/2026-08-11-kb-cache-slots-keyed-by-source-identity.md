# Decision: a KB cache slot is keyed by SOURCE identity, never by CLI version alone

## Date

2026-08-11

## Status

Active

## Category

Convention Adoption

## Context

`~/.pair/kb/` is a **machine-wide** cache shared by every project on the machine. It was keyed by CLI version alone (`~/.pair/kb/<cliVersion>/`), which encodes the assumption "one KB per machine". `--source` contradicts that assumption by design.

Reproduced during the review of #391 (story #395): `pair install --source <acme-kb.zip>` extracted the external KB **into the official KB's slot**. The consuming project received the official KB's `guidelines/`, `how-to/` and `getting-started.md` mixed with the external KB's content, and `~/.pair/kb/<cliVersion>/manifest.json` was rewritten to `{"name":"acme-kb","version":"1.0.0"}` — so `kb-info` in **every other project on the machine** then reported the external KB as the installed one. The damage outlives the command that causes it, and nothing connects cause to effect.

The same shape existed for `--url <remote zip>`: it wrote into the official slot too, guarded only by a backup/restore dance (`<slot>.bak`) whose existence is the admission that the slot was being clobbered.

## Decision

**The cache slot is derived from the identity of the SOURCE. Two different sources can never share a slot, and the same source always resolves to the same slot.**

Layout:

```text
~/.pair/kb/<version>/                          official KB only
~/.pair/kb/external/<kind>-<label>-<hash12>/   one slot per external source that owns one
```

- Identity is modelled as `KBSource` in `apps/pair-cli/src/kb-manager/cache-slot-key.ts` — `official | remote | git | zip`. `cacheSlotKey()` is the single place a slot name is derived; `getSourceCachePath()` the single place a slot path is.
- **A local directory owns no slot and is therefore not a `KBSource`.** `--source <dir>` is validated and installed from **in place** — no copy, nothing to invalidate, and edits to the directory are picked up by the next install. Only the forms that must be materialized before they can be read (local ZIP, remote ZIP, git clone) need a slot. This is encoded in the types (`LocalKBSource` classifies a `--source` path as `zip | directory`; only `zip` is a `KBSource`), not just documented — the previous wording claimed a `dir-<name>-<hash>/` slot that no code path ever created.
- The official KB keeps the bare version slot, so existing caches stay valid and no user re-downloads for the fix itself.
- The **git** slot reuses the pre-existing `gitCacheKey()` (`git-<sha256(url#ref)>`), now under `external/`, rather than introducing a second hashing scheme.
- **The discriminator for a local source is its resolved path**, not its content: `zip-<basename>-<sha256(path)[0..12]>`. See the alternatives below for why not content.
- Slot names keep a human-readable label (`zip-acme-kb-1.0.0-8ae362dc47aa`) so a user inspecting `~/.pair/kb/external/` can tell what a slot is without a lookup table.
- **A local ZIP install replaces its slot wholesale** (`purgeSlot` then extract). Extracting over an existing slot merges two KBs — that is the same class of defect one level down. This is the *only* install form that deletes before it writes, and the exception is deliberate: the source is a local file the user still has, so re-running the command is the recovery. Every form whose content comes over the network sets the slot aside instead (see the backup clause below).
- **A polluted slot is detected, not trusted** (#395 AC5). `inspectSlot()` compares the slot's `manifest.json` `name` against the name the source is expected to carry (`knowledge-base` for the official KB). On mismatch, `ensureKBAvailable` warns, replaces and re-fetches — it calls `inspectSlot()` itself, which is what makes the re-fetch happen on a plain `pair install`. `isKBCached()` is contamination-aware for consistency, but it is a **diagnostic predicate**: its only production caller (`config/kb-resolver.ts`) uses it to decide whether to print a `[diag]` line and then calls `ensureKBAvailable` unconditionally. Nothing behavioural hangs off it, and the code says so.
- **Only `name` is compared, never `version`** — deliberate, and the AC's "name/version vs. the expected source" is satisfied by construction: the official slot is *keyed* by the version, so a version mismatch inside `~/.pair/kb/0.4.3/` can only come from a hand-edited cache, while the cross-KB case the story exists to close is exactly a `name` mismatch. Comparing `version` would add a re-download path with no defect behind it (a slot legitimately written by `0.4.3` and read by `0.4.3`).
- **An unreadable or nameless manifest is inconclusive, not foreign** — the slot stays trusted. Slots predating the manifest contract are common; treating them as contaminated would delete user cache and force re-downloads for a signal that says nothing.
- **No manifest at all, where one is expected, is a half-written slot** — reported `empty`, so it is re-fetched rather than served (an aborted extraction used to read as a cache hit and yield an empty KB path). `empty` deletes nothing, so the argument above is untouched: the slot is set aside, and restored if the re-fetch fails.
- **A FETCHED slot is never deleted before its replacement is in hand.** `ensureKBAvailable` backs the slot up (`<slot>.bak`), installs, then drops the backup — and restores it when the install throws. This covers the contaminated official slot as much as a custom source: a failing re-fetch (offline, 5xx, proxy) must leave the user with the cache they had, not with none. **`installKBFromGit` does the same dance itself** (it is reached through `resolveDatasetRoot`, not through `ensureKBAvailable`): it used to purge and only then clone, and `cloneGitRepo` deletes the destination when git fails, so an offline clone left an empty slot where a working one had been. The set-aside also gives git the empty destination it requires, so it replaces the purge rather than adding to it. The scope of the invariant is exactly "content that comes over the network"; the local-ZIP path is the stated exception above.
- **One classifier per question.** ZIP-vs-directory is decided only in `localKBSource()` (case-insensitively) and every caller dispatches on the resulting `kind`; the slot key is derived only in `cacheSlotKey()`; version normalization (`v0.2.0` → `0.2.0`) happens only there too, so `getCachedKBPath(key)` maps a key verbatim and rejects an empty one instead of resolving to the cache root. Two classifiers meant `--source /downloads/KB.ZIP` took a ZIP slot and the directory installer.
- **Pure derivation is separated from filesystem lifecycle**: `kb-manager/cache-slot-key.ts` (identity → key → path, no fs) vs `kb-manager/cache-manager.ts` (inspect, purge, backup/restore). The public surface is re-exported from `kb-manager/index.ts` and **no production module outside `kb-manager/` imports one of its internal modules** — the three legacy deep imports (`kb-installer`, `git-clone`, `cli-options`) are gone. Test files still import internals directly, deliberately, to spy on them.
- **Slot mechanics never leave the module that owns slots.** Every source form's slot lifecycle (purge → create → populate) lives behind a `kb-manager` entry point — `installKB`, `installKBFromLocalZip`, `installKBFromGit` — and the config layer is a pure dispatcher. Git was briefly the exception (`kb-resolver` did `purgeSlot` → `ensureCacheDirectory` → `cloneGitRepo` → remove `.git`), which is precisely the shape — slot mechanics duplicated outside the owner — that produced the contamination this decision exists to fix. The barrel therefore exports install entry points, never slot primitives (`getSourceCachePath`, `purgeSlot`, `ensureCacheDirectory`, `getCachedKBPath` are module-private).
- **The cache root honours `PAIR_KB_CACHE_DIR`** (documented in the configuration reference, previously read by no code), defaulting to `~/.pair/kb`. The override is **validated, not trusted**: it must be absolute and free of `..` segments, and a slot key may not contain `..` either. This value prefixes every slot path and `purgeSlot` deletes a slot with `rm -rf` — `PAIR_KB_CACHE_DIR=.cache/kb` would otherwise make `pair install` create and recursively delete directories inside whatever repository it is run from. Same reasoning as the empty-key guard; leaving the root unchecked was the inconsistent half of it.
- **Absolute is judged by the HOST convention for the cache ROOT, by EITHER convention for a SOURCE path** — the two guards look alike and point opposite ways. For a source, accepting `C:\kb\acme.zip` as absolute *prevents* a join onto the cwd. For the root, accepting it means `join('C:\\cache\\kb', '0.4.3')` on POSIX yields the relative `C:\cache\kb/0.4.3`, and every slot resolves against the process cwd again — the hole the guard exists to close, under a different spelling. So `getCacheRoot` uses `path.isAbsolute` and only `resolveSourcePath` keeps the dual check.
- **The install dispatch is an exhaustive `switch` on `source.kind` with a `never` default**, like `cacheSlotKey`. The earlier "zip, else download" shape routed any *other* kind to the OFFICIAL KB's GitHub release zip, written into that source's slot — a cross-source write, the defect class this decision exists to close, with no compile-time or runtime signal. Unreachable at the time (`resolveSource` never produced `git`), but `KBSource` is a shared exported union: adding a kind must be a type error, not a silent official download.
- **A downloaded archive is unwrapped like a local one.** `installKB` (the official download *and* `--url <remote zip>`) calls `normalizeExtractedKB`, so an external KB packaged under a single root directory does not yield a dataset root one level too high. Unwrap only: a negative result is not raised as an error on this path — it never validated the downloaded structure, and making a structure check fatal on the official download is a behaviour change with no defect behind it. The local-ZIP path still throws, because its caller handed us the archive and can fix it.
- **Discarding the set-aside slot is BEST-EFFORT, and happens outside the reverting `try`.** The cleanup that follows a successful install used to sit inside the block whose `catch` *restores* the backup, so a failing `rm` of `<slot>.bak` deleted the KB that had just been installed correctly and reinstated the previous slot — including the contaminated one the AC5 self-heal had just replaced — while reporting an unrelated fs error. Both call sites (`ensureKBAvailable`, `installKBFromGit`) now discard after the `try/catch`, and `removeBackupKB` swallows its own failure (logging at debug): a leftover `.bak` is inert, because the next `backupCachedKB` overwrites it. `removeBackupKB` also passes `force: true` like every other `rm` in the module — its `existsSync` guard is check-then-act, and a concurrent same-source install (#428) can delete the `.bak` in between, turning the desired end state into an ENOENT throw.
- **The `external` namespace is not a slot.** `getCachedKBPath` rejects a key naming the namespace directory itself alongside the empty key and the `..` segment: `purgeSlot` would otherwise `rm -rf` the parent of every external slot on the machine. Unreachable today (the official key is a semver), so this is defence-in-depth — but the guard set is meant to cover the whole "one bad argument from `rm -rf`" class, and a partial guard set reads as a complete one. `EXTERNAL_NAMESPACE` stays module-private for the same reason the rest of the barrel is narrow: no caller outside derives a slot path by hand.
- **The slot label is stripped after truncation, not only before.** Cutting a long source name at 32 characters can land on a `-` or `.` and yield `zip-some-long-label--<hash>`, which defeats the label's only purpose (recognizing a slot in `~/.pair/kb/external/`). Uniqueness never depended on the label — it comes from the hash.
- **External slots are not inspected at all**, and the spec now says so: `inspectSlot` returns `ready` early whenever the source declares no expected manifest name, which is every non-official source. There is nothing to compare a foreign KB's manifest against, and `--source`/`--url` installs re-install into their own slot regardless of its content, so the check would have no consumer. The spec previously stated the no-manifest re-fetch unconditionally, which the code implements for the official slot only.
- **One filesystem location, one slot.** A source path is canonicalized before it is hashed (`.`/`..` segments collapsed, trailing separator stripped, with the rules of whichever convention called it absolute), so `/kb/acme.zip`, `/kb/./acme.zip` and `/kb/../kb/acme.zip` share one slot and `--source /kb/` does not fork a second one. Distinct from the path-vs-content trade-off below: there the same bytes at two paths stay two slots on purpose; here the *same path expression* simply had to canonicalize.

## Alternatives Considered

- **Extract external ZIPs to a temp dir, leave keying alone** (the story's fallback phrasing): rejected. It fixes the ZIP form and leaves `--url` and `--source <dir>` writing to the official slot; the defect is the keying, not the ZIP.
- **Hash the ZIP's CONTENT as the discriminator** (so the same archive at two paths shares a slot): rejected for now. The hash would be computed through `FileSystemService.readFileSync`, which is text-mode (`utf-8`) — hashing a lossily decoded binary is not an identity we want to defend in a security-adjacent path, and the alternative (a second, byte-mode read API) is a `content-ops` interface change out of scope here. Cost of the path-based key: the same archive copied to two directories occupies two slots. Bounded, visible, and harmless — it never merges two KBs, which is the property that matters.
- **Namespace by the manifest's declared `name@version`**: rejected. Two unrelated KBs can declare the same name and version, which is exactly the collision this decision exists to prevent; the story lists it as an edge case.
- **Keep the backup/restore dance as the protection**: rejected. It protects the official slot only for the duration of one command and only when the install fails; a successful external install still overwrote it. With identity keying the dance now protects **the source's own slot**, which is what it was always trying to express.

## Consequences

- `install --source <zip>`, `--url` and git sources install into `~/.pair/kb/external/…`; `--source <dir>` installs in place and touches no cache. The official slot is written only by the official KB.
- `installKBFromLocalDirectory` was **removed**, not kept as a spare: `ensureKBAvailable` was its only caller, reachable only with a local-directory `customUrl` — a combination the install/update parsers never produce (a non-remote source parses to `resolution: 'local'`) and `config/bootstrap.ts` short-circuits. It existed only for its own tests. `ensureKBAvailable` now rejects a local directory explicitly, so the two layers cannot silently disagree about where a directory KB lives. The message is written for the person who typed the flag — it names `--source <dir>`, not the internal functions — because `bootstrapEnvironment` wraps it in `KnowledgeHubSetupError` and prints it; the layering note stays in the JSDoc, where the reader who needs it is. Its coverage (missing directory, invalid structure, relative path) already lived on `resolveLocalDataset`, which is the code users actually reach.
- **A machine already contaminated self-heals** on the next install *of the same CLI version*: the foreign slot is detected, replaced and re-downloaded, with a warning naming both KBs. **Scope, stated honestly**: the official slot is keyed by CLI version, and this fix ships in a new version — a slot polluted by an older CLI lives under that older version's directory, which the fixed CLI never reads again. It is abandoned, not discarded; AC5's outcome (never serve foreign content) holds either way. The docs point users at `~/.pair/kb/<old-version>/` for the leftovers.
- **Disk**: one slot per distinct external source, plus one per distinct path of the same archive. Slots are plain directories with no hidden state — `rm -rf ~/.pair/kb/external` is always safe and the next install re-populates. That command does **not** cover three leftovers, all safe to delete by hand and named in the source-resolution spec: `~/.pair/kb/<old-cli-version>/`, `~/.pair/kb/git-<hash>/` (git clones from before the `external/` namespace) and `~/.pair/kb/<version>.bak` (interrupted installs — a stale one is now cleared automatically on the next backup). **Automatic eviction is deliberately not implemented**: an LRU/TTL over a shared cache needs a policy and a concurrency story of its own, and the growth here is proportional to the number of KBs a user actually installs (single digits), not to installs over time (re-installing the same source reuses its slot). Tracked as [#427](https://github.com/foomakers/pair/issues/427).
- **Concurrency is unchanged and still not safe for the same source** — stated, not solved. Two projects installing the **same** source at the same moment can interleave `purgeSlot` + extract in one shared directory and one of them can read a half-written slot. Cross-source interference, which was the realistic case (project A installing an external KB while project B reads the official one), is gone by construction: they no longer share a directory. Making same-source installs atomic requires a lock file or extract-to-temp + atomic swap, which is a separate change with its own failure modes (stale locks, cross-device renames); deliberately deferred rather than half-done here. Tracked as [#428](https://github.com/foomakers/pair/issues/428).
- **The path-not-content discriminator for local sources** (same archive at two paths ⇒ two slots) is tracked as [#429](https://github.com/foomakers/pair/issues/429).
- `apps/pair-cli/src/kb-manager/cache-manager.ts` functions that took a `version` string (`backupCachedKB`, `restoreCachedKB`, `removeBackupKB`) now take a `KBSource`. `getCachedKBPath(key)` survives as the key→path mapper — but takes a KEY verbatim now (no version normalization) and throws on an empty one.
- Local ZIP paths now resolve against the **injected** cwd (`fs.currentWorkingDirectory()`), like local directory paths already did, instead of `process.cwd()`. Two resolutions of the same relative path must not produce two slots.
- The `scaffold-kb` smoke scenario's pinned assertion for #395 (`assert_pinned_bug`) is flipped to a positive assertion: it pre-seeds an official slot in an isolated `HOME` and fails if a ZIP install rewrites it, or if the external KB does not land under `external/`. The isolated `HOME` stays, for a different reason than before — test hygiene, not a workaround.

- Local SOURCE paths are classified absolute under **either** convention (`posix.isAbsolute || win32.isAbsolute`), so a Windows path (`C:\kb\acme.zip`) is no longer joined onto the cwd into a bogus slot. The cache ROOT is judged by the host convention instead, for the opposite reason — see the decision clause.
- `OFFICIAL_KB_NAME` must byte-match the `--name` the release script passes (`scripts/workflows/release/package-kb-dataset.sh`), or every official slot reads as contaminated. A conformance test (`apps/pair-cli/src/kb-manager/official-kb-name.test.ts`) ties the two artifacts together. It lives in **pair-cli**, not in `knowledge-hub`: from there it could only read `cache-slot-key.ts` as text and regex the constant out — a package's suite coupled to an app's file layout, red on a semantically identical edit (double quotes, a move). Next to the code it imports the constant; text matching survives only for the shell script, which has no importable form.
- `isKBCached` is probed **only under `PAIR_DIAG`**. Its result feeds a `[diag]` line and nothing else — `ensureKBAvailable` inspects the slot itself and runs either way — while the probe now costs two `existsSync` + `readFile` + `JSON.parse` on the hot path of every command that reaches the fallback resolver. The injectable `isKBCachedFn` seam stays, and a test pins both halves (not called with diagnostics off, called with them on).

## Adoption Impact

- `.pair/adoption/tech/architecture.md` and the context map's glossary (`tech/boundedcontext/integration-process-standardization.md`) both describe the cache as source-keyed; no other adoption record changes. This is an internal keying convention of the CLI's KB cache.
