# Decision: no write is assumed — every write a skill makes is re-read back

## Date

2026-08-11

## Status

Active

## Category

Convention Adoption

## Context

[2026-07-31-pm-adapter-visibility-contract.md](2026-07-31-pm-adapter-visibility-contract.md) closed the adapter half of item visibility and explicitly deferred the skill half to #403: `$assignee` in the write contract, membership-precedes-state as a precondition, and a HALT on an unresolvable item — tool-agnostic, never a tool-shaped step.

While refining #403 (2026-08-04) the deferred half produced new evidence that changes what the fix has to be. Adding four cards to the board by hand reproduced the defect:

- `gh project item-add` **exited 0 and created nothing** on the first attempt for #413; `item-list` did not find the item. A second, identical invocation created it. Reproduced three times across the session.
- Every board write therefore had to be **membership → a read that confirms it → state**, in that order, with the read as the load-bearing beat.

So ordering the calls correctly is *not sufficient*. `/pair-capability-write-issue` Step 7 could add the membership before the state write, in the right order, following the adapter exactly — and still write the state field on an item that does not exist, because the add reported success. The same shape appeared on the code-host side: PRs #404, #405, #406 and #408 were published with no assignee, and #406 without its story's `risk:*` labels, all reported as successful publishes.

## Decision

**Any operation whose exit status can be 0 with no effect is verified by a read, and a skill reports what the read observed — never what the call returned.** A write that cannot be confirmed by a read is a failure or a finding, never a silent success.

Concretely:

1. The rule is stated **once, as an invariant**, in `/pair-capability-write-issue` Step 7 (the skill that owns item writes) and applied verbatim by `/pair-capability-publish-pr` (the skill that owns PR writes). Both are guarded by `packages/knowledge-hub/src/conformance/verified-writes-contract.test.ts`.
2. **Membership precedes state** is the ordering half, stated tool-agnostically in `/pair-capability-write-issue` Step 7b as three beats — membership, a read that confirms it, the state field — with all per-tool mechanics referenced out to the adapters (the constraint the 2026-07-31 ADL put on this story). An unconfirmable membership **HALTs with the specific reason**; a skipped board write is never reported as success.
3. **An unassigned item is a warning, not a blocker.** The assignee cascade (`$assignee` → adoption `default-assignee` → none) never HALTs: the failure mode is invisibility, and refusing to file the item is worse than filing it unassigned. The rejected-assignee case takes the same branch — reported, never silently dropped.
4. **The default assignee comes from a declared adoption key** (`default-assignee`, schema in `skill-conventions/way-of-working-pm-resolution.md` § *Assignee resolution*), never from the authenticated user: an agent under a bot token would assign every item to the bot and pass its own check.
5. **The cascade has one code-host branch**: a PR write resolves `code-host-assignee` first and `default-assignee` second, an item write resolves `default-assignee` only. Declared in the same section, applied by `/pair-capability-publish-pr`. Without the branch the key was a schema field no skill resolved — and a split project's PR would be assigned the PM tool's login, rejected by the host, and published unassigned.
6. **An update never reassigns an item away from its current assignee.** The resolved assignee is written on an update only when the caller passed `$assignee` explicitly or the item has none; otherwise the existing one stands. Add-vs-replace semantics stay the adapter's (only GitHub's `--add-assignee` adds; Linear, Azure and `filesystem` replace), so the skill states *which value and when*, never *how*.
7. **The D4 skip is expressed by resolving no target at all**, never by the writer softening its HALT: once a macrostate is requested, an unmappable one can only HALT (route (c)). Where the caller **composes** the item writer — `/pair-process-refine-story`, which passes `$status` and renders a full body in the same call — resolving no target means **omitting `$status`**, and omitting it is the caller's job, not the writer's. `/pair-capability-publish-pr` does **not** compose it (decision 11): it resolves `## State Mapping` itself and **writes no state field at all** when no board state maps to `Review` — membership is still established and confirmed, only the state beats are skipped — which is this project's own case. There is no `$status` parameter on the direct path to omit.
8. **Membership does not depend on `$status`.** `/pair-capability-write-issue` Step 7b runs its membership beats (check → add → confirm by read) on **every write-mode write** where the adoption names a tracked view — always on a create, equally on an update (decision 15 states the scope and why) — and writes the state field only when Step 6 resolved one. Gating membership behind a requested transition left the most common path uncovered — an item filed with no `$status` (a planned task, a promoted tech-debt finding) is an issue and not a board item on an explicit-membership tool, i.e. open, assigned, green and off the board: #384/#372 verbatim. The `Board:` output row therefore reports **membership and state separately** (`member of <view> — confirmed by read; no state written (no $status)`), because a row that could only say "state" or `n-a` renders an on-board item as absent.
9. **The PR update path is conditional exactly as the item update path is** (decision 6, applied to the code-host side): on an existing PR the resolved assignee is written only when `$assignee` was passed explicitly or the read shows no assignee; otherwise the existing one stands, and none is never cleared. "One rule, two callers" governs the **update semantics** as well as the resolution — otherwise the documented fix→re-publish loop silently pulls a PR reassigned to the reviewer back to `default-assignee`, the same invisibility inverted.
10. **The read-back invariant is universal inside these two skills, not scoped to the item/PR body.** The comment post (Step 7c) is confirmed by reading the item's comments back — a post that cannot be confirmed reports `Comment warned`, never `Commented` — and `/pair-capability-publish-pr` Phase 5 reads back both the `pair-review` status and the `pr-state:*` label it applies. A claimed-but-absent required check is worse than declared advisory enforcement, and a claimed-but-absent label is a report about a view that does not exist.
11. **Every declared key has a writer as well as a reader.** `/pair-capability-setup-pm` Step 4 now asks for the default assignee and writes `## Assignment` (plus `code-host-assignee` when it has just declared a split `code-host`), so the key the cascade reads is populated by the tool that populates the rest of that file — otherwise the warn-and-write-unassigned branch is the out-of-the-box outcome for every new adopter. `/pair-process-implement` Step 0.1b, which writes the PM tool directly on every story, resolves the assignee through the cascade (never the authenticated user, never a reassignment) and applies the membership → confirm → state order **by reference**; composing `/pair-capability-write-issue` is not available to it, because write mode is a full-body overwrite and a state-only change must not re-render the story body.
12. **No adapter count is stated anywhere.** The rule is "one rule stated here, every mechanic in its adapter" — a number goes stale the moment a tracker is added, and the PM-tool README already rejects asserting one.
13. **The document the skills defer to is part of the contract surface, and so is this record.** `canonical-states.md` is where `/pair-capability-write-issue` Step 6 and Step 7b send an agent to resolve a state, so its `## Integration with Skills` table is not commentary: it told the reader that `/pair-process-implement` (`In Progress`/`Review`) and `/pair-process-review` (`Done` on merge) write "through `/pair-capability-write-issue`", i.e. exactly the write-mode route decisions 7 and 11 forbid for a state-only change. Both rows now say **writes the board field directly, applying Step 7b by reference**; the `/pair-process-refine-story` row keeps its composition, because it passes `$status` **and** renders a full body in the same call. The guard therefore probes the KB authority (both corpora) and this ADL alongside the skills — a decision record that describes a design which never shipped is the same "one rule, two statements" divergence in the highest-authority file.

14. **The tool adapter is the last document before the command, so it is part of the contract surface too.** `github-implementation.md`'s `#### Common Transitions` table still routed `Refined → In Progress` through the item writer in write mode (`via /pair-capability-write-issue $status: In Progress`) — the route decisions 7, 11 and 13 forbid for a **state-only** change, in the file `/pair-process-implement` Step 0.1b sends an agent to for the actual call. That row now reads **writes the board field directly**, applying Step 7b **by reference** and pointing at the status mutation documented two headings above it. The `Todo → Refined` row is deliberately **unchanged** — refinement passes `$status` and renders a full body in the same call — and the guard pins it positively, so a future sweep that flattens every row to "direct" is caught as its own defect rather than passing as a fix.
15. **Membership is scoped to every write-mode write, not to creates.** Step 7b's beats were originally **scoped to creates**, which reproduces the defect one door down: `/pair-process-refine-story` writes `Draft → Ready` on a story that **already exists** and may never have been added to the tracked view, and an update with **no** `$status` is precisely the repair path for an item found off the board (#384/#372). The membership beats (1 to 4) therefore run on **every write-mode write** when the adoption names a tracked view — always on a create (an issue is not a board item yet) and equally on an update — whether or not a board state was requested; the state-field beats (5 to 6) stay gated on Step 6. Step 7's **update** bullet says so where an agent following that path actually reads, not only in Step 7b's preamble.
16. **On the merge path, `Done` is two writes — and a KB claim is asserted against the file that executes it.** Decision 13 made `canonical-states.md` say `/pair-process-review` "writes the board field directly" on merge, while the file that runs it (`merge-and-cascade.md` Step 6.4) only closed the issue and its parents: no board field, no membership → confirming read → state order, no read-back in its Verify. Closing an issue is **not** a board transition — the item keeps its column — so a story reported `Done` sat in `In Progress` on the board, and the two merge paths (`/pair-process-implement`'s `post-review-merge.md` Step 4.4 was already corrected) had diverged. Step 6.4 now states the two writes explicitly, applies Step 7b by reference for the story and each parent it transitions, and verifies by a **read** of each. The guard's new probe reads the KB row **and** the executing file in one assertion: whichever of the two changes, the other must follow.
17. **A step that documents two mechanisms for one write must state the read on both.** `/pair-capability-publish-pr` Phase 4 step 5 posts the back-link either by composing `$mode: comment` (confirmed by that skill's Step 7c read, degrading to `Comment warned`) or, when the item writer is **not installed**, by writing the comment directly through the PM tool's implementation guide — and that second branch declared no read at all, so decision 10's "universal inside these two skills" held for one of the two paths on the same line. The uncovered branch is the one that runs where the back-link is the **only** link from the board to the PR (a split-tool project, the sole configuration where the step does anything), so a comment API exiting 0 with no effect rendered `Cross-link: … PR URL posted on <item>` over a board that reaches nothing. The direct branch now carries the same read in the same words (`read the item's comments back` — the `## Activity Log` section on `filesystem`) and reports `back-link failed — manual link needed`, never `posted`; the Graceful Degradation bullet and the Composed Skills row say the same, and the guard asserts **both** branches of the step in one scoped probe.

## Alternatives Considered

- **Fix the ordering only (membership before state), no read-back**: Rejected by the observed evidence. The bug reproduced *with* correct ordering, because the add itself lied. The ordering fix closes one instance; the read closes the class.
- **Retry blindly instead of reading**: Rejected. A retry without a read cannot distinguish "the first call worked" from "neither worked" — it only changes the odds. The retry is kept, but as a response to a *negative read*, not as a substitute for one.
- **Put the read-back in the adapters, next to the mechanics**: Rejected. Every adapter would carry a copy of one rule, and the rule is about what a skill may *claim*, not about how a tool is called. The mechanics stay per-tool; the claim discipline is single-sourced in the skill.
- **A distinct `$verify` flag callers can turn off**: Rejected. An unverified write is exactly the behavior being removed; making it opt-out re-creates the defect behind a parameter.
- **Scope the "every write" wording down to the paths that already read back** (the honest alternative to extending it — decision 10): Rejected. The two uncovered paths are cheap to cover (one read each) and one of them is the required check that blocks the merge; narrowing the claim would leave the corpus stating a weaker rule than it can afford to keep.
- **Leave `/pair-process-implement` Step 0.1b to a follow-up story** and disclose the hole here (decision 11): Rejected. The contradiction runs on *every* story, in the one skill that always runs, and the fix is two bullets pointing at rules this PR already states. A disclosed defect that reproduces daily is not a smaller change than the pointer that removes it.
- **Treat an unassigned item as a HALT** (symmetry with the membership HALT): Rejected. The two failures are not equivalent — an item off the board has nowhere for a state field to go, while an unassigned item is written and merely under-visible. A HALT there would trade a warning for lost work.

## Consequences

- Every board write now costs at least one extra read, and a publish costs one PR read. Deliberate: the alternative price was items that look green and are not on the board.
- `/pair-capability-write-issue` gains a HALT (`membership could not be confirmed`) that did not exist before. It fires only where a board is present and membership is impossible — never on a project that simply has no board (the D4 minimal-board path stays a documented skip, and Step 6 now separates the two outcomes explicitly, because the pre-existing HALT for an unmappable `$status` was being read as covering both).
- Output shapes changed on both skills (`Labels`, `Assignee` and `Board` rows on the item write; `Assignee` and a read-confirmed `Tags` row on the publish), so both carry a minor version bump.
- On this project's board no column maps to `Review`, so every `/pair-capability-publish-pr` run takes the documented skip and reports `Board: n-a — no Review state on this board`. That is the intended outcome of decision 7, not a degraded publish: readiness is carried by the PR.
- A future skill that writes to a tracker inherits the rule by pointing at it — the invariant is prose in one skill plus a conformance guard, not a shared code path. That is the accepted limit of this decision: it binds the corpus, not a runtime. The **existing** direct writers are not left to inherit it later: decision 11 brings `/pair-process-implement` Step 0.1b under the rule, and the same by-reference pointer is applied to its `post-review-merge` Step 4.4 (story + parent epic + parent initiative — three state writes nobody re-runs, so a state reported without a read is terminal) and to `/pair-capability-publish-pr` step 7, which the maintainer resolved on 2026-08-12 to write the board state directly rather than by composing write mode, because it contradicted decision 4 on every story it ran (assign to "the current developer" is exactly the authenticated-user default the cascade forbids).
- **A rule about a composition has two files to keep, and the guard must read both.** Decision 11 was applied to `/pair-capability-publish-pr` and left the *composed* skill's own Composition Interface still describing the board write as "the second composition (default write mode)" — the route this decision classifies as body-destroying — because the negative probes ran on the publisher's file only. The corrected contract is therefore asserted on **both** corpora at once (`[...writeIssueCases, ...publishPrCases]`), and the publisher's Graceful Degradation section is asserted as its own scoped section: a degradation list that still said "not installed ⇒ skip the board-state update" would have re-created #384/#372 on every project that does not install the item writer, which is the configuration the list exists to serve. Rule of thumb this leaves behind: when a decision removes a composition, the losing shape must be probed in the caller **and** in the callee, never in whichever file the diff happened to touch last.
- **Two files were not enough either: the losing shape also lives where the skills defer, and in this record** (decision 13). With the caller and the callee corrected, the write-mode route survived one more round in `canonical-states.md`'s integration table and in decision 7 of this ADL — both outside the probe set, which read skill corpora plus the resolution convention. Extended rule of thumb: **the corpus of a contract is every file that states it** — the callers, the KB document they defer to, and the decision record that governs them. All four are now in the guard, so a divergence has nowhere left to sit.
- **A decision that widens an earlier one must edit that earlier one, not sit next to it.** Decision 15 widened membership from creates to every write-mode write and shipped it in Step 7b, but decision 8 — the item *titled* "Membership does not depend on `$status`", eight lines earlier in the same list — still stated the create-only scoping decision 15 exists to remove, so the record read as the narrower rule at the exact place a maintainer looks first. The append was not enough; decision 8 is corrected **in place** (as decision 7 was), decision 15's history no longer quotes the losing wording verbatim, and the guard pins the pair positively **and** negatively, plus a whole-section sweep so the create-only shape cannot move to a neighbouring item. Rule of thumb: **a decision list is a single statement of the rule — widening one item means rewriting every item that states the old scope.**
- Every create on an explicit-membership tool now costs a membership read (and, when absent, an add plus a confirming read) even when no state is requested. Deliberate, and the reason the story exists: the alternative price is the most common item shape — filed, assigned, green, off the board.
- `/pair-capability-setup-pm` gains a question and a write, so a bootstrap conversation is one exchange longer. Declining is supported and costs only the declared consequence (items and PRs filed unassigned), which the skill must state in so many words rather than proceeding silently.
- **Four files were not the bottom either — the chain ends at the adapter and at the executor** (decisions 14 to 16). With the two skills, the convention, the KB authority and this record corrected, the losing route survived in the **tool adapter** (the last document read before a command is typed) and, newly introduced by decision 13 itself, as a KB claim **no executing file carried**. The rule of thumb closes here: a claim is probed **where it is stated and where it is executed** — a KB row asserted on its own is a promise, not a contract. Concretely, the guard now also reads every PM-tool adapter guide (a class probe over all four, so the next tracker's guide cannot be written by copying the old table) and both merge paths.
- **A fallback is a mechanism, not a footnote** (decision 17). Rounds 3 to 6 walked the rule across *files*; this one found it missing across *branches of a single step* — the composed path read back, the "not installed" fallback did not, ten lines apart. Rule of thumb: **an invariant binds every mechanism a step documents for the same write, and the guard reads them together** — a probe scoped to the step (not to a sentence) that asserts each branch names its own confirming read, so the primary path cannot go on covering for the degraded one.
- Every merged story now costs one extra board write plus one read per transitioned item (story, and each parent the cascade closes). Deliberate and cheap where it matters most: nobody re-runs the merge phase, so an unread state there is terminal.
- A project whose board has no `Done` column is unaffected: the merge step reports the documented no-state outcome — closed item, no state written — never a state it did not write.
- **Open for the human merge gate:** AC6 on #403 was amended *during* this PR's review to state both outcomes (documented skip vs HALT) after the shipped contract had already split them. The split is argued in decision 7 and is consistent with `canonical-states.md` route (c), which this work leaves untouched (only that file's `## Integration with Skills` table changed — decision 13) — but the record moved to match the implementation, so the amendment wants an explicit endorsement at the merge gate rather than a silent one.

## Adoption Impact

- [way-of-working.md](../tech/way-of-working.md): gains a `## Assignment` section declaring `default-assignee` — the machine-readable half of the Assignment rule that had been prose-only since 2026-07-30.
- [way-of-working-pm-resolution.md](../../knowledge/guidelines/technical-standards/ai-development/skill-conventions/way-of-working-pm-resolution.md): owns the `Assignee resolution` schema and cascade, beside `code-host` / `base-branch`, plus the routing-table row that sends the item assignee to the PM tool and the PR assignee to the code host.
- `/pair-capability-setup-pm` is the **writer** of `## Assignment` (decision 11), the same way it already owns the PM section and backfills `## Git Workflow` — so the key is populated by the setup path, not only documented in the shipped template.
- [canonical-states.md](../../knowledge/guidelines/collaboration/project-management-tool/canonical-states.md) (both corpora): its `## Integration with Skills` table now distinguishes the caller that **composes** the item writer (refinement) from the two that **write the board field directly** and apply Step 7b by reference (decision 13). Nothing in the macrostate model, the Reading/Writing rules or route (c) changed.
- [github-implementation.md](../../knowledge/guidelines/collaboration/project-management-tool/github-implementation.md) (both corpora): the `Common Transitions` table's `Refined → In Progress` row is the direct board write (decision 14); `Todo → Refined` and `In Progress → Done` are untouched. The status-field mutation it points at, and every other mechanic in the guide, are unchanged — this is a routing correction, not a mechanics one.
- `/pair-process-review`'s `merge-and-cascade.md` Step 6.4 (decision 16): closes the item **and** writes its board state under the membership → confirming read → state order, verifying by a read of the story and of each parent transitioned — the same shape `/pair-process-implement`'s `post-review-merge.md` Step 4.4 already carried. Both skills take a minor version bump (`/pair-capability-write-issue` 0.9.0, `/pair-process-review` 0.6.0).
- No dataset mirror of this file: sibling ADLs in `adoption/decision-log/` are adoption-only records — the dataset is a curated seed, not an auto-mirror of adoption. It **is** read by the conformance guard (decision 13), which is why it must describe the shipped contract rather than an intermediate draft.
