# Decision: no write is assumed — every write a skill makes is re-read back

## Date

2026-08-11

## Status

Active

## Category

Convention Adoption

## Context

[2026-07-31-pm-adapter-visibility-contract.md](2026-07-31-pm-adapter-visibility-contract.md) closed the adapter half of item visibility and deferred the skill half to #403: `$assignee` in the write contract, membership-precedes-state as a precondition, a HALT on an unresolvable item — tool-agnostic, never a tool-shaped step.

Refining #403 (2026-08-04), adding four cards to the board by hand reproduced the defect: `gh project item-add` **exited 0 and created nothing** on the first attempt for #413 (`item-list` did not find it); a second, identical invocation created it. Reproduced three times. Every board write therefore had to be **membership → a read that confirms it → state**, with the read as the load-bearing beat.

So correct ordering is *not sufficient*: `/pair-capability-write-issue` Step 7 could follow the adapter exactly and still write the state field on an item that does not exist, because the add reported success. Same shape on the code host: PRs #404, #405, #406 and #408 were published with no assignee, and #406 without its story's `risk:*` labels, all reported as successful.

## Decision

**Any operation whose exit status can be 0 with no effect is verified by a read, and a skill reports what the read observed — never what the call returned.** A write a read cannot confirm is a failure or a finding, never a silent success.

1. The rule is stated **once, as an invariant**, in `/pair-capability-write-issue` Step 7 (owner of item writes) and applied verbatim by `/pair-capability-publish-pr` (owner of PR writes). Both guarded by `packages/knowledge-hub/src/conformance/verified-writes-contract.test.ts`.
2. **Membership precedes state** is the ordering half, stated tool-agnostically in `/pair-capability-write-issue` Step 7b as three beats — membership, a read that confirms it, the state field — with per-tool mechanics referenced out to the adapters (the 2026-07-31 ADL's constraint). An unconfirmable membership **HALTs with the specific reason**; a skipped board write is never reported as success.
3. **An unassigned item is a warning, not a blocker.** The assignee cascade (`$assignee` → adoption `default-assignee` → none) never HALTs: refusing to file is worse than filing unassigned. A rejected assignee takes the same branch — reported, never silently dropped.
4. **The default assignee comes from a declared adoption key** (`default-assignee`, schema in `skill-conventions/way-of-working-pm-resolution.md` § *Assignee resolution*), never from the authenticated user: under a bot token every item would go to the bot and pass its own check.
5. **The cascade has one code-host branch**: a PR write resolves `code-host-assignee` first and `default-assignee` second; an item write resolves `default-assignee` only. Declared in the same section, applied by `/pair-capability-publish-pr`. Without it the key had no reader, and a split project's PR would get the PM tool's login, be rejected by the host, and publish unassigned.
6. **An update never reassigns an item away from its current assignee.** The resolved assignee is written on an update only when `$assignee` was passed explicitly or the item has none. Add-vs-replace semantics stay the adapter's (only GitHub's `--add-assignee` adds; Linear, Azure and `filesystem` replace): the skill states *which value and when*, never *how*.
7. **The D4 skip is expressed by resolving no target at all**, never by the writer softening its HALT: once a macrostate is requested, an unmappable one can only HALT (route (c)). Where the caller **composes** the item writer — `/pair-process-refine-story`, which passes `$status` and renders a full body in the same call — resolving no target means **omitting `$status`**, the caller's job, not the writer's. `/pair-capability-publish-pr` does **not** compose it (decision 11): it resolves `## State Mapping` itself and **writes no state field at all** when no board state maps to `Review` — membership is still established and confirmed, only the state beats are skipped — which is this project's own case. There is no `$status` parameter on the direct path to omit.
8. **Membership does not depend on `$status`.** Step 7b runs its membership beats (check → add → confirm by read) on **every write-mode write** where the adoption names a tracked view — always on a create, equally on an update (decision 15) — and writes the state field only when Step 6 resolved one. Gating membership behind a transition left the most common path uncovered: an item filed with no `$status` (a planned task, a promoted tech-debt finding) is open, assigned, green and off the board — #384/#372 verbatim. The `Board:` row reports **membership and state separately** (`member of <view> — confirmed by read; no state written (no $status)`); a row that could only say "state" or `n-a` renders an on-board item as absent.
9. **The PR update path is conditional exactly as the item update path is** (decision 6 on the code host): on an existing PR the resolved assignee is written only when `$assignee` was passed or the read shows none; none is never cleared. "One rule, two callers" governs **update semantics** too — otherwise the fix→re-publish loop pulls a PR reassigned to the reviewer back to `default-assignee`.
10. **The read-back invariant is universal inside these two skills, not scoped to the item/PR body.** The comment post (Step 7c) is confirmed by reading the comments back — unconfirmed reports `Comment warned`, never `Commented` — and `/pair-capability-publish-pr` Phase 5 reads back both the `pair-review` status and the `pr-state:*` label it applies. A claimed-but-absent required check is worse than declared advisory enforcement.
11. **Every declared key has a writer as well as a reader.** `/pair-capability-setup-pm` Step 4 asks for the default assignee and writes `## Assignment` (plus `code-host-assignee` when it has just declared a split `code-host`); otherwise warn-and-write-unassigned is every new adopter's out-of-the-box outcome. `/pair-process-implement` Step 0.1b, which writes the PM tool directly on every story, resolves the assignee through the cascade (never the authenticated user, never a reassignment) and applies membership → confirm → state **by reference**; it cannot compose `/pair-capability-write-issue`, because write mode is a full-body overwrite and a state-only change must not re-render the story body.
12. **No adapter count is stated anywhere** — a number goes stale when a tracker is added, and the PM-tool README already rejects asserting one.
13. **The document the skills defer to is part of the contract surface, and so is this record.** `canonical-states.md` is where Step 6 and Step 7b send an agent to resolve a state; its `## Integration with Skills` table said `/pair-process-implement` (`In Progress`/`Review`) and `/pair-process-review` (`Done` on merge) write "through `/pair-capability-write-issue`" — the write-mode route decisions 7 and 11 forbid for a state-only change. Both rows now say **writes the board field directly, applying Step 7b by reference**; `/pair-process-refine-story` keeps its composition (it passes `$status` **and** renders a full body). The guard probes the KB authority (both corpora) and this ADL alongside the skills.

14. **The tool adapter is the last document before the command, so it is part of the contract surface too.** `github-implementation.md`'s `#### Common Transitions` row `Refined → In Progress` routed through the item writer (`via /pair-capability-write-issue $status: In Progress`) in the file Step 0.1b sends an agent to. It now reads **writes the board field directly**, applying Step 7b **by reference** and pointing at the status mutation two headings above. `Todo → Refined` is deliberately **unchanged** (refinement passes `$status` and renders a full body), and the guard pins it positively, so a sweep flattening every row to "direct" is caught.
15. **Membership is scoped to every write-mode write, not to creates.** Create-only scoping reproduced the defect one door down: `/pair-process-refine-story` writes `Draft → Ready` on a story that **already exists** and may never have been added, and an update with **no** `$status` is the repair path for an off-board item (#384/#372). Membership beats (1 to 4) run on **every write-mode write** when the adoption names a tracked view — always on a create, equally on an update — whether or not a state was requested; state-field beats (5 to 6) stay gated on Step 6. Step 7's **update** bullet says so where that path's reader reads, not only in Step 7b's preamble.
16. **On the merge path, `Done` is two writes — and a KB claim is asserted against the file that executes it.** Decision 13 made `canonical-states.md` say `/pair-process-review` "writes the board field directly" on merge, while `merge-and-cascade.md` Step 6.4 only closed the issue and its parents: no board field, no membership → confirming read → state, no read-back. Closing is **not** a board transition, so a story reported `Done` sat in `In Progress` (`post-review-merge.md` Step 4.4 was already corrected). Step 6.4 now states both writes, applies Step 7b by reference for the story and each parent it transitions, and verifies by a **read** of each. The guard reads the KB row **and** the executing file in one assertion.
17. **A step that documents two mechanisms for one write must state the read on both.** `/pair-capability-publish-pr` Phase 4 step 5 posts the back-link by composing `$mode: comment` (confirmed by Step 7c, degrading to `Comment warned`) or, when the item writer is **not installed**, directly through the PM tool's implementation guide — and that branch declared no read, though it runs exactly where the back-link is the **only** board→PR link (a split-tool project). The direct branch now carries the same read (`read the item's comments back` — the `## Activity Log` section on `filesystem`) and reports `back-link failed — manual link needed`, never `posted`; Graceful Degradation and the Composed Skills row say the same, and the guard asserts **both** branches in one scoped probe.

## Alternatives Considered

- **Fix the ordering only, no read-back**: Rejected by evidence — the bug reproduced *with* correct ordering, because the add itself lied.
- **Retry blindly instead of reading**: Rejected — a retry cannot distinguish "first call worked" from "neither worked". Retry is kept as a response to a *negative read*.
- **Put the read-back in the adapters**: Rejected — every adapter would copy one rule about what a skill may *claim*. Mechanics stay per-tool; claim discipline is single-sourced in the skill.
- **A `$verify` flag callers can turn off**: Rejected — re-creates the defect behind a parameter.
- **Scope "every write" down to paths already reading back** (decision 10): Rejected — the two uncovered paths cost one read each, and one is the required check that blocks merge.
- **Leave `/pair-process-implement` Step 0.1b to a follow-up story** (decision 11): Rejected — the contradiction runs on *every* story; the fix is two bullets pointing at rules this PR already states.
- **Treat an unassigned item as a HALT**: Rejected — an off-board item has nowhere for a state to go; an unassigned one is written and merely under-visible. A HALT trades a warning for lost work.

## Consequences

- Every board write costs at least one extra read; a publish costs one PR read. Deliberate.
- `/pair-capability-write-issue` gains a HALT (`membership could not be confirmed`), firing only where a board is present and membership is impossible — never on a project with no board (the D4 minimal-board path stays a documented skip; Step 6 now separates the two outcomes, because the pre-existing HALT for an unmappable `$status` was being read as covering both).
- Output shapes changed on both skills (`Labels`, `Assignee`, `Board` rows on the item write; `Assignee` and a read-confirmed `Tags` row on the publish): minor version bump on both.
- On this project's board no column maps to `Review`, so every `/pair-capability-publish-pr` run reports `Board: n-a — no Review state on this board` — the intended outcome of decision 7; readiness is carried by the PR.
- A future tracker-writing skill inherits the rule by pointing at it: prose plus a conformance guard, binding the corpus, not a runtime (accepted limit). Existing direct writers are covered now: decision 11 brings `/pair-process-implement` Step 0.1b under it; the same by-reference pointer applies to `post-review-merge` Step 4.4 (story + parent epic + parent initiative — nobody re-runs these, so an unread state is terminal) and to `/pair-capability-publish-pr` step 7, which the maintainer resolved on 2026-08-12 to write the board state directly, because composing write mode contradicted decision 4 (assigning "the current developer" is the authenticated-user default the cascade forbids).
- **A rule about a composition has two files to keep, and the guard must read both.** Decision 11 left the *composed* skill's Composition Interface still describing the board write as "the second composition (default write mode)", because negative probes ran on the publisher only. The contract is now asserted on both corpora (`[...writeIssueCases, ...publishPrCases]`), and the publisher's Graceful Degradation section is asserted on its own ("not installed ⇒ skip the board-state update" would re-create #384/#372 wherever the item writer is not installed). Rule of thumb: when a decision removes a composition, probe the losing shape in the caller **and** the callee.
- **The losing shape also lives where the skills defer, and in this record** (decision 13): it survived in `canonical-states.md`'s integration table and in decision 7, outside the probe set. Rule of thumb: **the corpus of a contract is every file that states it** — callers, the KB document they defer to, the governing record. All four are in the guard.
- **A decision that widens an earlier one must edit that earlier one, not sit next to it.** Decision 15 widened membership, but decision 8 still stated the create-only scoping. Decision 8 is corrected **in place** (as decision 7 was), decision 15 no longer quotes the losing wording, and the guard pins the pair positively **and** negatively, plus a whole-section sweep. Rule of thumb: **a decision list is a single statement of the rule — widening one item means rewriting every item that states the old scope.**
- Every create on an explicit-membership tool costs a membership read (plus, when absent, an add and a confirming read) even with no state requested. Deliberate: the alternative is items filed, assigned, green, off the board.
- `/pair-capability-setup-pm` gains a question and a write. Declining is supported and costs only the declared consequence (items and PRs filed unassigned), which the skill must state rather than proceed silently.
- **The chain ends at the adapter and at the executor** (decisions 14 to 16): the losing route survived in the **tool adapter** and, introduced by decision 13, as a KB claim **no executing file carried**. A claim is probed **where it is stated and where it is executed**. The guard reads every PM-tool adapter guide (a class probe over all four) and both merge paths.
- **A fallback is a mechanism, not a footnote** (decision 17): the composed path read back, the "not installed" fallback did not, ten lines apart. Rule of thumb: **an invariant binds every mechanism a step documents for the same write, and the guard reads them together** — a step-scoped probe asserting each branch names its own confirming read.
- Every merged story costs one extra board write plus one read per transitioned item (story and each parent the cascade closes).
- A board with no `Done` column is unaffected: the merge step reports closed item, no state written.
- **Open for the human merge gate:** AC6 on #403 was amended *during* review to state both outcomes (documented skip vs HALT) after the shipped contract split them. The split is argued in decision 7 and consistent with `canonical-states.md` route (c), untouched (only its `## Integration with Skills` table changed — decision 13) — but the record moved to match the implementation, so it wants explicit endorsement at the merge gate.

Macrostate model, Reading/Writing rules and route (c) unchanged.
- [github-implementation.md](../../knowledge/guidelines/collaboration/project-management-tool/github-implementation.md) (both corpora): `Common Transitions` row `Refined → In Progress` is the direct board write (decision 14); `Todo → Refined` and `In Progress → Done` untouched; mechanics unchanged — a routing correction.

Minor bumps: `/pair-capability-write-issue` 0.9.0, `/pair-process-review` 0.6.0.
- No dataset mirror of this file (adoption ADLs are adoption-only; the dataset is a curated seed). It **is** read by the conformance guard (decision 13), so it must describe the shipped contract.
