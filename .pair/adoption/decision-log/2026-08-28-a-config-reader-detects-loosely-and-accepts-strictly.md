# Decision: a config reader detects the KEY loosely and accepts the VALUE strictly — and a shipped mirror is a governed copy

## Date

2026-08-28

## Status

Active

## Category

Convention Adoption

## Context

Story #251's review found the same failure mode twice, on both sides of the profile: the resolver, and the gate around it.

1. **The resolver widened silently.** `parseWowProfileSection` matched one strict regex for a key AND its value. A `## Process Profile` section whose profile line left the VALUE unbackticked — the shape the schema's key/value TABLE suggests, rather than the fenced example — matched nothing, so the section resolved to `{profile: "default", enabled: 12 steps, halts: [], warnings: []}`. A PoC team got the full process, `plan-initiatives` and both DDD-mapping steps enabled and proposable, with nothing reported anywhere. The file's own normative rule is the opposite ("Every case below therefore HALTs rather than narrowing quietly"), and the failure ran in the **widening** direction — the one direction no downstream check looks at.

2. **The gate measured the source, not the loaded copy.** `checkStepMarkers` ran over `dataset/.skills` alone. Deleting `<!-- process-step: id=review -->` from `.claude/skills/pair-process-review/SKILL.md` left 168/168 tests green and `skills:conformance` PASS — a step that can no longer tell which step it is, whose profile gate never fires under `poc`, with every gate green. Same class as #280 ("it measured the DATASET copy only… the binding one is the installed MIRROR").

3. **The manual path had no entrypoint.** The catalogue makes the step→how-to mapping expressible; nothing a human with no skills installed reads mentioned the profile at all.

## Decision

**Detection is loose, acceptance is strict, and an unreadable declaration HALTs.**

- The key regex accepts decoration (`- **profile**:`, `- profile:`, `` - `profile`: ``) — the question it answers is "did the author mean to declare this key?".
- The value grammar stays exactly as strict as the schema (backticked tokens) — "is this value readable?".
- A key detected with no readable value is neither ignored nor guessed: it is a **HALT that restates the schema shape**. The two questions have different answers and must not share one regex.
- The same principle produced two distinguished messages where one was doing double duty: `custom` with **no** `whitelist` key is not `custom` with an **empty** one.

**The rule binds every level of the declaration, not just the key line** (round 2 — the review found the same hole through two other doors, both verified on the shipped resolver):

- **The SECTION HEADING is detected as loosely as the key.** `## Process profile` (sentence case) over a valid `` - `profile`: `poc` `` resolved to `{profile: "default", enabled: 12 steps, halts: [], warnings: []}` — byte-identical to writing nothing. Matching the heading exactly while matching the keys loosely reopens the widening hole one level up. The comparison is an **equality on normalized text**, never a prefix — `## Process Profile Gate` stays a different section. Normalization strips decoration on **every** side of the text, not only the trailing one (round 13): emphasis, code ticks, a closed-ATX `#` run, a trailing parenthetical and trailing punctuation; a **leading** run of non-alphanumerics and an optional `N.`/`N)` numbering; and internal separators — `-`/`_` map to a space and whitespace runs collapse. Trailing-only stripping left `## 🎯 Process Profile`, `## 1. Process Profile`, `## Process  Profile` and `## Process-Profile` unmatched, each resolving to `default` with all 12 steps and zero halts; the corpus's own house style is emoji headings (`## 🎯 Quick Start Process` in `AGENTS.md`/`CLAUDE.md`, `# 🤝 Way of Working` in the shipped template) and `Process-Profile` is the spelling story #251's statement uses.
- **Readability is decided on the RESIDUE, not on token count.** `values.length === 0` accepted a PARTIALLY backticked line: `` - `whitelist`: `implement`, review `` kept `implement` and dropped `review` on the floor, with no halt and one misleading prerequisite warning. Strip backticked spans and separators; anything left means the line is unreadable and the whole line HALTs. Applied to `profile` too: more than one backticked value is unreadable rather than "take the first".

The direction differs — the key case widened, the whitelist case NARROWED — and the schema calls narrowing the worse of the two, because a removed step is indistinguishable from a step not being due.

**"Every level" includes WHERE the section sits, not only what it says** (round 3 — the last two doors into the same room, both verified on the shipped resolver against this repo's own `way-of-working.md`):

- **A second `## Process Profile` section was silently ignored** (first match wins). This story is what makes that the likely edit: the shipped template AND this repo's own adoption file now both carry a `## Process Profile` section that is present and **empty** (prose only, no keys), so a team obeying the schema's own instruction — "the profile lives only in way-of-working.md, in a `## Process Profile` section" — by APPENDING one, rather than editing the existing paragraph, got `{profile: "default", enabled: 12, halts: [], warnings: []}`: byte-identical to the unmodified file.
- **The heading LEVEL was outside the loose-detection rule.** `### Process Profile` over a valid `` - `profile`: `poc` `` was not a section and, being unmatched, was not reported either — same silent `default`.

Both HALT. The level check is a **separate scan**, deliberately not a widening of `sectionOfWhere`'s `^##` predicate: that predicate also decides where a section ENDS, and for `## The Catalogue` / `## Built-in Profiles` / `## Quick Start Process` an `###` sub-heading is legitimately *inside* the section — widening it would silently truncate parsers no finding is about.

**"Every level" reaches the KEY and its LIST MARKER — the two rungs between the section and the value** (round 4, all three verified on the shipped resolver against the shipped catalogue and built-ins):

- **The same key on two LINES of one section resolved last-wins, silently.** `` - `profile`: `poc` `` followed by `` - `profile`: `custom` `` returned `{profile: "custom", enabled: ["implement"], halts: [], warnings: []}` — the `poc` line evaporated with nothing reported, and a team narrowed from 8 steps to 1 without a word. It was also **order-dependent**: the reverse order tripped the "whitelist under a built-in" HALT instead, so the same two lines halted or not depending on which came first. Now both orders return the same HALT naming the key. Counting is per key, not per section, because the section-level guard (round 3) and the value-level guard (round 2) each leave this rung untouched.
- **The marker class was `[-*]`.** `` + `profile`: `poc` `` — `+` is a CommonMark bullet, so that line IS "a backticked list item", exactly what the schema instructs — resolved to `default` with all 12 steps, zero halts: byte-identical to writing nothing. All three bullets are accepted.
- **A bullet-less or ordered-list key is DETECTED, not invisible.** `` `profile`: `poc` `` (the shape the `| profile | … |` schema table suggests) and `` 1. `profile`: `poc` `` were text the reader walked past, so they widened in silence too. They now land in `unreadable` and HALT with the schema handed back. Detection there requires the key to be **backticked**: without a list marker that is the only signal separating a declaration from a sentence about the key, and a looser test would read the schema's own prose as configuration.

**Below the key, the marker and the section there is a LEXICAL layer, and the rule binds it too: the reader reads CommonMark, not lines of text** (round 5, all verified on the shipped resolver against the shipped catalogue and built-ins):

- **Line endings are normalized once, at the parse boundary.** Every line regex here ends in `(.*)$` with no `m` flag — `.` cannot match `\r` and `$` anchors at end-of-string — so on a CRLF file NOTHING matched: `parseWowProfileSection` over a CRLF `## Process Profile` section carrying a valid `` - `profile`: `poc` `` returned `{profile: null, unreadable: [], duplicateKeys: [], sectionHalts: []}` and the full resolve returned `{profile: "default", enabled: 12, halts: [], warnings: []}` — byte-identical to writing nothing, with **every** rule above silent at once. CRLF is the default checkout on Windows (`core.autocrlf=true`), i.e. the file `pair update` writes there. The inversion was exact: on a CRLF file the shape the schema PRESCRIBES was ignored while the off-marker shape it REJECTS still HALTed.
- **A fence is a fence however it is spelled, and the recognizer must accept exactly what the skipper skips.** Example extraction matched only ```` ```[a-z]*\n ````, so a titled fence, an uppercase info string or a `~~~` block made a worked example invisible to the gate — while the section parser's own skipper still skipped it, leaving that shape neither read as a declaration nor checked as an example. Inside the section the mirror-image hole: only ``` blocks were skipped, so a `~~~` or four-space-indented illustration was read as the project's real declaration (the indented one silently BECAME the profile, 12 steps → 8, nothing reported; the `~~~` one HALTed `/next` on a placeholder id the project never configured). One fence scanner now serves both, closing only on the character that opened it.
- **Three CommonMark-valid heading spellings were neither matched nor reported**: `## Process Profile ##` (closed ATX), a heading indented by up to three spaces, and the setext form. Each resolved to `{profile: "default", enabled: 12, halts: [], warnings: []}` over a valid `poc` declaration. The first two are decoration in the same sense as emphasis and are now accepted; the setext form is not the shape this reader accepts and HALTs, because a heading that is neither read nor reported is the widening direction one more time.

**The LEXICAL layer has a LAYOUT half, and the same rule binds it: a key is one line at the top level, and a document the reader cannot see whole is not read at all** (round 6, all verified on the shipped resolver against the shipped catalogue and built-ins):

- **A value that spills past its key's line HALTs.** The residue check erases a trailing `,` exactly as it erases the separators between ids, so a wrapped whitelist read as complete and the continuation line matched no key regex and was discarded: the shipped `poc` id set on ONE line resolved `{profile:"custom", enabled:8}`, the SAME ids hand-wrapped resolved `{profile:"custom", enabled:4, halts:[], warnings:[]}` — four steps gone, nothing reported, and no prerequisite warning either since the surviving prefix happened to be prerequisite-closed. The wrap is the natural edit: a `custom` example runs past 130 columns and markdownlint's default line-length rule is 80 (this repo disables MD013; an adopting project does not). Dangling separator and lazy continuation are both detected, on the RAW remainder rather than the residue.
- **An indented key is ambiguous, so it HALTs rather than being read either way.** Four spaces or a tab is CommonMark's indented code block AND an ordinary sublist item. Skipped as code, `- Configuration:` + a 4-space `` - `profile`: `poc` `` resolved `{profile:"default", enabled:12, halts:[], warnings:[]}`; the same key indented by TWO spaces resolved `{profile:"poc", enabled:8}` — so which one a team got depended on their editor's Tab width. Gate-safe: no shipped surface carries an indented key line.
- **A fence closes on a run at least as long as the one that opened it.** The scanner tracked the character but not the length, so an inner ``` closed an outer four-backtick block — the standard way to SHOW a backticked declaration. With a real declaration alongside it the nested example collided into `` `## Process Profile` declares `profile` more than once (2 lines) `` on a key written exactly once; alone, it simply became the profile.
- **An HTML comment is not content.** A `## Process Profile` heading inside `<!-- ... -->` counted as a real section, so parking the old declaration in a comment while trying a new one HALTed every run with "keep one section" about a file that visibly shows one. Comment spans are masked before heading and key scanning, exactly as fenced spans already were.
- **A truncated view is not a view.** One unterminated fence anywhere above the section left every later line "inside a fence", so the real heading was never found: `` ```text `` never closed, over a valid `poc` section, resolved `{profile:"default", enabled:12, halts:[], warnings:[]}` — byte-identical to writing nothing, and `profileSectionProblems` reported nothing either. An unterminated fence or comment now HALTs the file instead of resolving it from what survived.

**A worked example is labelled by what it DECLARES, never by what the failure resolved to.** Every HALT path returns `profile: 'default'`, so a corrupted `custom` example was reported as `worked example (`default`)` — and `default` accepts no whitelist at all, so the label contradicted the message and pointed a maintainer at the wrong fence. Examples are now labelled by position and by their declared name.

**The sweep covers every shipped surface carrying a declaration, not only the two the feature was written from.** `apps/website/content/docs/**` (the feature's public documentation) and this repo's own `.pair/adoption/tech/way-of-working.md` (the file `/next` reads when run here) carried the same worked examples with no gate behind them — the same blast radius as the template hole, on the page a reader is likeliest to copy from. The precedent for reaching outside the package already existed (`MIRROR_SKILLS_DIR`); each file is swept only when present, so an adopting project's knowledge-hub checks exactly what it ships.

**A shipped worked EXAMPLE is recognized by its key lines, not by a heading inside its fence.** `extractProfileExamples` required a `## Process Profile` line *within* the fenced block. The KB schema writes its examples that way; the shipped adoption **template** does not — its heading is the section the fence sits in, and the fence holds bare key lines. So the file `pair update` writes into every adopting project had **none** of its examples checked while the gate reported them checked. Verified: replacing `plan-stories` with `plan-storys` in the template's `custom` example printed `PASS — 44 skills conformant`, exit 0; now it prints `dataset/.pair/adoption/tech/way-of-working.md: worked example (default): unknown step id(s) plan-storys ...` and exits 1. A fence carrying a `profile`/`whitelist` key line is an example; with no heading of its own it is given the one it is an example OF.

**A convention's normative snippet is pinned to the corpus it governs.** `process-profile-gate.md`'s "what stays in the skill" block prescribed a delta none of the twelve shipped skills carries. `checkOneStepMarker` only requires the marker plus the pointer *somewhere* in the skill dir, so a thirteenth author copying that snippet verbatim would land a differently-worded delta with every gate green. The snippet is now the `/refine-story` block verbatim, and a conformance test asserts the two are byte-equal.

**A shipped mirror is a governed copy, not a build artifact.** `skills:conformance` and the conformance suite now bind the marker + gate pointer on `.claude/skills/pair-*/SKILL.md` as well as on the dataset, mapping names through the real `pair update` transform (`installedSkillDir`) rather than a copy of it.

**The manual path is governed at its own entrypoint.** `AGENTS.md`'s "Without skills" flow carries a profile step before "identify your task", and `checkManualPathEntrypoint` asserts it — on the SECTION, not the file, since a mention parked in an appendix is not an entrypoint.

**A HALT yields NO step set — the resolution is a discriminated union** (round 7). Every HALT path returned `{profile: 'default', enabled: <the whole catalogue>, halts, warnings: []}`. Both callers read `halts` first, so nothing was broken — but the TYPE made this module's own worst failure representable: a caller reading `resolution.enabled` without checking `resolution.halts` gets the full 12-step process on a project whose declaration was unreadable, which is precisely the silent widening every HALT message in the file argues against. `ProfileResolution` is now `ResolvedProfile { ok: true, profile, enabled, warnings } | HaltedProfile { ok: false, halts }`, and callers surface problems through `profileProblems(resolution)`. The same rule reaches the prose readers: a HALT stops the run, it does not continue on `default`.

**A file the gate names as checked is read as what it IS** (round 7). `checkShippedProfileProse` resolved the shipped adoption template as a whole document, but this repo's own `.pair/adoption/tech/way-of-working.md` — the file `/next` reads when run here — was in the example-sweep list and nowhere else, and its `## Process Profile` section carries no fenced example, so ZERO checks applied to it while the PASS line named it. Verified: `` - `profile`: `pocc` `` under that heading printed `PASS — 44 skills conformant`, exit 0, while every `/next` run here would HALT on `unknown process profile \`pocc\``. Both way-of-working files now go through`resolveProcessProfile`as declarations (`PROFILE_DECLARATION_FILES`), in addition to the example sweep. A docs`.mdx` page stays example-only: its prose is not a declaration anyone resolves.

**A documentation TABLE row is not a declaration, and must not become one** (round 7). The off-marker rule's comment claimed the `| profile | … |` table row as a shape it catches; the pattern is `^`-anchored on the key and requires a `:` immediately after it, so it never did — and it must not, because the shipped adoption template and the KB schema both document the two keys in a table inside or beside the section, and matching that row would HALT the shipped template. The exclusion is now stated and pinned by a unit case.

**A decoration is a declaration; a quotation is documentation — and where the line falls is written down, not left implicit** (round 8, both verified on the shipped resolver against the shipped catalogue and built-ins). A key inside a **blockquote** was invisible to both key patterns (`^\s*[-*+]` — `>` is not whitespace — and `^[ \t]*`), so `> **Note**: PoC subset.` / `>` / `` > - `profile`: `poc` `` under the section heading resolved to `{ok: true, profile: 'default', enabled: <all 12>, warnings: []}` — byte-identical to writing nothing, the widening direction the module halts on for every other off-shape. It now HALTs, and that is the OPPOSITE ruling from the table row above, on purpose: the table row is the shape the schema and the shipped template use to DOCUMENT the two keys (matching it would redden the gate on its own governing files), while a blockquoted list item appears nowhere in this corpus as documentation (`grep -rn "^> [-*+] "` over `.pair/adoption/` and the dataset copy: zero hits) and reads as an author's decorated declaration. Both halves of the distinction are now stated in the schema, the adoption template, `/next` Step 0.5 and both docs pages, and pinned by unit cases in both directions — the round-7 exclusion was enforced in code and written nowhere. The rule has a second arm at the same beat: a blockquote OPENS a block in CommonMark, so blockquoted prose under a key line is no longer read as that value's lazy continuation (it HALTed a perfectly readable declaration as "spilled").

**A repeated step id inside a whitelist HALTs — it is never deduped in silence** (round 8). `` - `whitelist`: `implement`, `implement` `` resolved to `{ok: true, profile: 'custom', enabled: ['implement', 'implement'], warnings: [<the prerequisite warning>, <the byte-identical string again>]}`: one authoring mistake, told to the user twice, and an `enabled` list that makes every "N steps enabled" count wrong. The module already HALTs on the SAME mistake one rung up — the same KEY on two lines ("only the last is read") and two values on a `profile` line — so accepting it inside the value alone made this reader's strictness depend on which rung the typo landed on. It is also genuinely ambiguous: a repeat is as plausibly a copy-paste never edited into the step actually meant (the `plan-storys` class of error) as it is a harmless duplicate, and deduping picks one reading and hides the other.

**The key's CASE is part of its spelling, so it sits on the DETECTION side; the value's does not** (round 9, verified on the shipped resolver against the shipped catalogue and built-ins). All three key patterns were case-sensitive, while the HEADING one level up is matched case-insensitively for exactly the reason stated there — and the heading immediately above the key is Title Case (`## Process Profile`), so mirroring it into `` - `Profile`: `poc` `` is the same class of author error as copying the table's bare key spellings, which the reader already handles. Unread, that line resolved to `{ok: true, profile: 'default', enabled: <all 12>, warnings: []}` — byte-identical to writing nothing, the widening direction. The second arm was worse: `` - `profile`: `custom` `` + `` - `Whitelist`: `implement` `` HALTed with "profile `custom` declares no `whitelist` — `custom` requires one: add ``- `whitelist`: …``" about a line visibly in the file, which is the anti-pattern the schema's own error table writes down ("one message sends the reader hunting for a line their file does not have"). Detection is now case-insensitive on all three patterns and the capture is canonicalized to lowercase at one point (`canonicalKey`), so the duplicate-key counter reads two spellings of one key as one key declared twice, and every message prints the canonical name. The rejected shapes stay rejected in any case — an off-marker or blockquoted `` `Profile` `` HALTs rather than reopening the hole one shape lower down — and the VALUE stays strict: `` - `profile`: `POC` `` still HALTs as an unknown profile name. Gate-safe by inspection: `grep -rniE` for a case-variant key line across every file the gate reads (both way-of-working files, the KB schema, the shipped template, both docs pages) returns zero hits, and a case-variant documentation TABLE row remains no declaration, like its lowercase form.

**Two author errors on one line compose; they do not cancel** (round 10, verified on the shipped resolver against the shipped catalogue and built-ins). The two REJECTED-marker patterns required the key to be BACKTICKED while the ACCEPTED-bullet pattern does not, so each error axis HALTed alone and their INTERSECTION was invisible: `- profile: poc` HALTed (unreadable shape), `` 1. `profile`: `poc` `` HALTed (marker not accepted), and `1. profile: poc` resolved to `{ok: true, profile: 'default', enabled: <all 12>, warnings: []}` — byte-identical to writing nothing. Same for `> - profile: poc`. The stated reason for the backticks was that "without a list marker that is the only signal separating a declaration from a sentence mentioning the key" — but `1.` IS a list marker and `> -` carries a bullet, so the requirement over-reached exactly where its own rationale does not, and the unbackticked value is the shape the schema's documentation TABLE suggests, which is the case the accepted-bullet pattern was loosened for to begin with. The backticks are now required only on the genuinely marker-less line (`` `profile`: `poc` `` HALTs; `profile: poc` stays prose), and padding inside the ticks (`` - ` profile `: `poc` ``) is detection-side decoration like every other.

**A guard that cannot find its input reports that, it does not report nothing** (round 10). `checkShippedProfileProse` skipped an absent path in both of its loops, so a governed file that was MISSING or RENAMED went unchecked while the CLI printed the PASS banner that names all five as validated — and `checkShippedProfileProse(<empty tmpdir>, …)` returned `[]`, observationally identical to "all five validated clean". Two of the five reach outside the package into `apps/website/content/docs/**`, so a docs-site reorganisation dropped a page out of the gate with no signal and its worked examples were free to teach a shape no reader accepts. An absent governed file is now an error naming the path and the two lists to update — the fail-closed rule the corpus states one directory over in `approval-rounds.md` ("a guard that answers 'nothing to check' when it cannot parse its input is indistinguishable from a guard that passes").

**A GENERATED copy is a governed copy too — the rule already stated for skills, applied to the KB and to the root entrypoints** (round 11). The gate bound the dataset SOURCE of the step catalogue, the profile schema and `AGENTS.md`, and left the copies every reader actually resolves — `.pair/knowledge/**/step-catalogue.md`, `.pair/knowledge/**/process-profiles.md`, the root `AGENTS.md`/`CLAUDE.md` — outside it. Verified: deleting the `` `brainstorm` `` row from the installed catalogue and typo-ing `poc`'s first whitelist id there (`spcify-prd`) printed `PASS — 44 skills conformant`, exit 0; so did replacing the manual-flow profile step in both root files, which un-does AC8 for this repo since `checkManualPathEntrypoint` was asserted on `dataset/AGENTS.md` alone. At runtime that is a `poc` project halting on every `/next` run over an id it never configured, or an ungoverned step, with the gate green. `checkInstalledProfileCorpus` now binds step ids, how-to, `requires` and the built-in whitelists to the dataset — executables through the real `pair update` name transform (`installedSkillDir`), never a copy of it — and runs the manual-path check over both root files. Gated on the installed KB tree existing (an adopting project's knowledge-hub has none); present ⇒ each governed file inside it is REQUIRED, per the round-10 fail-closed rule.

**A per-skill obligation is checked per skill, not on a representative** (round 11). AC6 asks that each of the twelve step skills carries the direct-invocation gate; what was enforced per skill was the marker plus the string `process-profile-gate.md` anywhere in its directory, with the behavioural sentence pinned byte-for-byte for two of the twelve (`refine-story`, `map-subdomains`). Verified: deleting the whole delta sentence from `dataset/.skills/process/implement/SKILL.md` AND its mirror left `PASS — 44 skills conformant` and 107 green conformance tests, with the only instruction an executor reads gone. The delta is now checked as CLAUSES (direct ⇒ warn + confirm/HALT; composed ⇒ never prompts, degrades as not installed) over the skill's `## Process Profile` section plus the siblings it discloses — not as the convention's snippet byte-for-byte, because the corpus ships three legitimate shapes (plain, `$approval`-family, `brainstorm`'s disclosed half) and a byte-check would force two of them to lie. A link that climbs OUT of the skill directory does not resolve the obligation: the convention itself states both clauses, so reading through it would let any skill pass by carrying the pointer it already has to carry.

**A section ends at a level-1 heading as well as at level 2** (round 11). `sectionOfWhere` terminated only on the next `##`, so everything under a later `#` was read as still inside `## Process Profile`: `## Process Profile` + `` - `profile`: `poc` `` + `# Other` + `` - `profile`: `custom` `` HALTed with "declares `profile` more than once (2 lines)" about a section that visibly carries one — the misdirection class the round-7 example-labelling fix closed. The direction was safe (a HALT, never a widening), the message was not. `###`+ stays INSIDE, unchanged and pinned: a sub-heading is part of its section, a level-1 heading is a document division above it. No shipped file changes behaviour — every level-1 heading below the top of the files the gate reads sits inside a fence.

**A composition beat states the profile per COMPOSED STEP, not once per file** (round 11). `/bootstrap` declares three composed steps and the conformance guard asked for one occurrence of the clause anywhere before `## Graceful Degradation`, which its two `map-*` beats satisfied — so Phase 0 Step 0.1 still read "**Act** (missing or template): Compose `/specify-prd`." A `custom` project whitelisting `bootstrap` without `specify-prd` is legal and readable (AC9 reports, it does not repair), so `/bootstrap` stays invocable and an executor following the numbered algorithm on a fresh project ran a full interactive PRD-authoring session — which WRITES an adoption file — for a step the project declared it does not run, with no prompt and no note. The beat now carries the check, and the guard asserts the clause once per composed step id declared in the composer's own delta, matched inside the same `##`/`###` block as that step's executable.

**Binding a generated copy means its PROSE, not only its cells — and it means all three files of the feature** (round 12). Round 11 bound the installed catalogue and profile schema cell for cell and left the prose around those cells, plus the third governed file, unbound. Verified, each corruption reverted afterwards: reducing `.pair/knowledge/**/skill-conventions/process-profile-gate.md` to `# Process Profile Gate` + `TODO` printed `PASS — 44 skills conformant`, exit 0 — that is the file all twelve installed step skills point at, and the only home of the prompt wording, "proceed silently, byte for byte", the HALT carve-out and the `$approval: auto` ⇒ `auto=halt` resolution, so after the corruption an unattended run reaching a disabled step has no instruction anywhere and the natural default is to proceed; and typo-ing `` `specify-prd` `` to `` `spcify-prd` `` in the installed `process-profiles.md` worked example was reported by nothing, while the identical typo in the DATASET copy failed the gate. The example sweep is now path-based (`profileExampleErrors`), applied to both installed KB copies, and the installed convention is read fail-closed and checked for the same DIRECT/COMPOSED clauses each delta owes plus the `auto=halt` clause — the one instruction NO delta carries, so nothing else can report its loss.

**A guard whose subject list comes from the file under test de-scopes itself when that file shrinks** (round 12). The composers guard derived the ids it policed from the delta's own `composer of` clause, with a single global `perComposedStep.length > 0` backstop. Verified: rewriting `plan-tasks`' delta to "a composer of the context-mapping capability" and gutting its Step 2.5 beat (dataset AND mirror) left `pnpm skills:conformance` at `PASS`, exit 0, and `process-profile.test.ts` at `Tests 112 passed` — DOWN from 114, because the two `it.each` cases ceased to exist and nothing reads the count. The claim is now cross-checked against a declaration made INDEPENDENTLY in the same file, the `## Composed Skills` table, and the list of composers is itself derived from the corpus rather than typed here.

**A completion report is a governed surface: a step that names the next skill applies the profile filter** (round 12). Three surfaces were governed — `/next`'s cascade and fallback, direct invocation, composition — and the `Next:` line a step prints was not. On the `custom` whitelist this branch itself ships as a worked example (`specify-prd, plan-initiatives, plan-epics, plan-stories, refine-story, plan-tasks, implement, review` — the flagship "we do no DDD" case), `/plan-initiatives` is ENABLED, runs with no warning, and ended its report `Next: /map-subdomains (scoped to this initiative) or /plan-epics`: an enabled skill telling the project to run a DDD step it declared it does not run. The rule `/next`'s Step 5 fallback already had ("never name a disabled step") is now stated once in the convention and applied by every step report that names a catalogued step.

## Alternatives Considered

- **Keep the strict single regex and document the shape harder**: rejected. The mis-shaped line came from copying the file's own table; prose cannot beat a shape a reader already produced, and the failure is silent by construction.
- **Accept an unbackticked value** (loose acceptance): rejected. It makes the grammar guessable rather than declared, and re-opens "is `poc.` a profile name?" for every value.
- **Assert the mirror by byte-equality only** (leave it to `skill-md-mirror`): rejected. That guard is directional dataset→mirror equality; it catches a *drifted* copy, not a hand-edited one that both guards read as legitimate content — and the marker is the thing the profile hangs on.
- **A follow-up card for the manual path**: rejected by the story's own AC8 and success metric ("a project with no skills installed gets the same profile behaviour through the how-to path").
- **Return `enabled: []` on the HALT path** instead of the union (round 7): rejected. It only trades the widening for the NARROWING direction — the one this file already calls the worse of the two, because a removed step is indistinguishable from a step not being due. There is no honest step set behind an unreadable declaration, so the type stops offering one; the test file's flat view reports `profile`/`enabled` as `null` on a HALT, and every halt case asserts that.
- **Dedupe the whitelist ids** (`[...new Set(whitelist)]`, round 8): rejected, though it was the finding's first suggestion. It is a silent repair of an author error in a module whose whole stance is that an author error in the declaration is reported — and it picks one reading of an ambiguous line, hiding the unfinished-edit case entirely.
- **Treat a blockquoted key as documentation, like the table row** (round 8, the finding's other option): rejected. The two shapes are not symmetric. The table row must stay documentation because the gate's own governing files carry one; a blockquoted key appears nowhere in this corpus, so ruling it a declaration costs nothing and closes the one hole that resolves to `default` with no halt and no warning. The asymmetry is written down at every prose surface rather than left to the code.
- **Route a case-variant key to `unreadableShapeHalt`** (round 9, the finding's other option): rejected. It closes the same hole, but it rules the key's case the opposite way from the heading's one line above — and from every other decoration on the same line (bold, missing backticks, any of the three bullets), all of which are honoured rather than halted. Detection is the question "did the author mean to declare this key?", and a Title-Case key on a bullet answers it unambiguously; the HALT is reserved for lines whose VALUE the reader cannot accept. The rejected MARKER shapes keep their HALT in any case, because there the shape itself, not the spelling, is what the reader cannot honour.
- **Keep the backticks required behind an ordered marker / inside a blockquote** (round 10): rejected. It is the state that produced the hole: two independently-detected errors whose combination was undetected, and the combination is the likelier author mistake, not the rarer one — the wrong marker comes from reading the schema's numbered prose, the bare value from reading its table, and both readings come from the same page.
- **Keep skipping an absent governed file** (round 10): rejected. `existsSync`-guarding each entry was written so an adopting project's knowledge-hub checks only what it ships — but this function's file list is fixed and all five ship in this repo, so the guard bought nothing and cost the whole signal. Absence is now the error; a path that legitimately moves is a one-line edit to `PROFILE_PROSE_FILES` / `PROFILE_DECLARATION_FILES`, which is exactly the edit the gate should force.
- **Pin each of the twelve deltas to the convention snippet byte-for-byte** (round 11, the finding's first option): rejected. The corpus ships three legitimate shapes and only two are quoted in the convention; a byte-check would either redden `brainstorm` (whose half is disclosed to `degradation.md` under a byte budget) or force it to duplicate prose it deliberately does not carry. The clause check binds what an executor must be told and leaves the wording free — the same reasoning `approval-round` markers use against layout-derived windows, one notch looser.
- **Widen `sectionOfWhere`'s heading predicate to any level** (round 11): rejected, as in round 3 for the same reason. `###` sub-headings sit legitimately inside `The Catalogue`, `Built-in Profiles` and `Quick Start Process`; ending a section there would truncate the three documents this module parses. Only the START stays level-2-exact — a `# Process Profile` is still the mis-levelled-heading HALT, not a section.
- **Rely on `mirror-guard.test.ts` for the generated copies** (round 11): rejected. It does assert byte-equality with `transform(dataset)` for the KB tree and both root files, and it is what catches these corruptions in the full suite — but it is a different gate with a different failure message, and `skills:conformance` is the one whose PASS banner names the catalogue, the profiles and the manual-path entrypoint as validated. A gate that names a file reads it (round 7's rule), and the profile-shaped message ("the installed copy declares no step `brainstorm`") is the one a maintainer can act on.
- **Compare the installed convention to the dataset copy byte-for-byte through `installedSkillDir`** (round 12, the finding's second option): rejected for the round-11 reason, one level down. `mirror-guard.test.ts` already asserts that equality for the whole KB tree; what this gate owes is the profile-shaped message a maintainer can act on ("no longer resolves the gate for an UNATTENDED run"), and the clause check is the same rule `checkStepDelta` applies to the twelve skills that delegate here — one rule, two levels.
- **Scan each skill's algorithm text for named executables** (round 12, the finding's first option for the composers guard): rejected THEN, **adopted in round 13 in a narrowed form** — see the next bullet. The round-12 objection was measured and is real: a whole-body scan of the text before `## Graceful Degradation` returns 40 subject ids across the corpus, most of them not compositions (`Next:` lines, "not for X, use `/y`" cross-references, Callers matrices), and requiring a profile clause for each would redden 34 of them.
- **Restrict the algorithm scan to the OBJECT of a composition verb** (round 13): adopted. `/compos\w*[^.;:\n—]{0,60}/` — a `compos*` token and the ≤60 characters that follow it, stopped at the first sentence/clause boundary — yields, for the four composers, exactly the set their delta declares and nothing else (measured on dataset **and** mirror: `bootstrap` → `specify-prd`, `define-subdomains`, `define-bounded-contexts`; `refine-story` → both `map-*`; `plan-tasks` → `define-bounded-contexts`; `plan-epics` → `define-subdomains`). It is not a third declaration of the same claim: dropping the composition **from** the algorithm is the skill ceasing to compose that step, not a de-scoping of the guard.
- **Keep the composers guard's subject list on the delta + the `## Composed Skills` table alone** (round 13): rejected. Both are declarations by the same author in the same file, editable in one pass. Deleting `define-subdomains` from `/bootstrap`'s `composer of` clause and its `/map-subdomains` table row (dataset + mirror, two edits, no third) left `process-profile.test.ts` green at `Tests 147 passed`, DOWN from 149 — nothing reads the count — and a third edit gutting the Phase-3.5.1 beat then landed green too, reintroducing the round-11 failure. The subject list is now the **union** of the three sources, so no single declaration can shrink it.
- **Filter only the three `Next:` lines the finding named** (round 12): rejected. The rule as written in the convention is general, and a corpus-derived guard finds five more reports of the same shape (`brainstorm`, `plan-epics`, `plan-stories`, `plan-tasks`, `refine-story`, each naming a catalogued step a `custom` profile may disable). Exempting them would rebuild, in the new guard, the hand-written-list defect the second round-12 finding is about.
- **Resolve the docs `.mdx` pages as declarations too** (round 7): rejected. A documentation page's prose is a declaration nobody resolves; only its fenced examples are, and those the sweep already covers. Reading the pages as documents would report their illustrative text as this project's profile.

## Consequences

- A mis-shaped `## Process Profile` section now stops the run with the schema handed back, instead of quietly restoring the full process.
- `skills:conformance` fails on a hand-edited or half-regenerated skills mirror. Verified: deleting the `review` marker from the mirror prints `mirror: pair-process-review/SKILL.md: … declares no <!-- process-step: id=review --> marker` and exits 1 (it was green before).
- The shipped worked EXAMPLES go through the real resolver too, so an example that resolves with a prerequisite warning is a red gate — the class of defect the review found in `process-profiles.md`'s own `custom` example.
- `.claude/skills/**` is now inside the conformance surface for this convention: a mirror regeneration is required after a dataset edit, which `pair update` already does.
- A team appending one id to a working whitelist without backticks now gets the schema handed back, instead of losing that step from every suggestion for the life of the project.
- A decorated `## Process Profile` heading is honoured rather than ignored, so the section cannot be disabled by a cosmetic edit.
- A project that **appends** a `## Process Profile` section instead of editing the empty one the template ships now gets a HALT naming the duplication, rather than the full process back in silence. Same for a section written at `#`, `###` or deeper.
- A team hand-adding a second `profile` (or `whitelist`) line under an existing section gets a HALT naming the key, and the same one whichever order the two lines are in.
- `+` joins `-` and `*` as an accepted bullet; a bullet-less or numbered key line stops the run instead of resolving to `default`. A project whose section already uses `-` sees no change.
- Corrupting any worked example in the shipped `way-of-working.md` template is now a red gate, not a shape CI certifies and every adopting project copies.
- The gate's PASS line enumerates the checks this story added, so a green run is evidence they ran.
- A project on Windows gets the same profile behaviour as one on Unix: the CRLF checkout `pair update` produces there no longer resolves to `default` in silence.
- An illustrative code block next to the real declaration — in any of the three CommonMark forms — is an example on both sides of the reader: never read as the profile, always checked as an example.
- A docs edit that retitles a fence, or one that shortens a whitelist on the website, is now a red gate rather than a shape CI certifies and readers copy.
- A team whose linter forbids a 130-column line is told to exempt the line, not silently given a shorter process: the schema and the adoption template both state that a key is one line however long, and wrapping it HALTs.
- Commenting a section out is a supported way to park a previous profile; an unterminated fence or comment anywhere in way-of-working.md now stops the run instead of resolving the file from a truncated view.
- A future caller of `resolveProcessProfile` cannot consume a step set from a halted resolution: the halted arm does not have one, so the compiler rejects the read rather than a reviewer catching it.
- A profile typo in **this repo's own** way-of-working is a red gate, not a green one followed by a HALT at the next `/next`. Verified: `` - `profile`: `pocc` `` under the section → `FAIL — 1 violation / ../../.pair/adoption/tech/way-of-working.md: unknown process profile \`pocc\` …`, exit 1 (it printed`PASS`, exit 0, before).
- The four composers that reach DDD mapping — `refine-story`, `plan-tasks`, `plan-epics`, `bootstrap` — name the profile at the composition beat itself and in their graceful-degradation entry, as `brainstorm` already did. An executor following the numbered algorithm under `poc` no longer composes `/map-subdomains` on a project that declared it does no DDD mapping.

- A note-styled declaration (`` > - `profile`: `poc` ``) stops the run naming the shape instead of handing the project the full process in silence; a documentation table row keeps costing nothing, and both rules are now readable by an author who never opens the code.
- A whitelist that names a step twice stops the run naming the id, instead of double-reporting that step's prerequisite warning and over-counting the enabled set.
- A team that spells the key as the heading above it does (`` - `Profile`: `poc` ``) gets the profile it declared, rather than the full process in silence — and a `custom` section whose `whitelist` line is capitalized is no longer told it wrote no whitelist at all. No shipped file changes behaviour: none of them carries a case-variant key line.
- A half-run `pair update` or a hand edit of `.pair/knowledge/**/step-catalogue.md`, `.pair/knowledge/**/process-profiles.md` or the root `AGENTS.md`/`CLAUDE.md` is a red gate in the profile's own terms. Verified: the installed catalogue minus its `brainstorm` row plus `spcify-prd` in the installed `poc` whitelist → `FAIL — 2 violations`, exit 1; the manual-flow step replaced in both root files → `FAIL — 6 violations`, exit 1 (both printed `PASS — 44 skills conformant`, exit 0, before).
- Any of the twelve step skills losing its delta sentence is a red gate, dataset and mirror. Verified: the sentence deleted from `/implement` in both copies → `FAIL — 4 violations`, exit 1 (it was `PASS`, exit 0, with 107 conformance tests green).
- A key under a level-1 heading below the section is out of the section, so an author is no longer sent to look for a duplicate `profile` line that is not there.
- `/bootstrap` composes `/specify-prd` only when the step is enabled; disabled, it degrades exactly as "not installed" — HALT at Phase 0 with the how-to-01 pointer — instead of opening an unrequested PRD-authoring session that writes an adoption file.

- Gutting the installed gate convention is a red gate. Verified: reduced to `# Process Profile Gate` + `TODO` → `FAIL — 3 violations`, exit 1 (DIRECT, COMPOSED, `auto=halt`); a typo in the installed profile schema's `custom` worked example → `FAIL`, exit 1 (both printed `PASS — 44 skills conformant`, exit 0, before). An unattended run can no longer lose its `auto=halt` instruction silently.
- A composer that stops naming a composed step id in its delta reddens instead of shrinking the guard. Verified: `plan-tasks`' delta rewritten to name no id → 4 failed; one id of two dropped from `refine-story`'s → 3 failed (`Tests 112 passed`, no failure, before).
- No step's completion report names a step the project disabled. Eight reports across the corpus carry the filter, and a ninth added later reddens until it does.

- A `## Process Profile` heading written in the corpus's own house style is the section. Verified on this repo's own `way-of-working.md`, `` - `profile`: `pocc` `` under each of `## 🎯 Process Profile`, `## 1. Process Profile`, `## Process  Profile`, `## Process-Profile` → `FAIL — 1 violation`, exit 1 (all four printed `PASS — 44 skills conformant`, exit 0, before). `## Process Profile Gate` and `## Process-Profile-Gate` both stay different sections.
- The composers guard cannot be de-scoped by editing the two declarations it used to read. Verified: `/bootstrap`'s delta clause and its `/map-subdomains` table row deleted in dataset and mirror → still 149 tests (it was 147, green, before); a third edit gutting the Phase-3.5.1 beat → 2 failed (it was green before).
- The fourth clause of the gate convention is bound in the installed copy as the other three are. Verified: the completion-report paragraph deleted from `.pair/knowledge/**/process-profile-gate.md` → `FAIL — 1 violation`, exit 1 (it printed `PASS — 44 skills conformant`, exit 0, before).

## Adoption Impact

None for adopters' code. It changes `packages/knowledge-hub/src/tools/skills-conformance-check.ts`, the shipped `AGENTS.md` template (one manual-flow step, mirrored to root `AGENTS.md`/`CLAUDE.md` by `pair update`) and the profile schema's error-case table. An adopting project inherits the stricter reader and the new manual-flow step on its next `pair update`; a project whose way-of-working already carries a well-formed section sees no change. Round 12 adds one line to the gate convention and one sentence to the eight step skills whose completion report names a catalogued step; on the `default` profile — every step enabled — no report changes.
