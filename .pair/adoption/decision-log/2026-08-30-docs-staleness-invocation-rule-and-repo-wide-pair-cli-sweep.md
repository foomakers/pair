# Decision: the staleness gate reads the BINARY, and the `pair-cli` rename follows the gate's reach, not the file list

## Date

2026-08-30

## Status

Active

## Category

Convention Adoption

## Context

ADL [2026-08-25-cli-invocation-canonical-name-is-pair-cli.md](2026-08-25-cli-invocation-canonical-name-is-pair-cli.md) settled the name (`pair-cli`, no alias) and scoped the sweep from refinement evidence: ten `metadata.ts` files, `reference/cli/{examples,workflows}.mdx`, `DEVELOPMENT.md`. Turning the gate on in story #449 broke that scope:

1. **The real reach is 29 docs pages, not 2** (one measured number, used throughout). The branch's rule over `origin/main`'s docs tree (`checkDocsCommands` over `git show origin/main:<page>`, all 84 pages): **78 wrong-binary errors across 28 published docs pages**, heaviest `reference/cli/commands.mdx` and `reference/cli/update-link.mdx`. The sweep changed **29**: those 28 plus `customization/adopt.mdx`, whose one occurrence is a trailing comment in a fenced tree diagram (`# Upstream guidelines (updated by pair update)`), outside the gate's positional reach, renamed for consistency. Refinement grepped two files; the gate greps all. The DoD requires `pnpm docs:staleness` green, so the gate defines the scope.
2. **Bare `pair` cannot be matched like `pair-cli`.** `pair` is also the product name in prose on nearly every page, so naively widening `INVOCATION_PREFIX` floods false positives. Two noise sources appeared, each needing a rule, not an allow-list (the old `PROSE_WORDS` list was deleted for that reason).
3. **A latent bug surfaced.** The span rule's leading `\s*` crosses newlines and a CLOSING FENCE ends with a backtick, so ` ``` ` then a paragraph opening "pair creates Markdown files" matched an invocation of `creates` — harmless while only `pair-cli` matched, 8 hard failures once bare `pair` counted.

## Decision

**The invocation rule captures the binary and judges it; the rename sweep follows wherever that rule reaches.**

1. `INVOCATION_PREFIX` captures the binary — `(pair-cli|pair)` — instead of pinning literal `pair-cli`. A bare `pair <cmd>` is reported **once**, as wrong binary, never also as an unknown command. `PUBLISHED_BIN` is the single place the canonical name is written **because the alternation is BUILT from it** (`` const BINARY = `(${PUBLISHED_BIN}|pair)` ``): as a regex literal the name lived in two places, and editing only the constant (as this decision instructs) blinded the gate to the NEW name while flagging still-correct old lines. Verified with `PUBLISHED_BIN = 'pairx'` — the two `[]` mean OPPOSITE things: **literal form** → `[]` for `pairx install` because the regex MATCHES NOTHING, while correct `pair-cli install` is flagged; **derived form** → `[]` for `pairx install` because it matches and is CORRECT, `pair install` flagged with `write "pairx install"`. The derived form also returns `[]` for `pair-cli install` — the superseded name goes SILENT, not red, so a rename must add it beside `pair` while the corpus carries it. `pair` stays a literal: the known-WRONG binary, not a second published name. **One error, but an honest one**: `write "pair-cli <cmd>"` is prescribed only when `<cmd>` is a real command dir; otherwise it says so (`and "init" is not one of its commands`) — `pair init` used to answer `write "pair-cli init"`, and complying produced `"pair-cli init" … is not a command`: two red rounds, the first wrong.
2. **The binary–command separator is ONE space, not `\s+`.** Aligned whitespace is a diagram column: the four PM-tool pages map their hierarchy under a fenced heading (`pair                    Linear`), which `\s+` read as "run `pair Linear`". A positional rule, not a per-page exception. A **TAB** is excluded for the same reason as two spaces; both are pinned, so an unflagged `pair-cli\t<cmd>` leads a reader to narrow the diagram, not re-widen to `\s+`.
3. **The span rule TOKENIZES code spans** (`` `…` ``) and anchors the prefix at the start of a span's CONTENT, not "after a backtick". Both weaker shapes misfired once: `` `\s* `` let a closing FENCE cross into the next paragraph (`pair creates Markdown files` → `creates`); its fix `` `[ \t]* `` still matched after ANY backtick, so a closing INLINE span followed by prose did it again (`` `config.json` pair skills resolve state `` → `skills`) — real, since `pair` is the product name on ~10 pages and the advice would corrupt the sentence. Tokenizing removes the class — a fence yields no span (a span needs a non-backtick character between delimiters) — and both cases are pinned. It follows CommonMark's closer rule: an opening run of N backticks closes at the first run of exactly N; content may hold runs of other lengths. Pairing single backticks seemed enough because a **doubled** delimiter (` ``pair install`` `) still had its content read (the scan retries one character on, pairing the inner delimiters), but it consumed ONE of the two closers and the leftover flipped span parity for the REST OF THE LINE, silently hiding later inline invocations. Balancing the run alone fails too: doubling exists to quote a BACKTICKED literal, so content holds backticks — the shape of both lines carrying doubled spans (`reference/skill-management.mdx:211`, two spans; `:219`, one). Measured: an inline `pair install` span appended to `:219` → naive rule `PASS — 44 skills, 11 commands in sync`, closer rule `FAIL — 1 issue … write "pair-cli install"`. Doubling is NOT an exemption: the wrong-form exclusion below covers source fixtures and comments; on a docs PAGE a wrong form is shown in unbackticked prose, which this rule does not reach. Content may neither begin nor end with a backtick, so a fence still yields no span. Pinned: the doubled span, its backticked content and line-mates; the FENCE through what it can change — the fence pass's own cases and the closing fence not reaching the next paragraph — since "a fence yields no span" is not assertable via `checkDocsCommands` (the fence pass scans fenced lines regardless and errors dedup by binary+command).
4. **The runner prefix lists every runner the docs PUBLISH, not `npx` alone.** Also published: `pnpm dlx pair-cli install`, `pnpm dlx pair-cli update-link --dry-run` (`reference/cli/workflows.mdx`), `pnpm pair-cli install` (`tutorials/team-setup.mdx`), `pnpm pair-cli --version` (`tutorials/first-project.mdx`). Dropping `-cli` on any returned `[]`, and `pnpm dlx pair-cli kb validate` was invisible. `npx` / `pnpm dlx` / `pnpm exec` / `yarn dlx` consume a flag run; a **bare package manager (`pnpm <bin> <cmd>`) does not** — load-bearing: `pnpm --filter <pkg>` puts a PACKAGE NAME in flag-argument position and this repo's package is `pair-cli`, so `pnpm --filter @pair/pair-cli build` would read as the nonexistent command `build`, on three correct pages. Both halves pinned, as are package-install forms (`pnpm add -D @foomakers/pair-cli`, `npm install -g …`), which stay unflagged. **A flag whose ARGUMENT is a package name is consumed WITH it**; the listed runners have one — `--package`/`-p` (`RUNNER_FLAG`). As a lone flag it broke both directions of the npx idiom for a bin differing from its package: `npx --package @foomakers/pair-cli pair-cli install` (correct) read `@foomakers/` as scope, first `pair-cli` as binary, the real binary as command (`"pair-cli pair-cli" … is not a command`) — CI red with no fix but deleting a correct line; `npx --package=@foomakers/pair-cli pair install` returned `[]` (no `=value` form) — drift shipping green. Both spellings, both directions, pinned. Adding a runner is a one-token edit: add its package/name-argument flags to `RUNNER_FLAG`'s first alternative, and give the flag run only to a runner whose such flags are all listed — bare `pnpm`, with `--filter` deliberately unlisted, is the counter-example.
5. **Scope = every surface that documents or prints an invocation** — the ADL's own rule ("no dual naming") applied honestly:
   - all 11 command `metadata.ts` files (the ten **plus `run`**, added by #451 after refinement);
   - **the `Usage:` line the CLI PRINTS**, built from `program.name()`, which was `pkg.name` — `pair-cli install --help` opened `Usage: @pair/pair-cli install [options]`, answering `command not found: @pair/pair-cli`. The program is named from the manifest's sole `bin` KEY (`publishedBinName`), the key the registry gate reads, passed plain without the old `chalk.blue()` (ANSI escapes in a copy-pasteable line are a defect; the banner keeps the brand color). `metadata.usage` is now RENDERED (`cmd.usage(...)`, prefix stripped since Commander prints the `Usage: <bin> <command>` head): it was never passed to Commander, so the eleven renamed `usage:` strings appeared nowhere a user could read them. AC1 names this surface; gating an unrendered field is the story's failure mode one level up;
   - every printed `pair-cli` hint/usage/error string in `apps/pair-cli/src` and the `scaffold-kb` templates it generates into a user's KB repo;
   - the `pair-cli update` regenerate hints printed by `packages/knowledge-hub`'s mirror tools;
   - the **shipped KB dataset**, `packages/knowledge-hub/dataset/**` — 24 spans in 7 files (`working-area.md` 12, `.skills/loop/SKILL.md` 3, `guided-quick-setup.md` 4, `tier-aware-pipeline.md` 2, `delivery-metrics.md`, `skill-conventions/README.md`, `.workflows/pair-loop.js` 1 each). Sharpest failure: after `pair-cli install`, every command named in the installed `.pair/knowledge/guidelines/collaboration/working-area.md` is `command not found`. The dataset is canonical; twins under root `.pair/knowledge/**` and `.claude/**` are regenerated by the real `pair-cli update`, never hand-edited (DEVELOPMENT.md's two-step remedy);
   - `scripts/workflows/release/**` — operator-run release scripts: printed hints (`Please run 'pair-cli install' first`), the comments describing them, and **two executable lines in `smoke-test-kb-package.sh`**. Its detection probed `command -v pair` and `node_modules/.bin/pair` — a binary no install creates — so with `pair-cli` npm-installed it aborted `❌ Error: pair CLI not found`; it then ran `$PAIR_CMD kb package --output …`, a hyphen-less `kb <sub>` form (AC3's defect class) the CLI answers `error: unknown option '--output'` (`package` is top-level; `kb` is no group). Both fixed, not renamed into a more confident wrong claim. Sibling `smoke-test-npm-artifact.sh` had the same defect and the first sweep renamed only its echo strings: `PAIR_BIN`/`INSTALLED_BIN` pointed at `node_modules/.bin/pair` (npm never creates it; the one bin key is `pair-cli`), so Test A fell through to `npx pair-cli` outside the artifact, Test B warned and skipped, the standardized suite was skipped, and it printed `completed successfully`, exit **0** — a green release gate that exercised nothing. Paths corrected and **"binary not found" warnings are now hard failures**: warn-and-continue hid the wrong path;

Deliberately **out** of scope, left bare: `scripts/smoke-tests/**/*.sh` — every `.sh` at any depth, `scenarios/` and `lib/` included (`run_pair` is a shell function, not the binary, with its comments and log lines); `.github/workflows/*.yml` step _names_; the product name in prose ("pair installs bridge files", "the same shape pair runs"); and **fixtures or comments that deliberately QUOTE the wrong form as the illustrated defect** — **every bare `pair <cmd>` in `apps/website/lib/docs-staleness-check.ts`'s docstrings and comments** (11 spans today, e.g. `npx --package=… pair install` returned `[]`, `"pair creates Markdown files"` read as `creates`, `` `config.json` pair skills resolve state ``, `pair v0.5.0` as a version banner), the wrong-binary cases in `docs-staleness-check.test.ts`, and `commands/index.test.ts`'s quote of the shipped `usage: 'pair run [options]'`. Renaming them erases the evidence. **The exclusion is per FILE, not per line**: written as `docs-staleness-check.ts:499,510-511`, it was off by four on arrival (`:499` is the `RUNNER_FLAG` sentence, no wrong form; the intended `npx --package=… pair install` is `:495`) and later rounds added uncovered spans — a literal sweep would have skipped `:499` and renamed a protected quote. Same reason keeps the **append-only historical records** — `.pair/adoption/decision-log/**`, `.pair/adoption/tech/adr/**`, the CHANGELOGs, including ADL 2026-07-31's Context recording that all three places once said `pair update`. That exclusion stops at history; live adoption documents are in scope (above). `.pair/llms.txt`'s one remaining hit is the generated index entry for such a record's title, so it follows it. `qa/release-validation/*.md` was on this list until review ("headings only"), but its three expected-output assertions were never covered by that rationale, so the whole directory moved in scope (headings included, no mixed convention per file). **`scripts/smoke-tests/README.md` moved in scope too**: the directory exclusion's `run_pair` rationale does not cover its §1–§7, which describe scenarios in the reader's terms ("Verifies the `pair install` command", "(`pair install ./target`)") — copied into a shell, `command not found: pair`. The exclusion is narrowed to `scripts/smoke-tests/**/*.sh` (segment-crossing `**/*` on purpose: a literal `**.sh` degrades to `*.sh` within one segment under bash globstar and minimatch, leaving `scenarios/install-basic.sh` and `lib/ci-tests.sh` — where `run_pair` lives — in scope), and the seven spans plus `--binary`'s "Path to the `pair` executable" are renamed. No gate sees this file (`docs:staleness` scopes `apps/website/content/docs` only) — convention, checked by review, like `DEVELOPMENT.md`.

## Alternatives Considered

- **Keep the ADL's file list and narrow the gate to it**: rejected — a gate that looks only where drift is already fixed cannot catch the next regression.
- **Restrict the bare-`pair` command token to lowercase** (`[a-z]…`) to exclude `pair Linear` / `pair Filesystem`: rejected as discriminator — it works on today's four diagrams by capitalization, but _alignment_ is what makes them diagrams; the single-space rule holds for a lowercase label.
- **Re-indent the PM-tool diagrams** so `pair` is not at line start: rejected — bends docs to a regex, wrong for the next diagram.
- **Rename bare `pair <cmd>` only in `apps/pair-cli` source comments, leaving strings**: rejected as a half-measure — a mixed convention let the drift start. The first pass produced one by accident the OTHER way (three `knowledge-hub/src/tools/*.ts` comments renamed, the fourth file there and 26 spans elsewhere bare); the scope clause now states the comment boundary.
- **Compare the registry usage/examples gate to the literal `'pair-cli '`**: rejected — the name would live in three places (`apps/pair-cli/package.json`'s `bin`, `PUBLISHED_BIN`, the literal); renaming `bin` would leave all 11 usage strings naming a binary no install creates, gate green. The test reads the sole `bin` key; verified with `bin` renamed to `pairc`: 72 offenders, where the literal form reported none.
- **Have `apps/website` read the name from `apps/pair-cli/package.json` too**: rejected — couples a separately deployable app to the CLI manifest for one string. Safe transitively: `PUBLISHED_BIN = 'pair-cli'` is a single literal in the website (the alternation is built from it, decision 1), so a rename is a one-line edit, and the **CLI registry gate** reading the `bin` key reddens on all 11 usage strings (72 offenders under `pairc`), so a `bin` rename cannot land with the docs gate prescribing the old name.
- **Keep gating `metadata.usage` unrendered** (or drop it and gate `examples` only): rejected — the first produced this round's false confidence, the second discards a written line. The field feeds `cmd.usage()` and the gate checks the full `<bin> <command>` prefix (plus trailing space), so gate and reader assert the same string; a drifting `usage` falls back to Commander's generated line instead of a doubled one, a branch the gate keeps dead.
- **Leave the release smoke test's binary probe a warning** (`Warning: … Skipping suite`): rejected — it let a broken path survive a rename pass, a run identical to a pass. It exits 1, verified against a fixture whose bin key is `pair` (see Consequences).

## Consequences

- The diff is a string rename across `apps/website`, `apps/pair-cli`, `packages/knowledge-hub` (dataset + regenerated twins), `qa/release-validation`, `scripts/workflows/release` and root `DEVELOPMENT.md`, wider than the ~15 files the ADL predicted — **except in four places**, called out for review: the staleness rule (`apps/website/lib/docs-staleness-check.ts`, tested); the two executable lines in `smoke-test-kb-package.sh`; the CLI program name plus the newly rendered `cmd.usage()` (`apps/pair-cli/src/cli.ts`, tested against RENDERED help, not the registry field); `smoke-test-npm-artifact.sh`'s binary path and warning→failure change. Neither release script is gated (in neither `scripts/smoke-tests/**` nor CI outside the release workflow), so both were verified by running the real script against a fixture artifact. `risk:yellow` (carried by Change/diff risk) is unchanged in kind: multi-module, mostly a rename.
- The dataset rename is applied to the CANONICAL source only; root `.pair/knowledge/**`, `.claude/skills/**`, `.claude/workflows/**` are OUTPUT of a real `pair-cli update` here, verified by the three mirror guards (`mirror-guard`, `skill-md-mirror`, `workflow-mirror`, 630 assertions).
- Two `packages/knowledge-hub` assertions (`mirror-guard.test.ts`, `skill-md-mirror.test.ts`) pinning the printed regenerate hint were updated — text only.
- A bare `pair <cmd>` in any published docs page fails CI, not a reader's copy-paste.
- `AC5`'s `organization.mdx` occurrence was resolved before this story — zero repo-wide; untouched here. `AC3` has two halves: the `pair kb validate` FORM was already zero (`git show origin/main:…/reference/cli/examples.mdx | grep -c 'pair kb validate'` → 0), but every invocation on `reference/cli/{examples,workflows}.mdx` naming `pair-cli` was NOT true on `origin/main` — **67 lines across those two pages are renamed here** (`git diff origin/main...HEAD --numstat`: 43 + 24), e.g. `pair install --list-targets` → `pair-cli install --list-targets`; AC3 is satisfied BY this branch. **Sibling `pair kb package`** survived in `scripts/workflows/release/` (twice as prose, once live): the AC was checked by grepping one name, not the hyphen-less _form_ — keep the form as the check.
- **Two gates were added, not one.** `docs:staleness` guards docs; the CLI's OWN help had nothing. `apps/pair-cli/src/commands/index.test.ts` asserts every registry `usage` and `examples` entry starts with the `pair-cli` prefix (binary plus one space) — where 11 drifted files lived, and where `run/metadata.ts` arrived from #451 with `usage: 'pair run [options]'` while ts:check, lint, the full suite and docs:staleness stayed green.
- **The release npm-artifact smoke test was a no-op, now real.** Verified with a fixture `@foomakers/pair-cli` tarball whose `bin.pair-cli` execs the real built CLI: BEFORE, 18 lines — `Warning: Test B skipped`, `Warning: Installed binary not found … Skipping suite`, `NPM artifact smoke-test completed successfully`, **exit 0**; AFTER, 1240 lines — Test A and B run the installed binary and `run-all.sh --binary …/node_modules/.bin/pair-cli --ci --offline-only` runs the standardized suite. A fixture declaring `bin.pair` exits **1** with `Error: the installed artifact linked no executable at …/.bin/pair-cli`.
- **The npx form was never actually gated.** The old prefix spelled the runner as a package _slot_ plus a required literal binary (`npx\s+(?:--no\s+)?@?[\w/.-]+\s+(pair-cli|pair)` plus a space), so the documented `npx --no @foomakers/pair-cli <cmd>` (five pages) never matched and a misspelled command behind npx shipped silently; the one npx test passed only because `--no` was swallowed as the package token. The runner is now a **prefix of the captured binary** (`npx [flags]`, then optional `@scope/` and `@version` around it).
