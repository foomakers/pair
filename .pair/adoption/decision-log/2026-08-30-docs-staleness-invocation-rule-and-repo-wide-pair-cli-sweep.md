# Decision: the staleness gate reads the BINARY, and the `pair-cli` rename follows the gate's reach, not the file list

## Date

2026-08-30

## Status

Active

## Category

Convention Adoption

## Context

ADL [2026-08-25-cli-invocation-canonical-name-is-pair-cli.md](2026-08-25-cli-invocation-canonical-name-is-pair-cli.md) settled the name (`pair-cli`, no alias) and scoped the sweep from the evidence available at refinement: ten `metadata.ts` files, `reference/cli/{examples,workflows}.mdx`, `DEVELOPMENT.md`. Implementing story #449 turned the gate on and the scope did not survive contact:

1. **The real reach is 29 docs pages, not 2.** ONE measured number, used everywhere below. Run the branch's rule against `origin/main`'s docs tree (`checkDocsCommands` over `git show origin/main:<page>`, all 84 pages): **78 wrong-binary errors across 28 published docs pages**, `reference/cli/commands.mdx` and `reference/cli/update-link.mdx` the two heaviest. The sweep changed **29** pages — those 28 plus `customization/adopt.mdx`, whose single occurrence sits in a trailing comment inside a fenced tree diagram (`# Upstream guidelines (updated by pair update)`), outside the gate's positional reach and renamed for consistency rather than to satisfy the gate. Refinement's list came from grepping two files; the gate greps all of them. The story's Definition of Done requires `pnpm docs:staleness` green, so the file list is not a choice: the gate defines the scope, and the one page beyond it is named here rather than hidden in the count.
2. **Bare `pair` cannot be matched with the same shape as `pair-cli`.** `pair` is also the product's name and appears in prose on nearly every page, so widening `INVOCATION_PREFIX` naively turns the gate into a false-positive generator. Two distinct sources of noise showed up immediately, each needing a rule, not an allow-list (the previous `PROSE_WORDS` list was deleted for exactly that reason).
3. **A latent bug in the existing rule surfaced.** The span rule's leading `\s*` crosses newlines, and a CLOSING FENCE ends with a backtick — so `` ``` `` followed by a paragraph opening with "pair creates Markdown files" matched as an invocation of `creates`. Harmless while only `pair-cli` matched (paragraphs rarely open with it); 8 hard failures the moment bare `pair` counted.

## Decision

**The invocation rule captures the binary and judges it; the rename sweep follows wherever that rule reaches.**

1. `INVOCATION_PREFIX` captures the binary — `(pair-cli|pair)` — instead of pinning the literal `pair-cli`. A bare `pair <cmd>` is reported as its own error (wrong binary), **once**, and is never also reported as an unknown command. `PUBLISHED_BIN` is the single place the canonical name is written. **One error, but an honest one**: the message only prescribes `write "pair-cli <cmd>"` when `<cmd>` is a real command dir; otherwise it says so (`and "init" is not one of its commands`). Reporting once must not mean recommending a replacement that does not exist — `pair init` used to answer `write "pair-cli init"`, and the writer who complied got `"pair-cli init" … is not a command` on the next run: two red rounds, the first of them wrong.
2. **The separator between binary and command is ONE space, not `\s+`.** A run of aligned whitespace is a diagram column, never an invocation — the four PM-tool pages map their hierarchy under a fenced heading (`pair                    Linear`), which `\s+` reads as "run `pair Linear`". This is a positional rule in the same spirit as the existing one, not a per-page exception. It excludes a **TAB** for the same reason it excludes two spaces — a tab is column alignment by definition — and both exclusions are now pinned in the suite so a later reader meeting an unflagged `pair-cli\t<cmd>` narrows the diagram rather than re-widening the separator back to `\s+`.
3. **The span rule TOKENIZES code spans** (`` `…` `` pairs) and anchors the prefix at the start of a span's CONTENT — it does not scan for the prefix "after a backtick". Both weaker shapes misfired once each, in the same direction: `` `\s* `` let a closing FENCE cross the newline into the paragraph below (`pair creates Markdown files` → an invocation of `creates`), and its fix, `` `[ \t]* ``, still matched after ANY backtick — so a closing INLINE span followed by prose on the same line did it again (`` `config.json` pair skills resolve state `` → an invocation of `skills`). The second is not hypothetical noise: `pair` is the product name on ~10 docs pages, so the gate would have turned a correct edit red with advice that corrupts the sentence. Tokenizing removes the class instead of the two cases — a fence yields no span at all (a span needs a non-backtick character between its delimiters) — and both cases are pinned.
4. **The runner prefix lists every runner the docs PUBLISH, not `npx` alone.** `npx` was the only one recognised, and the corpus publishes three more forms today: `pnpm dlx pair-cli install` and `pnpm dlx pair-cli update-link --dry-run` (`reference/cli/workflows.mdx`), `pnpm pair-cli install` (`tutorials/team-setup.mdx`), `pnpm pair-cli --version` (`tutorials/first-project.mdx`). Drop the `-cli` on any of them and `checkDocsCommands` returned `[]` — the exact drift this story exists to catch, on a form the site actually ships — and an unknown command behind the same runner (`pnpm dlx pair-cli kb validate`) was invisible too. `npx` / `pnpm dlx` / `pnpm exec` / `yarn dlx` consume a flag run; a **bare package manager (`pnpm <bin> <cmd>`) does not**, and that asymmetry is load-bearing rather than an oversight: `pnpm --filter <pkg>` puts a PACKAGE NAME in flag-argument position and this repo's package is literally called `pair-cli`, so consuming the `--filter` flag together with its argument would read the filter's argument as the binary and the script name as its command — `pnpm --filter @pair/pair-cli build` reported as the nonexistent command `build`, on three pages correct as written. Both halves are pinned in the suite, as are the package-install forms (`pnpm add -D @foomakers/pair-cli`, `npm install -g …`), which are not invocations and must stay unflagged. Adding a runner is a one-token edit; give it the flag run only if its flags cannot take a package argument.
5. **Scope = every surface that documents or prints an invocation**, which is the ADL's own business rule ("no dual naming") applied honestly:
   - all 11 command `metadata.ts` files (the ten enumerated **plus `run`**, added by #451 after refinement);
   - **the `Usage:` line the CLI actually PRINTS**, which is built from `program.name()` and was `pkg.name` — so `pair-cli install --help` opened with `Usage: @pair/pair-cli install [options]`, a copy-pasteable line that answers `command not found: @pair/pair-cli`. The program is named from the sole `bin` KEY of the manifest (`publishedBinName`), the same key the registry gate reads. And `metadata.usage` is now RENDERED (`cmd.usage(...)`, prefix stripped because Commander prints the `Usage: <bin> <command>` head itself): it was dead — never passed to Commander anywhere — so the eleven renamed `usage:` strings appeared nowhere a user could read them while the one line they did read named the package. AC1 names this surface explicitly; a gate on an unrendered field is the story's own failure mode one level up;
   - every `pair-cli` printed hint/usage/error string in `apps/pair-cli/src` and in the `scaffold-kb` templates it generates into a user's KB repo;
   - the `pair-cli update` regenerate hints printed by `packages/knowledge-hub`'s mirror tools;
   - the **shipped KB dataset**, `packages/knowledge-hub/dataset/**` — 24 spans over 7 files (`working-area.md` 12, `.skills/loop/SKILL.md` 3, `guided-quick-setup.md` 4, `tier-aware-pipeline.md` 2, `delivery-metrics.md`, `skill-conventions/README.md`, `.workflows/pair-loop.js` 1 each). This is the surface with the SHARPEST failure: a consumer runs `pair-cli install`, opens the installed `.pair/knowledge/guidelines/collaboration/working-area.md`, and every command it names is `command not found`. The dataset is the canonical source; the generated twins under root `.pair/knowledge/**` and `.claude/**` are regenerated by running the real `pair-cli update`, never hand-edited (DEVELOPMENT.md's two-step remedy);
   - `scripts/workflows/release/**` — the release scripts an operator runs by hand: printed hints (`Please run 'pair-cli install' first`), the comments describing the same invocations, and **two executable lines in `smoke-test-kb-package.sh`** that are not strings at all. Its CLI detection probed `command -v pair` and `node_modules/.bin/pair` — a binary no install creates — so on a repo where `pair-cli` IS npm-installed the script aborted with `❌ Error: pair CLI not found`; and it then ran `$PAIR_CMD kb package --output …`, a hyphen-less `kb <sub>` form (AC3's own defect class) that the real CLI answers with `error: unknown option '--output'`, since `package` is a top-level command and `kb` is not a command group. Both fixed here rather than renamed into a more confident wrong claim. Its SIBLING `smoke-test-npm-artifact.sh` carried the identical defect and the first sweep renamed only the echo strings around it: `PAIR_BIN`/`INSTALLED_BIN` pointed at `node_modules/.bin/pair`, a path npm never creates (the package declares one bin key, `pair-cli`), so Test A fell through to `npx pair-cli` — resolving outside the artifact under test — Test B warned and skipped, the standardized suite was skipped, and the script printed `completed successfully` and exited **0**. A release gate green having exercised nothing. Paths corrected, and **the "binary not found" warnings are now hard failures**: a smoke test that cannot find the binary it just installed has not passed, it has not run — warning-and-continue is what hid the wrong path for as long as it lived;
   - `qa/release-validation/*.md` — including the **expected-output assertions** ("Error message suggests using `pair-cli update` instead"), which pin the exact string `install/handler.ts` and `update/handler.ts` print and would otherwise assert output the CLI no longer produces, the `**Scope**:` lines, and the `MT-*` headings;
   - all 29 docs pages, `DEVELOPMENT.md`, **`.gitignore`** (its "Generated by `pair-cli update`" header: a developer-facing instruction in the file most likely to be opened when those generated markers look stale) and the **LIVE adoption documents** — `tech/boundedcontext/integration-process-standardization.md`, `product/subdomain/collaborative-workflow.context.md`. Live adoption prose is current-state, not history, so the record-preserving reason that protects `decision-log/**` and the CHANGELOGs does not reach it;
   - **source code comments and test names naming an invocation, repo-wide** — 29 spans over 16 files in `packages/content-ops`, `packages/knowledge-hub` (`tools/skills-guide-mirror.ts` + 8 conformance suites), `packages/dev-tools` and `apps/website/lib/docs-staleness-check.ts` itself. Not decoration: a contributor opens `skills-guide-mirror.ts` and runs the `pair update` its docstring names, and gets `command not found`; `content-ops/src/observability.ts` carried a full runnable line with flags (`pair kb-validate --path ./downloaded-kb`). Nothing gates comments, so a partial sweep is invisible — which is why the boundary is stated here rather than left to whoever grepped last;
   - `packages/dev-tools/src/quality-gates/pre-push-gate-composition.ts` — `PRE_PUSH_REMEDY` is the PRINTED half of the two-step remedy ADL [2026-07-31-pre-push-gate-is-check-only.md](2026-07-31-pre-push-gate-is-check-only.md) requires to agree in three places (`DEVELOPMENT.md`, the `development-setup.mdx` twin, this string). The first sweep renamed the two documents and missed the string, so the terminal and `DEVELOPMENT.md` named two mutually exclusive commands and the copy-pasted one did not exist. Now pinned by a unit test (`toContain('pair-cli update')` plus a negative on the bare form), so the third place cannot drift again.

Deliberately **out** of scope, and left bare: `scripts/smoke-tests/**.sh` (`run_pair` is a shell function, not the binary — including its comments and log lines, which describe that function); `.github/workflows/*.yml` step *names*; the product name in prose ("pair installs bridge files", "the same shape pair runs"), which is not an invocation; and **fixtures or comments that deliberately QUOTE the wrong form as the defect being illustrated** — `docs-staleness-check.ts:499,510-511`, the wrong-binary cases in `docs-staleness-check.test.ts`, and `commands/index.test.ts`'s quote of the `usage: 'pair run [options]'` that shipped. Renaming those would erase the evidence the gate exists for. The same reason keeps the **append-only historical records** untouched — `.pair/adoption/decision-log/**`, `.pair/adoption/tech/adr/**` and the CHANGELOGs, including ADL 2026-07-31's Context where it records that all three places once said `pair update`. That exclusion is about *history*, and it stops at history: live adoption documents state current facts and are in scope (above). `.pair/llms.txt`'s one remaining hit is the generated index entry for such a record's title — derived from an excluded file, so it follows it. `qa/release-validation/*.md` was ALSO on this list until review: the exclusion was written as "headings only", but the same files carry three expected-output assertions an operator compares against the real error message, so the recorded rationale never covered them and the whole directory moved in scope (headings included, rather than leaving a mixed convention inside one file). **`scripts/smoke-tests/README.md` moved in scope for the same reason** — the exclusion was path-scoped to the whole directory on a rationale about `run_pair`, and that README's §1–§7 describe what each scenario verifies in the reader's own terms ("Verifies the `pair install` command", "(`pair install ./target`)"), not what `run_pair` does; a contributor with the CLI npm-installed copies one into a shell and gets `command not found: pair`. The exclusion is therefore narrowed to `scripts/smoke-tests/**.sh`, and the seven spans plus `--binary`'s "Path to the `pair` executable" are renamed. No gate can see this file — `docs:staleness` scopes `apps/website/content/docs` only — so it is convention, checked by review, exactly as `DEVELOPMENT.md` is.

## Alternatives Considered

- **Keep the sweep to the ADL's file list and narrow the gate to those files**: rejected. A gate that only looks where the drift has already been fixed cannot catch the next regression — the exact failure mode this story exists to close.
- **Restrict the bare-`pair` command token to lowercase** (`[a-z]…`) to exclude `pair Linear` / `pair Filesystem`: rejected as the discriminator. It happens to work on today's four diagrams because their next word is capitalized, but the property that makes them diagrams is the *alignment*, not the capitalization; the single-space rule states the real reason and stays true for a lowercase diagram label.
- **Fix the PM-tool diagrams instead of the rule** (re-indent so `pair` is not at line start): rejected — bending documentation to a regex, and the rule would still be wrong for the next diagram.
- **Also rename bare `pair <cmd>` inside `apps/pair-cli` source comments only, leaving strings**: rejected as a half-measure — the comments describe the same invocations, and a mixed convention is what let the drift start. The first pass then produced that same mixed convention by accident in the OTHER direction (three `knowledge-hub/src/tools/*.ts` comments renamed, the fourth file in the same directory and 26 spans elsewhere left bare); the scope clause above now states the comment boundary explicitly instead of leaving it to be inferred from the diff.
- **Compare the registry usage/examples gate against the literal `'pair-cli '`**: rejected. The canonical name would then be written in three independent places (`apps/pair-cli/package.json`'s `bin`, `PUBLISHED_BIN`, the literal), and renaming the `bin` key would leave all 11 usage strings naming a binary no install creates while the gate built to catch exactly that stayed green — the story's own failure mode, one level up. The test reads the sole `bin` key from the manifest instead. Verified: with `bin` temporarily renamed to `pairc`, the gate reports 72 offenders where the literal form reported none.
- **Have `apps/website` read the canonical name from `apps/pair-cli/package.json` too** (symmetry with the registry gate): rejected — it would couple a separately deployable app to the CLI's manifest for one string. The asymmetry is deliberate and safe transitively: `PUBLISHED_BIN = 'pair-cli'` is a literal in the website package, and what protects it is the **CLI registry gate**, which reads the sole `bin` key rather than a literal — renaming `bin` turns that gate red on all 11 usage strings (72 offenders under the `pairc` mutation above), so a `bin` rename cannot land with the docs gate silently still prescribing the old name.
- **Keep gating `metadata.usage` without rendering it** (or drop the field and gate `examples` only): rejected — the first is what produced the false confidence this round found, the second throws away a written line rather than printing it. The field is wired into `cmd.usage()` and the gate tightened to the full `<bin> <command>` prefix (plus its trailing space), so gate and reader now assert the same string. A `usage` that drifts from that prefix falls back to Commander's generated line instead of printing a doubled one, and the tightened gate keeps that branch dead.
- **Leave the release smoke test's binary probe a warning** (`Warning: … Skipping suite`): rejected. That is the property that let a broken path survive a rename pass in the adjacent lines — the run looked identical to a passing one. It exits 1 now; verified against a fixture artifact whose bin key is `pair` (see Consequences).

## Consequences

- The diff is a string rename across `apps/website`, `apps/pair-cli`, `packages/knowledge-hub` (dataset + its regenerated twins), `qa/release-validation`, `scripts/workflows/release` and root `DEVELOPMENT.md` instead of the ~15 files the ADL predicted — mechanical and wider than the refinement estimate. It is a string rename **except in four places**, all called out for review: the staleness rule itself (`apps/website/lib/docs-staleness-check.ts`, tested); the two executable lines in `smoke-test-kb-package.sh`; the CLI's program name plus the newly rendered `cmd.usage()` (`apps/pair-cli/src/cli.ts`, tested against the RENDERED help, not the registry field); and `smoke-test-npm-artifact.sh`'s binary path plus its warning→failure change. Neither release script has an automated gate — they are in neither `scripts/smoke-tests/**` nor CI outside the release workflow — so both were verified by running the real script against a fixture artifact. The story's `risk:yellow` (carried by Change/diff risk) is unchanged in kind: still multi-module, still overwhelmingly a rename.
- The dataset rename is applied to the CANONICAL source only; root `.pair/knowledge/**`, `.claude/skills/**` and `.claude/workflows/**` are the OUTPUT of a real `pair-cli update` run in this repo, and the three mirror guards (`mirror-guard`, `skill-md-mirror`, `workflow-mirror`, 630 assertions) verify it.
- Two existing assertions in `packages/knowledge-hub` (`mirror-guard.test.ts`, `skill-md-mirror.test.ts`) pin the printed regenerate hint and were updated to the new string — assertion text only, no behavior change.
- The gate now fails on a bare `pair <cmd>` in any published docs page, so a regression back to the wrong name is caught at CI, not by a reader whose copy-paste fails.
- `AC5`'s `organization.mdx` occurrence was already resolved before this story started — verified zero repo-wide; nothing to change. `AC3`'s `pair kb validate` was too, but its **sibling `pair kb package` was not**: it survived in `scripts/workflows/release/`, twice as prose and once as a live invocation. The AC was checked by grepping one command name, not the hyphen-less *form* — so the form is the check to keep, not the string.
- **Two gates were added, not one.** `docs:staleness` guards the docs tree; the CLI's OWN help text had nothing. `apps/pair-cli/src/commands/index.test.ts` now asserts every `usage` and every `examples` entry in the command registry starts with the `pair-cli` prefix (binary plus one space) — the surface where 11 of the drifted files lived, and where `run/metadata.ts` arrived from #451 carrying `usage: 'pair run [options]'` while ts:check, lint, the full suite and docs:staleness all stayed green.
- **The release npm-artifact smoke test was a no-op, and is now real.** Verified by packing a fixture `@foomakers/pair-cli` tarball whose `bin.pair-cli` execs the real built CLI and running the actual script against it: BEFORE, the whole run was 18 lines — `Warning: Test B skipped`, `Warning: Installed binary not found … Skipping suite`, `NPM artifact smoke-test completed successfully`, **exit 0**. AFTER, the same artifact produces a 1240-line run: Test A and Test B execute the installed binary and `run-all.sh --binary …/node_modules/.bin/pair-cli --ci --offline-only` runs the whole standardized suite against it. A second fixture, identical but declaring `bin.pair`, exits **1** with `Error: the installed artifact linked no executable at …/.bin/pair-cli` — the hard-failure branch.
- **The npx form was never actually gated.** The pre-existing prefix spelled the runner as a package *slot* followed by a still-required literal binary (`npx\s+(?:--no\s+)?@?[\w/.-]+\s+(pair-cli|pair)` plus a space), so the real documented form — `npx --no @foomakers/pair-cli <cmd>`, used on five pages — could not match at all and a misspelled command behind npx shipped silently. The suite's single npx test passed only because `--no` was swallowed as the package token. The runner is now a **prefix of the captured binary** (`npx [flags]` then optional `@scope/` and optional `@version` around it), so scope and version attach to the binary instead of hiding it.

## Adoption Impact

- `.pair/adoption/tech/infrastructure.md` — the existing canonical-name line gains the enforcement fact: the name is now checked by the website's `docs:staleness` gate, which errors on a bare `pair <cmd>`. Cross-references this ADL.
- No change to `tech-stack.md` or `way-of-working.md` — no new tool, no new process; the gate already existed and already ran in CI.
