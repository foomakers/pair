# Decision: /pair-process-review forwards a PR IDENTIFIER to verify-quality, never the resolved tier — and a supplied `$pr` never falls through

## Date

2026-08-11

## Status

Active

## Category

Process Decision

## Context

`/pair-capability-verify-quality` resolves the `risk:*` tier from the **current-branch** PR (`gh pr view` with no argument) — the standalone pre-push flow. `/pair-process-review` composes it from a context that is usually **not** the PR's branch (a detached review worktree, a bare-repo review session), so the no-arg read finds no PR, resolution fail-safes to 🔴, and review runs the full suite set on every PR regardless of tier. The tier-check parity #259 established for pre-push never held on the review path — the one compared against the CI gate.

The question is **what crosses the composition boundary**: `/pair-process-review` already resolved an authoritative review-time tier in Phase 1 (`/pair-capability-classify`, confirm-or-raise, D17), so handing that value over is the obvious move — and the wrong one.

## Decision

`verify-quality` takes an **optional `$pr` argument that names WHICH PR the tier is resolved from**. The tier itself is **read, never carried**:

1. **Name the PR, never carry the tier.** `$pr` is an identifier (number or URL). `verify-quality` reads that PR's `risk:*` labels from the **code host** — the source CI reads. No second copy of the tier, no widen-only guard of its own: the labels stay the single source of truth, review-raised (D17) tags included.
2. **No story-card fallback on the `$pr` path.** Precedence is `$pr` → current-branch PR → `$story` card → fail-safe 🔴; an entry is consulted only when the earlier ones were **not supplied** — never as a retry of one that failed. A supplied `$pr` with no tag fail-safes with its own reason ("reachable but carries no `risk:*` tag" vs. "unreadable"), decided by a **`risk:`-prefix test on the labels, not by empty labels** — a PR with `pr-state:*`/`cost:*`/type labels and no `risk:*` is normal once the PR state flow is provisioned.
3. **Tier parity is not result parity — and both report rows are RESOLVED, not improvised.** `$pr` makes the *tier* exact, not the *result*: off-branch the suites run against the checked-out tree. The report states `Tier source:` and `Tree:` separately; the caller's advisory rule keys on the `Tree:` row's **resolved value** (decision 5), and for the PR state synthesis the authoritative signal is CI's check on the PR head commit, read by a **named, routed** command (`gh pr checks` on GitHub — an unnamed read on the input deciding `ready-to-merge` is a guess). Both rows are snippet variables with one value per rendered arm — `TREE_MATCH` and `TIER_SOURCE` — because an improvising agent has no true arm for "a PR was named but could not be read" (`PR #N (named by $pr)` asserts a tier from an unreadable PR; `fail-safe — no source resolved` denies a named source). The modes that read **no tag at all** — the `Pre-merge tiering: disabled` default and the matrix-not-found fallback — **assign** `TIER_SOURCE` (`n/a (tiering disabled — no tag read)` / `n/a (matrix fallback — no tag read)`); otherwise the live default renders the `fail-safe — no source resolved` initializer on a run that never attempted a tier read. A conformance property requires **exact correspondence in both directions** between assigned values and rendered arms of each row, so a prose-only arm fails.
4. **The tree question is tier-independent, and it is a COMMIT question — on BOTH resolution paths, from ONE read.** `Tree:` is resolved *before* the `Pre-merge tiering` flag is read, including for the **checked-out branch's own PR**: one read point serves the `$pr` and no-arg paths, so the row and its ⚠️ arm are reachable in the `disabled` default — otherwise a run from an unrelated or stale checkout reports green gates with nothing saying which code they ran on. **Trade-off accepted, and bounded**: on `disabled` this costs one code-host round trip per run the pre-#382 flow did not make (with tiering enabled the tier needs it anyway); **skipped entirely with no code-host remote**; degrades gracefully — an unreachable host renders `Tree: unknown` and changes no gate. The host command's request-timeout knob is set **where it offers one**; GitHub's `gh` exposes **none**, so on the reference host the residual cost of an *unreachable* host is `gh`'s default timeout. Accepted **with no session bound, because none is implemented**: `resolve_pr_tree` re-initializes its names and re-reads on **every** call and each gate invocation is a separate process, so the cost is one read **per run** — one `gh` default timeout **per task gate** on a configured-but-unreachable host in the `disabled` default (`/pair-process-implement` gates once per task, `/pair-capability-publish-pr` once as a pre-flight). The one mitigation is the documented `pr_view_json` **override**: an offline session installs a fail-fast definition before sourcing the asset and lands on `unknown`, which changes no gate. Memoizing a failed read was rejected (Alternatives); the asset comment and `verify-quality` Step 1.5 state the per-run cost and that mitigation, and a conformance property bans a "once per session" claim in either place. The match test is always `git rev-parse HEAD` vs. the PR's `headRefOid`, never branch names (display only). **Six resolved values, six rendered arms** — `match`; `ahead` (strictly ahead of the PR head: the canonical pre-push state `/pair-process-implement` and `/pair-capability-publish-pr` produce every task, so *reported*, not warned — a ⚠️ on the expected state trains the reader to ignore the one meaning "other code"); `mismatch` (stale or divergent ⇒ ⚠️); `unknown` (PR unreadable — never assert an unread mismatch — rendered in **two spellings**, since `PR_NUM` is empty on the no-`$pr` path and one numbered arm would print the malformed `PR # unreadable` on every unauthenticated or offline default run); `none` (no PR — pre-publish, the host *answered* so); `no-remote` (**the read was skipped**: no code-host remote configured — merging it into `unknown` misattributes configuration to the network and, by leaving the pre-publish flag down, dropped the `$story` fallback for a repo provably without a PR; so it raises that flag and carries its own `Tier source:`/reason wording). The identity half is **pinned to a commit locally too**: `git rev-parse --abbrev-ref HEAD` is a moving BRANCH NAME and yields literal `HEAD` when **detached**, so the row renders `<branch>@<sha7>` (short sha alone when detached). The sha is one `git rev-parse --short HEAD`, resolved once and reused — a row naming only `main` on the `mismatch` arm says which code was NOT run, not which WAS.
5. **Only `TREE_MATCH=match` is authoritative — the rule keys on the RESOLVED VALUE, not on the ⚠️ glyph — and absence of a CI conclusion is not a green.** For both uses (`/pair-process-review` Step 2.1's `resolve_pr_state <gates> …` synthesis *and* the verdict cap): the local run is authoritative **only** when `Tree:` resolved to `match`; `ahead`, `mismatch`, `unknown` and `none` are **advisory**, and CI's conclusion on the PR **head commit** is authoritative. A glyph-keyed rule broke once `ahead` was split from `mismatch`: it reads `ahead` — the implement→review→fix loop's state on **every** locally committed, unpushed fix — as authoritative and lets a PR reach `pr-state:ready-to-merge` on code the PR does not contain; `unknown` is the same hole. Redirecting `<gates>` to CI requires **naming the SET**: the **mechanical gate checks only** — the branch protection's required contexts **minus `pair-review` and `pair-explicit-approval`**. Those are outputs of *this* flow, already carried on **separate** axes by `resolve_pr_state <gates> <review> <tier> <explicit_approval>` (`pair-review` registered *pending* at t0 by `/pair-capability-publish-pr` and concluded only in Step 5.4; `pair-explicit-approval` fails at 🔴 until a human approves); folding either into `gates` double-counts it and, since the evaluator short-circuits on a non-`pass` gate, makes `pr-state:ready-to-merge` unreachable **by construction** on every advisory arm, with the verdict also capped by the flow's own pending self-check. Where the target branch is **not protected** (or its required set is unreadable — the degraded, non-blocking configuration pr-states.md documents, and this repository's own) the fallback is **defined**: every non-`pair-*` check reported on the head commit, `Gates: pending` when none. When CI has published **no** conclusion on that commit (first minutes after a push; permanently on a host with no checks) it resolves **not green** (`Gates: pending`) ⇒ `pr-state:to-be-reviewed`, never `ready-to-merge`: a state flow never promotes on absence of evidence. An advisory run contributes review **findings** and never blocks the PR on evidence declared advisory.
6. **Every failure state has its own reason; emptiness and bare exit status decide nothing.** `gh pr view` exits non-zero both when the branch has no PR and when the host is unreachable, and a PR with **zero labels** is a third state — so the branch arm decides on the host's *no-PR message* (the only case that may fall through to `$story`) and on *tag presence*, never on `[ -z "$LABELS" ]`. An unreadable branch PR fails safe with `current-branch PR unreadable`, symmetric with `$pr`, rather than degrading to the card's refinement tier (an under-check).
7. **Nothing the step reads may be unassigned, and identifiers are normalized by structure.** Every variable the snippet reads is initialized at the top of the step — `LABELS` included (three arms fall through to `resolve_tier "$LABELS"` without assigning it) — **including the two names read OUTSIDE the step**, `TIER` and `ACTIVE_SUITES`: Step 4 runs "only the suites in `ACTIVE_SUITES`", while the two no-tag arms (tiering `disabled` — the default — and the matrix fallback) describe the widest set in *prose*; a surviving narrower value would make Step 4 run **less**. Both are initialized to the widest value (`ACTIVE_SUITES=all`, a sentinel Step 4 defines as "every adopted gate") and re-assigned on those arms explicitly. The step **installs no `trap … EXIT`** for its stderr temp file: an EXIT trap is a shell **global** and would discard a caller's handler, while no arm of the read chain exits early, so the explicit `rm -f` suffices. The skill is idempotent and re-invoked in shells where previous variables survive; an unassigned read would resolve the *previous* tier — a silent **narrow** on fail-safe paths. A conformance property (not a spelling ban) asserts no name is read before assignment. A `$pr` URL is normalized from its `pull/<n>` **path segment**, never the string tail (`…/pull/420/files` has no trailing digits; `…/pull/420#issuecomment-98765` ends in a comment id), and the **read consumes the normalized value**, not the raw `$pr` — otherwise a host rejecting a trailing segment or fragment fail-safes as "unreadable — nonexistent identifier, or the code host is not reachable", a parsing problem misattributed to the host. A bare number is unambiguous for every host, so non-GitHub substitutions inherit the normalization. Accepted forms: `420`, `#420`, and a `pull|pull-requests|merge_requests/<n>` URL. **`#420` is how this corpus writes PR references everywhere**; echoed verbatim it renders `PR ##420 unreadable` and hands a non-GitHub host an identifier it may reject — so the leading `#` is stripped in the bare-number branch.

## Alternatives Considered

- **Pass the tier `/pair-process-review` resolved in Phase 1** (`$tier=yellow`): Rejected. A second source of truth needing its own widen-only guard, and a stale or hand-written value narrows the set CI would run. Reading labels keeps one authority — the one CI gates on.
- **Reuse `$story` instead of adding `$pr`**: Rejected. The card carries the **refinement-time** tier and review confirms-or-**raises** (D17): a PR raised at review would run a **NARROWER** set than CI — the under-check the quality model forbids. `$story` stays the pre-publish fallback.
- **Compare branch NAMES when attached, commits only when detached** — or **promote to `match` on branch identity alone** on the current-branch path: Rejected (both were intermediate implementations). `headRefOid` is fetched either way; the name arm reports `matches PR #N's head` for a stale or unpushed-ahead checkout of the same branch — which the standalone pre-push flow hits by construction (commit, gate, then push).
- **Memoize a failed PR read across invocations (a `PR_READ_FAILED` sentinel)**: Rejected — this was the "once per session" bound decision 4 once *claimed* while nothing implemented it. (a) Every gate invocation is a **separate process**, so a shell-local sentinel never reaches the next gate and the rule would be prose to the agent — the prose-only arm banned elsewhere. (b) A read skipped because an earlier one failed is a **seventh state** needing its own `Tree:` arm, `Tier source:` value and reason ("a skipped read is not a failed one", why `no-remote` exists). (c) It goes **stale**: a host recovering mid-session is not re-read, so every later gate renders `Tree: unknown` and fail-safes 🔴 — a one-off timeout becomes a permanent over-check. No test can hold its invalidation rule; the per-run cost plus the fail-fast override can.
- **Let a supplied `$pr` with no tag fall through**: Rejected. It reads a *different* PR or the card's refinement tier while the report claims the named PR. Fail-safe 🔴 with the actual cause is wider but never wrong, and surfaces the configuration problem.

## Consequences

- The review path runs the CI check set for the PR's real tier — 🟢/🟡 work stops running the 🔴 set — while an untagged or unreadable PR still widens to 🔴.
- `$pr` is **optional and additive** for the **composition contract** of every existing caller (`/pair-process-implement`, `/pair-capability-publish-pr`, direct pre-push): same PASS/FAIL shape, same precedence. The **run** differs: in the `Pre-merge tiering: disabled` default they pay one code-host read for the `Tree:` row (skipped with no remote), and the report gains that row. The Arguments table states the narrow claim.
- The label read is only as exact as the tag projection: with no `## Tag Projection` in `tech/risk-matrix.md`, `/pair-capability-classify` writes the matrix to the PR description and applies no label, so the `$pr` read fail-safes to 🔴 by design; `/pair-process-review` states this qualification.
- Only `match` is authoritative (decision 5), now also in the `disabled` default this repository runs. **Accepted**: the loop's normal state is `ahead`, so a review from that worktree gets an advisory local run and reads CI on the head commit — wider, never narrower.
- One read point for both paths: labels, `headRefName`, `headRefOid` and `number` from a single `gh pr view … --json labels,headRefName,headRefOid,number`, so an unreadable PR cannot half-succeed and render an unestablished relation. On `disabled` its labels go unconsumed. **Per run means per run** (decision 4); neither skill nor asset may claim a per-session bound (conformance-pinned).
- **The `<gates>` axis is the mechanical checks only** (decision 5); a conformance assertion pins the exclusion of `pair-review` and `pair-explicit-approval` so the deadlock cannot return.
- **The skill carries the RULE; this record carries the ARGUMENT.** Step 1.5's shell comments state the rule and a one-line why; the justifications (commit compare, three states behind one failing read, stale-variable/idempotency, round-trip trade-off) live here only — two unchecked prose copies would drift.
- **The standalone on-branch path differs from pre-#382, deliberately, only in the widening direction**: (a) a branch PR with **zero labels** no longer falls back to the card (fail-safe 🔴, own reason); (b) a **failed** branch-PR read no longer falls back (⇒ `current-branch PR unreadable`); (c) `Tree:` is a **commit** compare, so a stale/divergent checkout reports `⚠️` and an unpushed-ahead one `ahead` where branch identity reported a match; (d) with **no code-host remote** the read is skipped and the row renders `no-remote` — provably no PR, so a supplied `$story` **still** resolves the tier, and without one the report names `no code-host remote — no PR to read` rather than blaming the host. All four widen or inform, never under-check.

## Adoption Impact

- No adoption file change: two skills' contracts (`capability/verify-quality`, `process/review`) and their mirrors change. `tech/way-of-working.md` (Quality Gates), `tech/risk-matrix.md` (Tag Projection) and the quality model's tier→checks matrix are **consumed** unchanged.
- An ADL, not an ADR: no new library, pattern or technology (ADR-013's resolution cascade and D17/D18 applied, not amended).
