# Decision: /pair-process-review forwards a PR IDENTIFIER to verify-quality, never the resolved tier — and a supplied `$pr` never falls through

## Date

2026-08-11

## Status

Active

## Category

Process Decision

## Context

`/pair-capability-verify-quality` resolves the `risk:*` tier from the **current-branch** PR (`gh pr view` with no argument) — the standalone pre-push developer flow. `/pair-process-review` composes it from a context that is usually **not** the PR's branch (a detached review worktree, or a bare-repo review session), so the no-arg read finds no PR, the resolution fail-safes to 🔴, and the review path runs the full suite set on every PR regardless of tier. The tier-check parity #259 established for the pre-push path therefore never held on the review path, which is the path the CI gate is compared against.

Fixing it requires deciding **what crosses the composition boundary**: `/pair-process-review` has already resolved an authoritative review-time tier in its Phase 1 (`/pair-capability-classify`, confirm-or-raise, D17), so handing that value to `verify-quality` is the obvious move — and the wrong one.

## Decision

`verify-quality` takes an **optional `$pr` argument that names WHICH PR the tier is resolved from**. The tier itself is **read, never carried**:

1. **Name the PR, never carry the tier.** `$pr` is an identifier (number or URL). `verify-quality` reads that PR's `risk:*` labels from the **code host** — the same source the CI gate reads. Nothing but an identifier crosses the boundary, so there is no second copy of the tier to keep consistent and no widen-only guard of its own is needed: the labels stay the single source of truth, review-raised (D17) tags included.
2. **No story-card fallback on the `$pr` path.** Resolution precedence is `$pr` → current-branch PR → `$story` card → fail-safe 🔴, and an entry is consulted only when the ones before it were **not supplied** — never as a retry of one that failed. A supplied `$pr` that yields no tag resolves to the fail-safe with its own specific reason ("reachable but carries no `risk:*` tag" vs. "unreadable"), distinguished by a **`risk:`-prefix test on the labels, not by empty labels** — a PR labelled `pr-state:*`/`cost:*`/type and no `risk:*` is the normal shape once the PR state flow is provisioned, and an emptiness test would misreport it as sourceless.
3. **Tier parity is not result parity — and both report rows are RESOLVED, not improvised.** `$pr` makes the *tier* exact, not the *result*: off-branch the suites still run against the checked-out tree. The report states `Tier source:` and `Tree:` separately, and the caller's advisory rule keys on the `Tree:` row's **resolved value** (decision 5) — for the PR state synthesis the authoritative gate signal is CI's check on the PR head commit (read from the code host by a **named, routed** command, `gh pr checks` on GitHub: an unnamed read on the input that decides `ready-to-merge` is a guess). Both rows are snippet variables with one value per rendered arm — `TREE_MATCH` and `TIER_SOURCE` — for the same reason: a reading agent improvising the source row has no true arm for "a PR was named but could not be read" (claiming `PR #N (named by $pr)` asserts a tier read from an unreadable PR; claiming `fail-safe — no source resolved` denies a source that *was* named). That holds for the modes that read **no tag at all**: the `Pre-merge tiering: disabled` default and the matrix-not-found fallback **assign** `TIER_SOURCE` (`n/a (tiering disabled — no tag read)` / `n/a (matrix fallback — no tag read)`) rather than asking in prose for a value the variable does not hold — otherwise the live, default configuration renders the `fail-safe — no source resolved` initializer on a run that never attempted a tier read. A conformance property requires **exact correspondence in both directions** between the assigned values and the rendered arms of each row, so a prose-only arm fails the suite.
4. **The tree question is tier-independent, and it is a COMMIT question — on BOTH resolution paths, from ONE read.** `Tree:` is resolved *before* the `Pre-merge tiering` flag is read, and that includes the **checked-out branch's own PR**: a single read point serves the `$pr` path and the no-arg path alike, so the row and its ⚠️ arm are reachable in the default `disabled` configuration on either path — otherwise a run from an unrelated or stale checkout reports green gates with nothing saying which code they ran on. **Trade-off accepted, and bounded**: on the `disabled` default this costs one code-host round trip per run that the pre-#382 flow did not make (with tiering enabled it is the read the tier resolution needs anyway); it is **skipped entirely when the repository has no code-host remote** (the round trip cannot pay — there is no PR to read), and it degrades gracefully — an unreachable host renders `Tree: unknown` and changes no gate. On the timeout: the host command's request-timeout knob is set **where it offers one**, so an offline or rate-limited session fails fast instead of hanging on every task gate — GitHub's `gh` exposes **none**, so on the reference host that mitigation is a no-op and the residual cost of an *unreachable* host is `gh`'s own default timeout. Accepted **with no session bound, because none is implemented**: `resolve_pr_tree` re-initializes its names and re-invokes the read on **every** call and each gate invocation is a separate process, so the honest cost is one read **per run** — i.e. one `gh` default timeout **per task gate** on a configured-but-unreachable host in the `disabled` default (`/pair-process-implement` composes the gate once per task, `/pair-capability-publish-pr` once as a pre-flight). The one mitigation that exists is the documented `pr_view_json` **override**: a session that must run offline against a configured remote installs a fail-fast definition before sourcing the asset, and lands on the `unknown` arm, which changes no gate. Memoizing a failed read across invocations was considered and rejected (see Alternatives) — the asset comment and `verify-quality` Step 1.5 state the per-run cost and that mitigation, and a conformance property bans the "once per session" claim in either place, because a bound nothing implements misinforms the merge decision it is offered to. The match test is always `git rev-parse HEAD` vs. the PR's `headRefOid`, never branch names, which stay display only. **Six resolved values, six rendered arms** — `match`, `ahead` (this tree is strictly ahead of the PR head: the canonical pre-push state `/pair-process-implement` and `/pair-capability-publish-pr` produce on every task, so it is *reported*, not warned — a ⚠️ on the normal expected state trains the reader to ignore the one that means "other code"), `mismatch` (stale or divergent ⇒ ⚠️), `unknown` (PR unreadable: never assert a mismatch that could not be read — rendered in **two spellings**, since `PR_NUM` is empty on the no-`$pr` path and a single numbered arm would print the malformed `PR # unreadable` on every unauthenticated or offline run of the *default* configuration), `none` (no PR at all — pre-publish, the host having *answered* so), and `no-remote` (**the read was skipped**: no code-host remote is configured — not the same fact as an unreachable host, and merging it into `unknown` both misattributes a configuration problem to the network and, by leaving the pre-publish flag down, silently dropped the `$story` fallback for a repo that provably has no PR; the skipped state therefore raises that flag and carries its own `Tier source:`/reason wording). The identity half of the row is resolved too, and **pinned to a commit on the local side as well**: `git rev-parse --abbrev-ref HEAD` is a BRANCH NAME, which moves, and yields the literal `HEAD` in a **detached** checkout — so the row renders `<branch>@<sha7>` (the short sha alone when detached, where the two coincide). A row naming only `main` as the code that ran tells the reader which code was NOT run and not which code WAS, on the very arm (`mismatch`) whose purpose is to say so; the sha is one `git rev-parse --short HEAD`, resolved once and reused.
5. **Only `TREE_MATCH=match` is authoritative — the rule keys on the RESOLVED VALUE, not on the ⚠️ glyph — and absence of a CI conclusion is not a green.** Stated once, for both uses (`/pair-process-review` Step 2.1's `resolve_pr_state <gates> …` synthesis *and* the verdict cap): the local run is authoritative **only** when `Tree:` resolved to `match` (the checked-out tree IS the PR's head commit); `ahead`, `mismatch`, `unknown` and `none` are all **advisory**, and on each of them CI's conclusion on the PR **head commit** is the authoritative signal. Keying the rule on the glyph instead was wrong once `ahead` was split out of `mismatch` (decision 4): ⚠️ then marks `mismatch` alone, so a glyph-keyed rule reads `ahead` — the state the implement→review→fix loop produces on **every** locally committed, not-yet-pushed fix — as authoritative and lets a PR reach `pr-state:ready-to-merge` on gates that ran over code the PR does not contain and CI has never seen; `unknown` (the relation could not be established) is the same hole with no glyph either. Redirecting `<gates>` to CI's check requires **naming the SET** it reads, not only the command: the authoritative read is the **mechanical gate checks only** — the branch protection's required contexts **minus `pair-review` and `pair-explicit-approval`**. Those two are outputs of *this* flow and `resolve_pr_state <gates> <review> <tier> <explicit_approval>` already carries them on **separate** axes (`pair-review` is registered *pending* at t0 by `/pair-capability-publish-pr` and concluded only in Step 5.4 itself; `pair-explicit-approval` fails at 🔴 until a human approves), so folding either into `gates` double-counts it — and because the evaluator short-circuits on a non-`pass` gate, `pr-state:ready-to-merge` would be unreachable **by construction** on every advisory arm, i.e. on the implement→review→fix loop's *normal* state, with the verdict additionally capped by the flow's own pending self-check. Where the target branch is **not protected** (or its required set cannot be read — the degraded configuration pr-states.md documents as non-blocking, and the configuration this repository itself runs) the required set resolves to nothing, so the fallback is **defined** rather than left open: every non-`pair-*` check reported on the head commit, and `Gates: pending` when none is reported. Redirecting `<gates>` also needs the arm where CI has published **no** conclusion on that commit — the normal state in the first minutes after a push and the permanent state on a host with no checks. That arm resolves to **not green** (`Gates: pending`) ⇒ `pr-state:to-be-reviewed`, never `ready-to-merge`: a state flow may never promote on absence of evidence. An advisory run therefore contributes review **findings** and never blocks the PR on evidence the same step declared advisory.
6. **Every failure state has its own reason; emptiness and bare exit status decide nothing.** `gh pr view` exits non-zero both when the branch has no PR and when the code host is unreachable, and a PR that exists with **zero labels** is a third state — so the branch arm decides on the host's *no-PR message* (the only case that may fall through to `$story`) and on *tag presence*, never on `[ -z "$LABELS" ]`. An unreadable branch PR fails safe with `current-branch PR unreadable`, symmetric with the `$pr` path, rather than degrading to the story card's refinement tier (an under-check).
7. **Nothing the step reads may be unassigned, and identifiers are normalized by structure.** Every variable the resolution snippet reads is initialized at the top of the step — `LABELS` included, since three arms fall through to `resolve_tier "$LABELS"` without assigning it — **and that includes the two names read OUTSIDE the step**, `TIER` and `ACTIVE_SUITES`: Step 4 runs "only the suites in `ACTIVE_SUITES`", while the two arms that read no tag (tiering `disabled` — the default — and the matrix fallback) describe the widest set in *prose*. Left unassigned there, a previous run's narrower value surviving in the shell makes Step 4 run **less** than the arm demands, so both are initialized to the widest value (`ACTIVE_SUITES=all`, a sentinel Step 4 defines as "every adopted gate") and re-assigned on those arms explicitly. The step also **installs no `trap … EXIT`** for its stderr temp file: an EXIT trap is a shell **global**, so installing (and then clearing) one discards the handler a caller or sourcing wrapper may already own — state this snippet does not own — while no arm of its read chain can exit early, which makes the explicit `rm -f` sufficient. The skill is idempotent by contract, so it is re-invoked in shells where the previous run's variables survive; an unassigned read would resolve the *previous* run's tier, i.e. a silent **narrow** on precisely the paths whose purpose is to fail safe. A conformance property (not a spelling ban) asserts the invariant: no name is read before it is assigned. For the same "no wrong identifier in a fail-safe reason" reason, a `$pr` URL is normalized from its `pull/<n>` **path segment**, never from the string tail — `…/pull/420/files` has no trailing digits and `…/pull/420#issuecomment-98765` ends in a comment id — and the **read consumes that normalized value**, not the raw `$pr`: a host command handed a URL with a trailing segment or a fragment may reject it, and a documented-as-accepted input would then fail-safe reporting "unreadable — nonexistent identifier, or the code host is not reachable", i.e. a parsing problem misattributed to an unreachable host. A bare number is unambiguous for every host, so each non-GitHub substitution inherits the normalization instead of re-implementing URL parsing. The accepted forms are `420`, `#420`, and a `pull|pull-requests|merge_requests/<n>` URL: the **`#420` spelling is the one this corpus writes PR references in everywhere**, and letting it fall through to the verbatim echo renders the malformed `PR ##420 unreadable` and hands a non-GitHub host an identifier it may reject — the same misattribution one paragraph earlier forbids. The leading `#` is therefore stripped in the bare-number branch, not echoed.

## Alternatives Considered

- **Pass the tier value `/pair-process-review` already resolved in Phase 1** (`$tier=yellow`): Rejected. It creates a second source of truth for the tier that must then be kept widen-only by its own guard, and it lets a caller under-check by construction (any caller passing a stale or hand-written value narrows the set CI would run). Reading the labels keeps exactly one authority — the one CI gates on.
- **Reuse the existing `$story` argument instead of adding `$pr`**: Rejected. The story card carries the **refinement-time** tier, and review confirms-or-**raises** (D17). A PR raised at review time would resolve to the card's *lower* tier and run a **NARROWER** set than CI — an under-check, the one direction the quality model forbids. `$story` stays what it is: the pre-publish fallback for a branch that has no PR yet.
- **Compare branch NAMES when the checkout is attached, commits only when detached** — or, weaker still, **promote to `match` on branch identity alone** on the current-branch path: Rejected (both were intermediate implementations). The commit compare is correct in both shapes — `headRefOid` is fetched either way — so the name arm was strictly weaker: it reports `matches PR #N's head` for a stale or unpushed-ahead checkout of the same branch, which is precisely the "confident report about different code" the `Tree:` row exists to prevent, and which the *standalone pre-push developer flow* hits by construction (commit locally, run the gate, then push).
- **Memoize a failed PR read across invocations (a `PR_READ_FAILED` sentinel reused by later task gates)**: Rejected — this was the "once per session" bound decision 4 previously *claimed*, and the claim shipped while nothing implemented it. (a) Its propagation cannot be implemented here: every gate invocation is a **separate process** (an agent's bash call, a per-task `/pair-process-implement` gate), so a shell-local sentinel never reaches the next task gate and the carrying rule would have to be prose addressed to the executing agent — the prose-only arm this record bans elsewhere. (b) A read skipped because a previous one failed is a **seventh state**: decision 4's own rule ("a skipped read is not a failed one", the reason `no-remote` exists) then demands its own `Tree:` arm, `Tier source:` value and reason, or the report misattributes a cache hit to an unreachable host. (c) The sentinel goes **stale**: a host that recovers mid-session is not re-read (nothing pushed, nothing to trigger the documented re-read), so every later gate renders `Tree: unknown` and fail-safes 🔴 — turning a one-off timeout into a permanent over-check plus a row that states no relation at all. The cost being confined to degraded-network sessions and never changing a verdict does not buy a cache whose invalidation rule no test can hold; the honest per-run cost plus the fail-fast override does.
- **Let a supplied `$pr` that yields no tag fall through to the next precedence entry**: Rejected. Falling through reads either a *different* PR (the branch's) or the refinement tier (the card's) while the report still claims to describe the named PR. Failing safe to 🔴 with a reason naming the actual cause is wider but never wrong, and it surfaces the configuration problem instead of hiding it behind a correct-looking widen.

## Consequences

- The review path runs the CI check set for the PR's real tier — 🟢/🟡 work in review stops running the 🔴 suite set — while an untagged or unreadable PR still widens to 🔴 rather than narrowing.
- `$pr` is **optional and additive** in the precise sense that the **composition contract** is unchanged for every existing caller (`/pair-process-implement`, `/pair-capability-publish-pr`, direct pre-push invocations): same PASS/FAIL shape, same resolution precedence. The **run** is not identical — in the `Pre-merge tiering: disabled` default those callers now pay one code-host read (for the tier-independent `Tree:` row, skipped with no remote) where that mode previously made none, and their report gains a `Tree:` row. The skill's Arguments table states the narrow claim, not the broad one.
- The label read is only as exact as the project's tag projection: with no `## Tag Projection` declared in `tech/risk-matrix.md`, `/pair-capability-classify` writes the matrix to the PR description and applies no label, so the `$pr` read fail-safes to 🔴 by design. `/pair-process-review` states this qualification rather than promising exactness the flow cannot deliver in that configuration.
- A local gate run is authoritative only when `Tree:` resolved to `match`; every other arm (`ahead`, `mismatch`, `unknown`, `none`) is advisory and can never contribute a green to `ready-to-merge`. The required CI checks on the head commit remain authoritative there. Because the tree resolution is tier-independent, that rule now fires in the default `Pre-merge tiering: disabled` configuration as well — the configuration this repository itself runs. **Practical consequence, accepted**: the implement→review→fix loop's normal state is `ahead` (a fix committed locally, gates run, not yet pushed), so a review composed from that worktree gets an advisory local run and must read CI on the head commit for its state synthesis — wider than before, never narrower.
- One code-host round trip per run, from ONE read point shared by both paths: labels, `headRefName`, `headRefOid` and `number` come from a single `gh pr view … --json labels,headRefName,headRefOid,number` read — `$pr` and current-branch use the same field set and the same arms — so an unreadable PR cannot half-succeed (some fields empty, some read) and render a relation it never established. In the `Pre-merge tiering: disabled` default that read is made for the `Tree:` row alone and its labels go unconsumed (see Decision 4's trade-off). **Per run means per run**: nothing is memoized between invocations, so a caller that gates once per task pays it once per task, and on a configured-but-unreachable host that is one `gh` default timeout per task gate — the only mitigation being the fail-fast `pr_view_json` override. The skill and the asset state that cost as it is paid; neither may claim a per-session bound (conformance-pinned).
- **The `<gates>` axis is the mechanical checks only.** `pair-review` and `pair-explicit-approval` are excluded by name from the CI read `/pair-process-review` Step 2.1 feeds to `resolve_pr_state`, because that function already takes the review verdict and the explicit approval as its own arguments. Without the exclusion the advisory arms — the loop's normal state — could never reach `pr-state:ready-to-merge`, and a conformance assertion now pins the exclusion so the deadlock cannot be re-introduced.
- **The skill carries the RULE; this record carries the ARGUMENT.** Step 1.5's shell comments state the rule and a one-line why; the multi-sentence justifications (the commit compare, the three states behind one failing read, the stale-variable/idempotency argument, the round-trip trade-off) live here only. Two prose copies of the same reasoning in two files that no test cross-checks is a drift surface, and the agent executing the step needs the rule, not the debate.
- **The standalone on-branch path is not byte-identical to the pre-#382 behaviour, deliberately, and only in the widening direction**: (a) a branch PR that exists with **zero labels** no longer falls back to the story card (it is reachable-with-no-tag ⇒ fail-safe 🔴 with its own reason), (b) a **failed** branch-PR read no longer falls back either (⇒ `current-branch PR unreadable`), (c) the `Tree:` row on that path is now a **commit** compare, so a stale or divergent checkout reports `⚠️` and an unpushed-ahead one reports `ahead` where branch identity would have reported a match, and (d) a repository with **no code-host remote** skips the PR read entirely: the row renders its own `no-remote` arm instead of `unknown`, and — because no remote means provably no PR, i.e. the pre-publish shape — a supplied `$story` **still** resolves the tier from the card (the fallback's purpose), while with no `$story` the report names the missing configuration (`no code-host remote — no PR to read`) rather than blaming an unreachable host. All four are widen-or-inform only — never an under-check — (c) makes the pre-push flow's report *truthful* about which code the suites ran on, which is the point of the row, and (d) exists so the skipped read is not misreported as a failed one.

## Adoption Impact

- No adoption file change is required: this decision alters two skills' contracts (`capability/verify-quality`, `process/review`) and their generated mirrors, not a project convention. `tech/way-of-working.md` (Quality Gates), `tech/risk-matrix.md` (Tag Projection) and the quality model's tier→checks matrix are all **consumed** unchanged.
- Recorded as an ADL, not an ADR: no new library, pattern or technology is introduced (ADR-013's resolution cascade and D17/D18 are applied, not amended).
