# Decision: /review forwards a PR IDENTIFIER to verify-quality, never the resolved tier — and a supplied `$pr` never falls through

## Date

2026-08-11

## Status

Active

## Category

Process Decision

## Context

`/pair-capability-verify-quality` resolves the `risk:*` tier from the **current-branch** PR (`gh pr view` with no argument) — the standalone pre-push developer flow. `/pair-process-review` composes it from a context that is usually **not** the PR's branch (a detached review worktree, or a bare-repo review session), so the no-arg read finds no PR, the resolution fail-safes to 🔴, and the review path runs the full suite set on every PR regardless of tier. The tier-check parity #259 established for the pre-push path therefore never held on the review path, which is the path the CI gate is compared against.

Fixing it requires deciding **what crosses the composition boundary**: `/review` has already resolved an authoritative review-time tier in its Phase 1 (`/classify`, confirm-or-raise, D17), so handing that value to `verify-quality` is the obvious move — and the wrong one.

## Decision

`verify-quality` takes an **optional `$pr` argument that names WHICH PR the tier is resolved from**. The tier itself is **read, never carried**:

1. **Name the PR, never carry the tier.** `$pr` is an identifier (number or URL). `verify-quality` reads that PR's `risk:*` labels from the **code host** — the same source the CI gate reads. Nothing but an identifier crosses the boundary, so there is no second copy of the tier to keep consistent and no widen-only guard of its own is needed: the labels stay the single source of truth, review-raised (D17) tags included.
2. **No story-card fallback on the `$pr` path.** Resolution precedence is `$pr` → current-branch PR → `$story` card → fail-safe 🔴, and an entry is consulted only when the ones before it were **not supplied** — never as a retry of one that failed. A supplied `$pr` that yields no tag resolves to the fail-safe with its own specific reason ("reachable but carries no `risk:*` tag" vs. "unreadable"), distinguished by a **`risk:`-prefix test on the labels, not by empty labels** — a PR labelled `pr-state:*`/`cost:*`/type and no `risk:*` is the normal shape once the PR state flow is provisioned, and an emptiness test would misreport it as sourceless.
3. **Tier parity is not result parity — and both report rows are RESOLVED, not improvised.** `$pr` makes the *tier* exact, not the *result*: off-branch the suites still run against the checked-out tree. The report states `Tier source:` and `Tree:` separately, and the caller's advisory rule keys on the `Tree:` row's **resolved value** (decision 5) — for the PR state synthesis the authoritative gate signal is CI's check on the PR head commit (read from the code host by a **named, routed** command, `gh pr checks` on GitHub: an unnamed read on the input that decides `ready-to-merge` is a guess). Both rows are snippet variables with one value per rendered arm — `TREE_MATCH` and `TIER_SOURCE` — for the same reason: a reading agent improvising the source row has no true arm for "a PR was named but could not be read" (claiming `PR #N (named by $pr)` asserts a tier read from an unreadable PR; claiming `fail-safe — no source resolved` denies a source that *was* named). That holds for the modes that read **no tag at all**: the `Pre-merge tiering: disabled` default and the matrix-not-found fallback **assign** `TIER_SOURCE` (`n/a (tiering disabled — no tag read)` / `n/a (matrix fallback — no tag read)`) rather than asking in prose for a value the variable does not hold — otherwise the live, default configuration renders the `fail-safe — no source resolved` initializer on a run that never attempted a tier read. A conformance property requires **exact correspondence in both directions** between the assigned values and the rendered arms of each row, so a prose-only arm fails the suite.
4. **The tree question is tier-independent, and it is a COMMIT question — on BOTH resolution paths, from ONE read.** `Tree:` is resolved *before* the `Pre-merge tiering` flag is read, and that includes the **checked-out branch's own PR**: a single read point serves the `$pr` path and the no-arg path alike, so the row and its ⚠️ arm are reachable in the default `disabled` configuration on either path — otherwise a run from an unrelated or stale checkout reports green gates with nothing saying which code they ran on. **Trade-off accepted**: on the `disabled` default this costs one code-host round trip per run that the pre-#382 flow did not make (with tiering enabled it is the read the tier resolution needs anyway), and it degrades gracefully — an unreachable host renders `Tree: unknown` and changes no gate. The match test is always `git rev-parse HEAD` vs. the PR's `headRefOid`, never branch names, which stay display only. **Five resolved values, five rendered arms** — `match`, `ahead` (this tree is strictly ahead of the PR head: the canonical pre-push state `/implement` and `/publish-pr` produce on every task, so it is *reported*, not warned — a ⚠️ on the normal expected state trains the reader to ignore the one that means "other code"), `mismatch` (stale or divergent ⇒ ⚠️), `unknown` (PR unreadable: never assert a mismatch that could not be read — rendered in **two spellings**, since `PR_NUM` is empty on the no-`$pr` path and a single numbered arm would print the malformed `PR # unreadable` on every unauthenticated or offline run of the *default* configuration), `none` (no PR at all — pre-publish). The identity half of the row is resolved too: `git rev-parse --abbrev-ref HEAD` yields the literal `HEAD` in a **detached** checkout — the canonical independent-review/CI shape — so it is replaced by the short commit, since both renderings promise a commit there.
5. **Only `TREE_MATCH=match` is authoritative — the rule keys on the RESOLVED VALUE, not on the ⚠️ glyph — and absence of a CI conclusion is not a green.** Stated once, for both uses (`/review` Step 2.1's `resolve_pr_state <gates> …` synthesis *and* the verdict cap): the local run is authoritative **only** when `Tree:` resolved to `match` (the checked-out tree IS the PR's head commit); `ahead`, `mismatch`, `unknown` and `none` are all **advisory**, and on each of them CI's conclusion on the PR **head commit** is the authoritative signal. Keying the rule on the glyph instead was wrong once `ahead` was split out of `mismatch` (decision 4): ⚠️ then marks `mismatch` alone, so a glyph-keyed rule reads `ahead` — the state the implement→review→fix loop produces on **every** locally committed, not-yet-pushed fix — as authoritative and lets a PR reach `pr-state:ready-to-merge` on gates that ran over code the PR does not contain and CI has never seen; `unknown` (the relation could not be established) is the same hole with no glyph either. Redirecting `<gates>` to CI's check also needs the arm where CI has published **no** conclusion on that commit — the normal state in the first minutes after a push and the permanent state on a host with no checks. That arm resolves to **not green** (`Gates: pending`) ⇒ `pr-state:to-be-reviewed`, never `ready-to-merge`: a state flow may never promote on absence of evidence. An advisory run therefore contributes review **findings** and never blocks the PR on evidence the same step declared advisory.
6. **Every failure state has its own reason; emptiness and bare exit status decide nothing.** `gh pr view` exits non-zero both when the branch has no PR and when the code host is unreachable, and a PR that exists with **zero labels** is a third state — so the branch arm decides on the host's *no-PR message* (the only case that may fall through to `$story`) and on *tag presence*, never on `[ -z "$LABELS" ]`. An unreadable branch PR fails safe with `current-branch PR unreadable`, symmetric with the `$pr` path, rather than degrading to the story card's refinement tier (an under-check).
7. **Nothing the step reads may be unassigned, and identifiers are normalized by structure.** Every variable the resolution snippet reads is initialized at the top of the step — `LABELS` included, since three arms fall through to `resolve_tier "$LABELS"` without assigning it. The skill is idempotent by contract, so it is re-invoked in shells where the previous run's variables survive; an unassigned read would resolve the *previous* run's tier, i.e. a silent **narrow** on precisely the paths whose purpose is to fail safe. A conformance property (not a spelling ban) asserts the invariant: no name is read before it is assigned. For the same "no wrong identifier in a fail-safe reason" reason, a `$pr` URL is normalized from its `pull/<n>` **path segment**, never from the string tail — `…/pull/420/files` has no trailing digits and `…/pull/420#issuecomment-98765` ends in a comment id — and the **read consumes that normalized value**, not the raw `$pr`: a host command handed a URL with a trailing segment or a fragment may reject it, and a documented-as-accepted input would then fail-safe reporting "unreadable — nonexistent identifier, or the code host is not reachable", i.e. a parsing problem misattributed to an unreachable host. A bare number is unambiguous for every host, so each non-GitHub substitution inherits the normalization instead of re-implementing URL parsing.

## Alternatives Considered

- **Pass the tier value `/review` already resolved in Phase 1** (`$tier=yellow`): Rejected. It creates a second source of truth for the tier that must then be kept widen-only by its own guard, and it lets a caller under-check by construction (any caller passing a stale or hand-written value narrows the set CI would run). Reading the labels keeps exactly one authority — the one CI gates on.
- **Reuse the existing `$story` argument instead of adding `$pr`**: Rejected. The story card carries the **refinement-time** tier, and review confirms-or-**raises** (D17). A PR raised at review time would resolve to the card's *lower* tier and run a **NARROWER** set than CI — an under-check, the one direction the quality model forbids. `$story` stays what it is: the pre-publish fallback for a branch that has no PR yet.
- **Compare branch NAMES when the checkout is attached, commits only when detached** — or, weaker still, **promote to `match` on branch identity alone** on the current-branch path: Rejected (both were intermediate implementations). The commit compare is correct in both shapes — `headRefOid` is fetched either way — so the name arm was strictly weaker: it reports `matches PR #N's head` for a stale or unpushed-ahead checkout of the same branch, which is precisely the "confident report about different code" the `Tree:` row exists to prevent, and which the *standalone pre-push developer flow* hits by construction (commit locally, run the gate, then push).
- **Let a supplied `$pr` that yields no tag fall through to the next precedence entry**: Rejected. Falling through reads either a *different* PR (the branch's) or the refinement tier (the card's) while the report still claims to describe the named PR. Failing safe to 🔴 with a reason naming the actual cause is wider but never wrong, and it surfaces the configuration problem instead of hiding it behind a correct-looking widen.

## Consequences

- The review path runs the CI check set for the PR's real tier — 🟢/🟡 work in review stops running the 🔴 suite set — while an untagged or unreadable PR still widens to 🔴 rather than narrowing.
- `$pr` is **optional and additive**: every existing caller (`/pair-process-implement`, `/pair-capability-publish-pr`, direct pre-push invocations) is unchanged, and the composition contract's PASS/FAIL shape is unchanged.
- The label read is only as exact as the project's tag projection: with no `## Tag Projection` declared in `tech/risk-matrix.md`, `/classify` writes the matrix to the PR description and applies no label, so the `$pr` read fail-safes to 🔴 by design. `/review` states this qualification rather than promising exactness the flow cannot deliver in that configuration.
- A local gate run is authoritative only when `Tree:` resolved to `match`; every other arm (`ahead`, `mismatch`, `unknown`, `none`) is advisory and can never contribute a green to `ready-to-merge`. The required CI checks on the head commit remain authoritative there. Because the tree resolution is tier-independent, that rule now fires in the default `Pre-merge tiering: disabled` configuration as well — the configuration this repository itself runs. **Practical consequence, accepted**: the implement→review→fix loop's normal state is `ahead` (a fix committed locally, gates run, not yet pushed), so a review composed from that worktree gets an advisory local run and must read CI on the head commit for its state synthesis — wider than before, never narrower.
- One code-host round trip per run, from ONE read point shared by both paths: labels, `headRefName`, `headRefOid` and `number` come from a single `gh pr view … --json labels,headRefName,headRefOid,number` read — `$pr` and current-branch use the same field set and the same arms — so an unreadable PR cannot half-succeed (some fields empty, some read) and render a relation it never established. In the `Pre-merge tiering: disabled` default that read is made for the `Tree:` row alone and its labels go unconsumed (see Decision 4's trade-off).
- **The standalone on-branch path is not byte-identical to the pre-#382 behaviour, deliberately, and only in the widening direction**: (a) a branch PR that exists with **zero labels** no longer falls back to the story card (it is reachable-with-no-tag ⇒ fail-safe 🔴 with its own reason), (b) a **failed** branch-PR read no longer falls back either (⇒ `current-branch PR unreadable`), and (c) the `Tree:` row on that path is now a **commit** compare, so a stale or divergent checkout reports `⚠️` and an unpushed-ahead one reports `ahead` where branch identity would have reported a match. All three are widen-or-inform only — never an under-check — and (c) makes the pre-push flow's report *truthful* about which code the suites ran on, which is the point of the row.

## Adoption Impact

- No adoption file change is required: this decision alters two skills' contracts (`capability/verify-quality`, `process/review`) and their generated mirrors, not a project convention. `tech/way-of-working.md` (Quality Gates), `tech/risk-matrix.md` (Tag Projection) and the quality model's tier→checks matrix are all **consumed** unchanged.
- Recorded as an ADL, not an ADR: no new library, pattern or technology is introduced (ADR-013's resolution cascade and D17/D18 are applied, not amended).
